# ADR-0035 탈퇴 회원 차단을 인가 계층 한 곳으로 모은다

**상태**: Accepted (2026-09-05, Issue #106 에서 구현) — 결정은 그대로 유지됐다.
착수 전 열어 둔 5개 질문의 답과 구현 중 드러난 사실은
[PRD-021](../prd/PRD-021-탈퇴회원중앙차단.md) 에 있다. 이 문서는 고치지 않는다(ADR 불변).

**관계**: [ADR-0006](0006-auth-hardening.md) 의 "액세스 토큰을 DB 로 검증하지 않는다" 결정과
"즉시 무효화 불가" 한계 기술을 **부분 대체**한다. ADR-0006 의 나머지(해시 저장, 복합 유니크,
회전 등)는 그대로 유효하다.

**근거 자료**: [2026-09-04 인증 수명주기 E2E 검증](../verification/2026-09-04-auth-lifecycle-e2e.md)

## 맥락

### 실제로 일어난 일

탈퇴한 회원이 **탈퇴 전 발급받은 액세스 토큰**(TTL 30분)으로 실서버에 요청해 성공했다.
서버 재기동을 사이에 두고 두 번 재현했다.

| 요청 | 게스트(토큰 없음) | **탈퇴 회원** |
|---|---|---|
| `GET /auth/me` | 401 | 401 |
| `POST /users/profile` | 401 | 401 |
| `POST /posts/{id}/comments` | 401 | **201 CREATED** |
| `POST /posts/{id}/votes` | 401 | **200 OK** |
| `POST /comments/{id}/pick` | 401 | **201 CREATED** |

**탈퇴 회원이 게스트보다 권한이 많다.** 계정을 지운 사람이 한 번도 가입한 적 없는 사람보다
더 많은 것을 할 수 있다.

피해는 조회에 그치지 않는다. 원픽은 포인트를 지급하므로 **탈퇴 계정에 `PICKING +5`,
상대에게 `PICKED +10`** 이 적립됐다. 포인트는 TOP 피커 랭킹의 입력이고, `users.point` 집계는
배치가 나중에 채우므로(ADR-0028) **즉시 드러나지 않고 다음 재계산 때 오염이 표면화된다.**

### 왜 뚫렸나

`JwtAuthenticationFilter` 는 의도적으로 무상태다 — 액세스 토큰 클레임만으로
`SecurityContext` 를 채우고 DB 를 보지 않는다(ADR-0006 결정 10). 따라서 탈퇴 여부는
**각 서비스가 `isActive()` 를 직접 확인해야** 걸러진다.

그런데 확인 지점은 `AuthService`(3곳)·`UserProfileService`(1곳)·`User.registerProfile`·
`AccountWithdrawalPersistenceService` 뿐이고, **`vote`·`comment`·`point` 패키지에는 한 줄도
없다.** 막힌 두 엔드포인트는 우연히 그 확인을 하는 서비스를 지났을 뿐이다.

이 저장소에는 같은 문제를 이미 푼 선례가 있다 — `ActivePostGuard` 가
"투표·댓글·원픽이 저마다 확인하면 한 곳만 빠뜨려도 뚫린다" 며 관문을 하나로 모았다.
**다만 그 관문이 보는 것은 게시글의 생사이지 사용자의 생사가 아니다.**

즉 결함은 세 개가 아니라 **하나** 다. 탈퇴 사용자를 거르는 관문이 없다.

### ADR-0006 과의 충돌

ADR-0006 은 "액세스 토큰도 DB 조회로 검증" 을 **명시적으로 기각**했다
("즉시 무효화는 얻지만 매 요청 DB 를 때린다. 인증이 부하의 주범이 된다") 그리고
"액세스 토큰이 stateless 라 즉시 무효화가 불가능하다" 를 **수용한 한계**로 적었다.

**그 판단은 로그아웃을 전제로 쓰였다.** 로그아웃은 30분이면 자연 소멸하고 사용자가
스스로 한 행동이다. 탈퇴는 영구적이고, 위에서 보듯 **데이터와 원장을 오염시킨다.**
전제가 다르므로 재검토 대상이다.

ADR-0006 은 "측정 없이 미들웨어를 들이지 않는다" 는 원칙도 세웠다. 그래서 측정했다.

| 항목 | 실측 |
|---|---|
| `SELECT state FROM users WHERE id=?` | 0.03ms (warm), `type=const` / `key=PRIMARY` / `rows=1` |
| `GET /auth/me` | p50 6.2ms / p95 7.8ms (n=30 순차) |
| 동시 40요청(풀 10) | 전부 200, p50 6.0ms / p95 12.0ms |

**단, 이 측정을 "부하 문제 없음" 의 근거로 쓰지 않는다.** 빈 테이블·워밍된 버퍼 풀·
localhost 도커이고, 대조군(`/posts`)은 다른 컨트롤러라 한계비용을 분리하지 못한다.
**매 요청 도는 0.1ms 는 건당은 싸도 총 DB 용량을 지배할 수 있다.**

**따라서 ADR-0006 을 뒤집는 근거는 성능이 아니라 데이터 오염 증거다.**
측정이 말해주는 것은 "쿼리 모양이 건전해 시도해 볼 만하다" 까지다.

## 결정

**탈퇴 회원 차단을 인가 계층 한 곳으로 모은다.**

1. **`JwtAuthenticationFilter` 는 신원 확립까지만 한다.** 지금처럼 무상태로 토큰을 파싱해
   `SecurityContext` 를 채운다. **여기서 DB 를 보지 않는다.**
2. **계정 상태 판정은 `AuthorizationManager` 가 한다.** 보호 경로에 대해
   `users.id = ? AND state = 'ACTIVE'` 존재 확인을 수행하고, 아니면 거부한다.
   조회는 `User` 엔티티 전체 로딩이 아니라 **좁은 존재 확인 쿼리**여야 한다.
3. **실패를 구분해 응답한다.**
   - 토큰 무효·만료 → **401**
   - 토큰은 유효하나 계정이 비활성 → **401 또는 403** (정책으로 택일)
   - **DB 장애·풀 타임아웃 → 503** (401 로 바꾸지 않는다)
4. **도메인·서비스의 기존 확인은 분류해 남긴다.** 일괄 제거하지 않는다.
5. **ADR-0006 의 해당 항목만 대체한다.** 새 미들웨어(Redis 등)는 도입하지 않는다.

### 왜 필터가 아니라 인가 계층인가

JWT 는 *누가* 토큰을 냈는지를 증명하고(인증), 계정 상태는 *지금 행동해도 되는지*를
정한다(인가). 둘을 한 필터에 합치면:

- **DB 장애가 "토큰이 유효하지 않다" 로 나간다.** 현재 필터는 `ApiException` 을 삼키고
  컨텍스트를 비우므로(`JwtAuthenticationFilter:44`), 조회 실패가 이 경로를 타면 전 클라이언트
  재로그인 폭주를 부르고 장애가 모니터링에서 감춰진다.
- **공개·정적 경로에까지 조회가 번진다.** 필터에 `shouldNotFilter` 가 없어 토큰이 붙은
  모든 요청이 파싱된다(아래 참조).

`AuthorizationManager` 는 인증이 끝난 뒤에 돌고 경로별로 붙일 수 있어 두 문제를 자연히 피한다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 필터 안에서 직접 조회 | 동작은 한다. 그러나 인증·인가가 섞이고 DB 장애가 401 이 되기 쉬우며 공개 경로에 실수로 적용된다 |
| 서비스별 확인 + ArchUnit 강제 | 회귀 방지로는 유용. 그러나 "모든 변경 경로가 올바른 사용자를 확인했음" 을 증명할 수 없다. **이미 누락으로 뚫린 방식이다** |
| 액세스 토큰 TTL 단축 | 노출 창만 줄인다. 즉시 차단이 아니고 남은 수명 동안 오염은 그대로. 재발급 부하만 는다 |
| jti/사용자 블랙리스트 | 결국 요청마다 조회가 필요하고 수명주기·만료·배포 복잡도가 는다. Redis 는 ADR-0006 이 기각한 그 미들웨어이고, DB 블랙리스트는 현재 상태 조회보다 싸지 않다 |
| 토큰에 state 버전 클레임 | 클레임은 발급 시점에 고정되어 낡는다. 증분을 알려면 결국 매 요청 조회해야 한다 |
| `AuthenticationProvider` | 계정 상태는 신원이 확립된 *뒤* 의 인가다. DB 조회도 경합도 없애지 못하고 현재 구조와 덜 맞는다 |

**즉시 차단을 원하면 어떤 형태로든 서버 상태를 매 요청 확인해야 한다.**
더 싼 무상태 설계는 없다 — 이것이 ADR-0006 이 옳게 본 부분이다.

## 결과

### 얻는 것
- 새 엔드포인트가 생겨도 자동으로 보호된다. D-1 이 세 곳에서 동시에 터진 구조적 원인이 사라진다.
- 탈퇴 회원의 권한이 게스트 이하로 내려간다.
- 포인트 원장 오염 경로가 닫힌다.

### 잃는 것 / 감수하는 것
- **요청당 조회 1회가 는다.** 운영 규모에서의 총량 영향은 아직 측정되지 않았다.
- **`DELETE /auth/me` 재호출이 200 → 401 로 바뀐다.** 현재는 멱등하게 200 이다.
  외부에 보이는 계약 변경이므로 의식적으로 수용하거나 예외를 두어야 한다.
- **TOCTOU 경합은 남는다** (아래).

### 남는 한계 — 과장하지 않는다

**중앙 관문은 진입 장벽이지 트랜잭션 불변식이 아니다.**
`open-in-view: false` 이므로 인가 시점 조회는 서비스 트랜잭션 **밖**에서 끝난다.

```
1. 요청 A 의 인가 조회: ACTIVE
2. 요청 B 가 탈퇴를 커밋: INACTIVE
3. 요청 A 가 서비스에 진입해 그 사용자로 쓰기를 커밋
```

"조회 시점엔 ACTIVE" 는 보장해도 "커밋 시점에도 ACTIVE" 는 보장하지 못한다.
이 저장소는 같은 한계를 이미 `ActivePostGuard` 주석에 적어 두었다.
**"절대 안 된다" 가 요구사항이면 포인트 원장 같은 치명적 쓰기에는 조건부 쓰기·잠금 등
트랜잭션 수준 방어가 따로 필요하다.**

또한 중앙 관문은 **이 시큐리티 체인을 지나는 HTTP 요청만** 보호한다. 배치·내부 호출·
테스트·향후 두 번째 필터체인은 못 막는다. 그래서 기존 확인을 일괄 제거하지 않는다.

## 착수 전 결정해야 할 것

1. **비활성 계정을 401 로 볼 것인가 403 으로 볼 것인가.** 클라이언트가 재로그인 유도와
   접근 거부를 구분하는 방식에 달렸다.
2. **선택적 인증 공개 경로의 정책.** `permitAll` 은 필터를 우회하지 **않는다** — 실측:

   ```
   GET /posts/{id}/comments
     게스트(토큰 없음)  → comments[0].mine = false
     탈퇴자 토큰 첨부   → comments[0].mine = true
   ```

   탈퇴자가 공개 조회에서 여전히 "본인" 으로 식별된다. 거부할지 익명으로 강등할지 정해야 한다.
   R-20(탈퇴자의 글은 계속 보인다)은 **글의 가시성**을 말하는 것이지 탈퇴자가 개인화된 신원을
   유지해도 된다는 뜻이 아니다.
3. **`/auth/refresh` 는 예외다.** `permitAll` 이고 액세스 토큰 없이도 호출되므로
   중앙 관문이 대신할 수 없다. **자체 `isActive()` 확인(`AuthService:103`)을 유지한다.**
4. **`/auth/logout` 은 그대로 둔다.** 익명·탈퇴자도 부를 수 있어야 쿠키를 지울 수 있다.
   자격증명을 버리는 데 ACTIVE 를 요구할 이유가 없다.
5. **부하 판정 기준.** 같은 엔드포인트 A/B(조회 있음·없음), 단계적 지속 부하,
   Hikari active/pending·획득 시간, p99, DB 장애 시 5xx 확인.

## 참고

- 이 초안은 [E2E 검증 리포트](../verification/2026-09-04-auth-lifecycle-e2e.md) 의 D-1 과
  그 권고 절을 근거로 한다. 증거·재현 명령은 그쪽에 있다.
- 설계는 이종 모델(Codex) 적대적 리뷰를 1회 거쳤다. 위의 TOCTOU·503 분리·`permitAll` 경계
  지적이 그 결과다. **리뷰는 read-only 였고 코드 변경은 없었다.**
