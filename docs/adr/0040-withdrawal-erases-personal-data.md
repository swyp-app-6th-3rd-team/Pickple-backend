# ADR-0040 — 탈퇴는 모든 provider에서 개인정보를 즉시 파기한다

**상태**: Accepted

**관계**: [ADR-0037](0037-apple-withdrawal-detaches-provider-identity.md)을 **확장한다**.
0037의 §1·§3(Apple 탈퇴 시 identity 분리와 재로그인 신규 가입 계약)은 그대로 유효하고,
0037이 §4에서 "결정하지 않는다"고 명시적으로 미뤄 둔 두 항목 — 다른 provider의 탈퇴 동작과
과거 행의 개인정보 처리 — 을 이 문서가 결정한다.
0037 §2의 "도메인에서 `provider_id = NULL`이 유효한 조합은 오직 `APPLE AND INACTIVE`"
**한 문장만 부분 대체**하며, 같은 절의 DB 최소 보장과 유니크 제약 판단은 바꾸지 않는다.
Superseded가 아닌 이유는 0037의 어떤 결정도 뒤집지 않기 때문이다 — 0037이 비워 둔 자리를 채운다.

**근거 자료**: 개인정보처리방침 제1조·제3조·제9조(부칙 시행 2026-09-20), Issue #111, Issue #45 축 1·2·3

## 맥락

개인정보처리방침 제3조는 **"회원 탈퇴 시 지체 없이 파기"** 를 약속한다. 시행일은 2026-09-20이다.

현재 `User.withdraw()`는 두 가지만 한다.

```java
this.state = State.INACTIVE;
if (provider == SocialProvider.APPLE) {
    this.providerId = null;
}
```

그 결과 탈퇴한 회원의 행에 다음이 **무기한 남는다**.

| 컬럼 | 현재 | 성격 |
|---|---|---|
| `email` | 남는다 | 소셜 provider가 준 실제 이메일 |
| `name` | 남는다 | 소셜 provider가 준 실명 |
| `nickname` | 남는다 | 이용자가 지정한 표시명 |
| `profile_image_url` | 남는다 | 이용자가 올린 이미지 위치 |
| `provider_id` | APPLE만 비운다. **KAKAO는 남는다** | provider가 발급한 subject |

방침이 약속한 상태와 실제 저장 상태가 다르다. 이것은 성능이나 사용성 문제가 아니라
**공표한 처리방침과 시스템 동작의 불일치**다. 제9조가 "암호화하여 저장·관리" 대상으로
선언한 소셜 로그인 식별값이 Kakao 회원에게는 평문으로 남는 것도 같은 불일치다.

### 왜 지금까지 안 풀렸나

0037이 이 문제를 알고도 남긴 것은 범위 판단이었다. 0037은 Issue #103의 403 회귀
(Apple 재로그인 실패)만 좁게 고치기로 하고, §4에 "과거 행의 이메일·이름·닉네임·프로필 이미지
익명화 또는 삭제를 결정하지 않는다", "이 결정이 개인정보 삭제 정책을 충족한다고 간주하지 않고
Issue #45에서 별도로 결정한다"고 적었다.

즉 **0037은 이 결정의 자리를 예약해 뒀다.** 방침 시행일이 확정되면서 그 자리를 채울 시점이 됐다.

더 깊은 원인은 **도메인 모델에 파기 규칙이 아예 없었다**는 것이다. 규칙 표에는 R-20
("탈퇴해도 데이터를 지우지 않고 비활성으로 표시한다")만 있었다. 코드가 파기를 하지 않은 것이
아니라, 코드가 표현할 규칙 자체가 존재하지 않았다. 그래서 이 결정은 R-27·R-28을 함께 세운다.

### 두 provider가 다르게 동작하는 것은 도메인 사실이 아니다

`provider_id`를 비울 수 있는 조건이 `provider == APPLE`인 것은 **0037이 Apple만 검증했기
때문에 생긴 잠정 경계**이지 도메인이 요구한 것이 아니다. 조건의 본질은
**"로그인 조회 대상인가"** 이고 그것은 `state`가 정한다. provider 종류는 이 판정과 무관하다.

V12가 이미 그렇게 적혀 있다.

```sql
CHECK (state <> 'ACTIVE' OR provider_id IS NOT NULL)
```

DB는 처음부터 `state`만 본다. **도메인 가드만 DB보다 좁게 잠겨 있었고, 이번 변경은 둘을
일치시킨다.** 스키마 변경 없이 이 결정이 성립하는 이유가 여기에 있다.

### 표시 경로는 이미 마스킹을 전제로 쓰여 있다

`PostListRepository`의 작성자 표시는 다음과 같다(`CommentRepository`·`RankingListRepository`도 같은 형태다).

```sql
COALESCE(NULLIF(u.nickname, ''), NULLIF(u.name, ''), '알 수 없음') AS author_nickname
...
FROM (...) page
JOIN users u ON u.id = page.user_id
```

**`JOIN`은 INNER다.** 따라서 이 폴백은 **행이 존재하면서 컬럼이 비었을 때만** 발동한다.
개인정보를 비우면 작성자가 `'알 수 없음'`으로 비식별화되지만, 행 자체를 지우면 폴백이 아니라
**그 사람의 게시글·댓글이 목록에서 통째로 사라진다.**

이 폴백은 원래 "가입 직후 프로필 등록 전" 회원을 위해 쓰였지만, 형태가 그대로 파기 요구에
들어맞는다. #45 축 1(보존 + 익명화)이 조회 코드 변경 없이 성립하는 이유다.

## 결정

### 1. 탈퇴는 개인정보를 즉시 파기한다 (R-27)

`User.withdraw()`는 상태 전이와 함께 다음 필드를 **전부 `null`로** 만든다.

- `email`
- `name`
- `nickname`
- `profileImageUrl`
- `providerId`

파기는 **provider와 무관하다.** Apple·Kakao 및 앞으로 추가될 provider가 같은 동작을 한다.

파기 값은 sentinel 문자열이 아니라 `NULL`이다. `uk_users_provider (provider, provider_id)`가
살아 있어 상수 sentinel은 같은 provider의 두 번째 탈퇴에서 유니크 위반을 일으키고,
InnoDB는 유니크 키에서 `NULL`을 중복으로 세지 않는다. 표시 경로도 이미
`COALESCE(NULLIF(u.nickname,''), NULLIF(u.name,''), '알 수 없음')`이라 `NULL`을 전제한다.

### 2. 도메인 불변식을 provider가 아니라 state로 판정한다 (R-28)

`User`의 private 생성자 가드를 다음과 같이 넓힌다.

| | 이전 (0037 §2) | 이번 |
|---|---|---|
| `providerId = null`이 유효한 조합 | `provider == APPLE && state == INACTIVE` | `state == INACTIVE` |

`state == ACTIVE`인 회원이 `providerId` 없이 조립·복원되는 것은 여전히 막는다.
이로써 도메인 가드와 `ck_users_active_provider_id`의 조건이 **같은 문장**이 된다.

이 확장이 없으면 마스킹한 Kakao 행을 읽는 **모든 조회가 생성자 예외로 실패한다** —
`User.restore()`가 같은 생성자를 지나기 때문이다. 도메인이 스키마보다 좁게 잠겨 있을 때
나타나는 전형적인 실패 형태다(쓰기는 성공하고 읽기가 터진다).

### 3. 파기는 물리 삭제가 아니다 (R-20 유지)

`users` 행은 지우지 않는다. 게시글·댓글·투표·포인트 이력·뱃지가 이 행을 FK로 참조하고,
남긴 콘텐츠는 다른 사람의 맥락이기 때문이다(R-20). **지우는 것은 행이 아니라 컬럼 값이다.**

R-21의 닉네임 반납 장치(`active_nickname` 생성 컬럼 + 유니크 인덱스)도 **그대로 둔다.**
마스킹은 `User.withdraw()`를 지나는 경로에만 걸리지만 생성 컬럼은 모든 경로에 걸리고,
동시 가입의 유일성은 마스킹이 보장하지 못한다.

### 4. provider 연결 해제는 파기보다 먼저 끝난다

`AccountWithdrawalService.withdraw()`는 Kakao의 경우
`kakaoUnlinkGateway.unlink(user.providerId())`를 호출한 **뒤**
`persistenceService.complete(userId)`로 로컬 상태를 확정한다. 마스킹은 `complete()` 안의
`User.withdraw()`에서 일어나므로 unlink는 아직 값이 있는 `providerId`를 받는다.

**이 순서는 이제 우연이 아니라 계약이다.** 외부 연결 해제를 마스킹 뒤로 옮기면 `null`을
들고 호출하게 된다. 다만 조용히 실패하지는 않는다 — `KakaoUnlinkGateway.unlink`가
`providerId`의 null·blank를 검사해 503으로 거부하므로, 순서를 뒤집으면 탈퇴가 실패한다.
Apple 경로는 `userId`로 provider token을 조회하므로 이 제약을 받지 않는다.

### 5. 활성 상태 저장은 행이 아직 활성일 때만 쓴다

로그인은 회원을 읽고 활성인지 확인한 뒤 저장한다(`AuthService.loginOrRegister`).
그 사이에 탈퇴가 커밋되면 읽어둔 옛 값이 그대로 쓰여 **파기한 다섯 컬럼과 `ACTIVE` 상태가
되살아난다.** 확인과 쓰기 사이의 틈이라 응용 계층 검사로는 막지 못한다.

`JpaUserStore.save()` 는 활성 상태를 쓸 때 조건부 UPDATE 를 쓴다.

```sql
UPDATE users SET email = :email, name = :name, updated_at = :updatedAt
 WHERE id = :id AND state = 'ACTIVE'
```

0건이면 "활성 회원이 아니어서 쓰지 않았다" 는 사실이고, 저장이 성립하지 않았음을 올린다.
탈퇴(`INACTIVE` 쓰기)에는 조건을 걸지 않는다 — 그것이 이 전이의 목적이다.

**엔티티에 자바 가드를 두는 것으로는 부족하다.** 영속성 컨텍스트가 *읽은 시점*의 엔티티를
1차 캐시로 돌려주므로 엔티티의 `state` 를 봐도 여전히 옛 값이다. 쓰기 시점의 행을 아는 것은
DB 뿐이다. `updateProfile` 이 같은 이유로 이미 같은 조건을 걸고 있었다.

경합 자체는 이번 변경 이전부터 있었다. 다만 그때 되살아나는 것은 `state` 뿐이었고 관문
(ADR-0035)이 매 요청 다시 확인해 피해가 제한됐다. 파기를 도입한 뒤로는 **파기했다고 선언한
개인정보가 되돌아오므로** 등급이 다른 문제가 된다.

### 6. 범위를 명시한다

- **이 결정은 `users` 테이블의 개인정보만 다룬다.** 이용자가 게시글·댓글 본문에 스스로 적은
  개인정보는 파기 대상이 아니며, 그것까지 지운다고 주장하지 않는다.
  방침 제1조 3항이 "회사가 별도로 수집·요구하는 개인정보가 아니다"로 선을 그었다.
- refresh token과 Apple provider token은 종전대로 같은 트랜잭션에서 삭제한다(0037 §1).
- **재가입 제한·재가입 대기 기간은 이번에도 결정하지 않는다.** 아래 §결과 참조(#45 축 4).
- 토큰 폐기(#45 축 5)는 [ADR-0035](0035-withdrawn-user-central-authorization.md)가
  인가 계층에서 매 요청 `state`를 확인하는 방식으로 이미 해소했다.

## 결과

### 얻는 것

- 공표한 처리방침 제3조와 실제 저장 상태가 일치한다.
- Kakao 탈퇴자의 소셜 subject가 남지 않아, 같은 Kakao 계정의 다음 로그인이
  `(KAKAO, sub)`로 과거 비활성 행을 찾지 않고 **신규 가입 흐름**으로 들어간다.
  0037이 Apple에 준 계약이 전 provider로 같아진다.
- 작성자 표시는 별도 작업 없이 비식별화된다 — `nickname`·`name`이 `NULL`이 되면
  기존 `COALESCE`가 `'알 수 없음'`을 낸다. #45 축 1(보존 + 익명화)이 신규 코드 없이 성립한다.
- 랭킹 배치가 탈퇴자의 `ranking`을 `NULL`로 되돌리기 전까지 최대 5분간 목록에 남는
  기존 창(ADR-0028)에서도, 이제 노출되는 이름이 `'알 수 없음'`이라 개인정보가 새지 않는다.
- 도메인 가드와 DB CHECK가 같은 조건이 되어, 다음 provider가 추가돼도 탈퇴 동작에
  분기를 더할 필요가 없다.

### 잃는 것 / 감수하는 것

- **재가입 제한이 원리적으로 불가능해진다.** 소셜 subject를 해시조차 남기지 않으므로,
  같은 사람이 탈퇴·재가입을 반복해도 서버는 동일인임을 알 수 없다. 포인트·뱃지 초기화
  악용과 재가입 대기 기간 강제를 포기한다. 0037이 Apple에 대해 이미 수용한 것을
  전 provider로 확대한다.
- **이 비가역성은 소급되지 않는다.** 나중에 재가입 제한 정책이 생겨도 그 시점 이후
  탈퇴자에게만 적용할 수 있고, **이미 파기한 회원에 대해서는 영원히 불가능하다.**
  Issue #111이 이 점을 감수한 결정으로 명시했다.
- **탈퇴 회원이 누구였는지 서버가 답할 수 없다.** 분쟁·문의 대응에서 본인 확인이 불가능하다.
  이것은 파기의 목적 그 자체이지만 운영이 놀라지 않도록 기록한다. 탈퇴 시각 같은 비식별
  감사값이 필요하면 별도 컬럼·이력 테이블로 다룬다(SPEC의 `deleted_at` 예고 항목).
- **코드 변경만으로는 과거 탈퇴자에게 적용되지 않는다.** 이미 `INACTIVE`인 행의
  `email`·`name`·`nickname`·`profile_image_url`과 Apple 이외 provider의 `provider_id`는
  그대로 남는다. 방침 시행일 기준으로 준수하려면 V12가 Apple `provider_id`에 했던 것과 같은
  **백필 마이그레이션이 함께 필요하다.** 백필된 값은 DB만으로 복구할 수 없다(0037이 같은
  비가역성을 이미 수용했다).
- `provider_id` 컬럼의 기존 COMMENT `'... 탈퇴한 Apple 사용자는 NULL'`이 사실과 어긋나게 된다.
  같은 마이그레이션에서 함께 고친다.
- 탈퇴 후 `hasProfile()`이 `false`가 된다(`nickname == null` 판정). 탈퇴자는 로그인 조회에
  잡히지 않아 `profileCompleted` 계산 경로에 도달하지 않으므로 현재 노출 경로는 없다.
  탈퇴 행을 읽는 새 경로를 추가할 때 이 값을 "프로필 미등록"으로 오해하지 않아야 한다.
- 탈퇴 회원의 `/auth/me` 응답이 `email`·`name`을 `null`로 낸다. 현재는 인가 관문(ADR-0035)이
  비활성 신원을 먼저 막으므로 도달하지 않는다.
- 활성 상태 저장이 조건부 UPDATE 로 바뀌면서 로그인 동기화가 쓰는 컬럼이 `email`·`name` 으로
  좁혀졌다. `syncProfile` 이 원래 그 둘만 바꾸므로 동작은 같지만, 앞으로 로그인이 다른 컬럼을
  갱신해야 하면 이 문장을 함께 고쳐야 한다.
- **R-27에는 스키마 안전망이 없다.** `CHECK`는 상태 전이를 표현하지 못해(다른 행도 이전 값도
  볼 수 없다) 도메인이 유일한 방어선이다. `state`를 `INACTIVE`로 바꾸는 다른 경로가 생기면
  그 경로는 파기를 건너뛴다. 그래서 상태 전이와 파기를 `withdraw()` 한 메서드 안에 묶어
  분리 불가능하게 둔다 — R-28이 도메인·스키마 양쪽에서 지켜지는 것과 대비되는 지점이다.

## 검토한 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **sentinel 문자열로 치환** (`'withdrawn'`, `'deleted@…'`) | `uk_users_provider (provider, provider_id)`가 살아 있어 같은 provider의 **두 번째 탈퇴에서 유니크 위반**이 나고 탈퇴 요청 자체가 실패한다. `userId`를 섞어 유일하게 만들면 충돌은 피하지만 여전히 그 회원을 가리키는 값이라 파기가 아니다. `email`·`name`은 유니크가 없지만, 표시 경로의 `COALESCE(NULLIF(...))`가 `NULL`과 빈 문자열만 걸러내므로 sentinel은 화면에 그대로 노출된다 |
| **N일 유예 후 파기** (배치로 지연 삭제) | 방침 제3조는 "지체 없이"다. 유예에는 보유 근거 조항이 필요한데, 방침의 `부정이용 관련 기록 \| 탈퇴 후 [ ]개월` 항목이 **공란**이다. 공란은 "0개월"이 아니라 **보유 근거 미확정**이고, 근거 없는 보유가 곧 위반이다. 시행일(2026-09-20)까지 정책 공란을 채우는 결정을 기다릴 여유도 없다. 나중에 기간이 확정되면 `users` 행에 개인정보를 방치하는 방식이 아니라, 목적을 명시한 별도 보유 테이블에 필요한 필드만 남기는 것이 맞다 |
| **소셜 subject의 hash를 보존** (#45 축 2 B안) | 재가입 탐지가 가능해지지만, subject는 provider별 고정값이라 같은 계정이 돌아오면 해시가 일치한다 — **사실상 식별자를 계속 보유하는 것**이라 "파기"로 인정받기 어렵다. 게다가 그 값을 쓸 **재가입 제한 정책이 아직 없다**(0037 §4가 미결로 남겼다). 목적 없는 보유는 그 자체가 방침 위반 방향이다. 새 컬럼·마이그레이션·조회 경로가 붙어 이슈 범위가 재가입 정책 전체로 번지기도 한다. 재가입 제한이 정책으로 확정되면 그때 별도 ADR로 다룬다 |
| **불변식을 APPLE 한정으로 두고 KAKAO만 다른 곳에서 특수 처리** | 특수 처리 위치가 두 곳뿐인데 둘 다 나쁘다. **인프라**(`UserEntity.applyState`·`JpaUserStore`)에서 우회하면 저장 어댑터가 도메인 불변식을 무시하는 것이라 [ADR-0019](0019-policy-belongs-above-infrastructure.md)와 계층 책임 규율에 정면으로 어긋난다. **서비스**에서 마스킹하면 애그리거트 하나로 판정되는 규칙을 위로 올리는 것이라 다른 호출 경로가 지나칠 수 있다. 무엇보다 **불변식이 provider를 아는 것 자체가 잘못된 결합**이다 — 조건의 본질은 "로그인 조회 대상인가"이고 그것은 `state`가 정한다 |
| **`users` 행을 물리 삭제** (#45 축 1 C안) | 두 가지가 각각 독립적으로 막는다. ①정책: R-20의 콘텐츠 보존이 깨지고 방침 제3조도 게시물·댓글은 보존하되 작성자를 비식별 처리하라고 요구한다. ②기계적: `PostListRepository`·`CommentRepository`가 `JOIN users`(INNER)라서 행을 지우면 **그 회원이 쓴 게시글·댓글이 목록에서 통째로 사라진다.** 작성자 표시가 이미 `'알 수 없음'`으로 비식별화되므로 행을 지워서 더 얻는 것도 없다 |
| **계정 참조만 유지하고 표시만 가린다** (#45 축 1 B안) | 표시 계층에서 가려도 `users` 행에 원본이 남아 제3조의 "파기"를 충족하지 못한다. 새 조회 경로가 생길 때마다 가리는 것을 잊으면 그대로 샌다 — 방어선이 화면 개수만큼 늘어난다 |
| **행을 지우되 조인을 `LEFT JOIN`으로 바꾼다** | 물리 삭제를 살리려는 변형이지만, 작성자 컬럼을 읽는 모든 조회를 함께 고쳐야 하고 `COALESCE` 폴백이 "탈퇴자"와 "조인 실패"를 구분하지 못하게 된다. 마스킹은 같은 결과를 조회 코드 변경 **0줄**로 얻는다 |
| **`state`가 아니라 `provider_id IS NULL`로 탈퇴를 판정** | 한 사실을 두 컬럼이 표현하게 된다. V5가 `deleted_at`과 `state`의 이중 정본 문제를 겪고 `state` 하나로 통일한 선례가 있다. `state`가 회원 활성 여부의 정본이다 |
| **닉네임 반납 장치(`active_nickname`)를 마스킹으로 대체** | 마스킹은 `User.withdraw()`를 지나는 경로에만 걸리고, 동시 가입의 유일성을 보장하지 못한다. 백필하지 않은 과거 탈퇴 행에서는 생성 컬럼이 유일한 방어선이다. 두 장치를 함께 둔다 |

## 검증

- `UserTest`가 각 provider의 `withdraw()` 뒤 다섯 필드가 모두 `null`인지 고정한다.
- 같은 테스트가 `state == ACTIVE`이면서 `providerId == null`인 조립·복원이 여전히 거부되는지,
  `state == INACTIVE`이면 provider와 무관하게 허용되는지 확인한다.
- 통합테스트가 탈퇴 후 `users` 행을 **직접 조회**해 다섯 컬럼이 비었는지 본다.
  인메모리 객체의 게터가 `null`인 것은 영속화 증거가 아니다.
- Kakao 탈퇴 경로 테스트가 `unlink`가 **값이 있는** `providerId`로 호출된 뒤 마스킹이
  일어나는 순서를 고정한다.
- 두 명 이상 연속 탈퇴에서 `uk_users_provider` 위반이 없는지 확인한다.
- **탈퇴와 겹친 로그인이 파기를 되돌리지 못하는지** 인터리빙을 고정한 테스트로 확인한다.
  로그인 조회 → 탈퇴 커밋 → 로그인 저장 순서를 실제로 만들고, 저장이 거부되며 행이
  `INACTIVE` + 다섯 컬럼 `NULL` 로 남는지 본다. 가드를 꺼서 이 테스트가 **실패하는 것**까지
  확인했다 — 통과만으로는 보호의 증거가 아니다.
- 소급 파기 테스트는 SQL 사본이 아니라 **실제 V14 파일을 읽어** 실행한다. 사본을 검증하면
  마이그레이션에서 `WHERE` 가 빠져도 통과한다. `WHERE` 를 지워 테스트가 실패하는 것을 확인했다.
- **목록 조회 통합 테스트가 탈퇴한 작성자의 게시글이 여전히 목록에 나오고 작성자만
  `'알 수 없음'`인지 확인한다.** 행 보존과 비식별화가 동시에 성립하는지가 이 결정의 핵심이다.
- 백필 마이그레이션 적용 후 `INACTIVE` 행에 위 다섯 컬럼의 비-`NULL` 값이 0건인지
  카운트로 확인한다. 빌드 green은 근거가 아니다.
