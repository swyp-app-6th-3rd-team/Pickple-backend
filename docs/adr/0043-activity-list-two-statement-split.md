# ADR-0043 — 내 활동 목록은 키 확정과 행 조립 두 문장으로 읽는다

**상태**: Accepted

**관련**: [ADR-0036](0036-my-activity-list-reads-posts-through-activity-index.md)이 내 활동 목록의 읽기 경로
(활동 테이블에서 시작 · 커서는 활동 시각과 게시글 id)를 정했다. 이 문서는 그 경로를 **네이티브 SQL 한 문장에서
QueryDSL 두 문장으로** 옮기면서 바뀌는 성능 계약을 정한다. [ADR-0041](0041-read-only-mapping-for-derived-columns.md)이
`popularity_score` 의 읽기 전용 매핑으로 선행 조건을 풀었다.

## 맥락

`ActivityListRepository` 는 조회 저장소 중 가장 크고(271줄) 가장 위험했다. [#130](https://github.com/swyp-app-6th-3rd-team/Pickple-backend/issues/130)이
지적한 `Object[]` + 컬럼 인덱스 상수 11개에 더해, **SQL 본문을 문자열로 조립**했다.

```java
case VOTE -> columns.formatted("v.created_at") + " FROM vote v JOIN post p ...";
```

"enum 만 들어오므로 SQL 주입 경로가 없다" 는 주석의 방어는 **호출자 규약에 의존**한다 — `String` 을 받는
오버로드가 하나 생기면 뚫린다. 이것을 없애려면 세 갈래를 문자열이 아니라 **질의 객체**로 조립해야 하고,
그러려면 QueryDSL 이어야 한다.

그런데 옛 SQL 의 뼈대가 **파생 테이블**이다.

```sql
SELECT …, (대표 사진 서브쿼리) FROM ( SELECT … FROM vote v JOIN post p … ORDER BY … LIMIT ? ) page ORDER BY …
```

안쪽이 활동 인덱스로 조각을 확정하고 바깥이 그 몇 줄에만 대표 사진을 붙인다. 그 순서를 지켜야
대표 사진 서브쿼리가 조각 크기만큼만 돌고, 정렬이 남는 경로(인기순·내 글)에서 내 활동 전체에 대해
돌지 않는다. **QueryDSL-JPA 는 FROM 절 서브쿼리를 지원하지 않는다.** 이것이 이 저장소를 네이티브에
묶어 두던 마지막 매듭이다.

## 결정

**한 문장을 두 문장으로 나눈다.** 옛 파생 테이블의 안쪽이 키 문장, 바깥이 행 문장이 된다.

| 문장 | 하는 일 | 시작점 | 읽는 행 |
|---|---|---|---|
| ① 키 | `ORDER BY … LIMIT size+1` 로 조각에 들어갈 게시글 id 를 확정한다 | **활동 테이블** (`idx_*_user_activity`) | Θ(조각 크기) — 최신·오래된순 |
| ② 행 | 그 id 들에만 게시글 본문·활동 시각·대표 사진을 붙인다 | **게시글** (`PRIMARY` 범위 + `uk_*_post_user` 단건 조회) | Θ(조각 크기) |

세 유형의 분기는 `switch` 가 `JPAQuery` 를 다르게 조립한다. keyset 은 HQL 튜플 비교
`(정렬키, id) < (?, ?)` 로 쓰고, MySQL 에 옛 SQL 과 같은 행 값 비교로 내려간다.

### 왕복이 하나 늘어난다. 그것이 받아들인 대가다

판정 기준은 **왕복 횟수가 아니라 실행계획**이다. 옛 한 문장에서 인덱스 이득이 있던 구간은 안쪽 질의뿐이고,
그 구간이 키 문장에 그대로 남는다. 바깥 질의가 하던 일(조각 크기만큼 조인)은 행 문장이 같은 크기로 한다.
`ActivityControllerIT.statementCountDoesNotGrowWithSliceSize` 가 지키는 성질 — 문장 수가 **행 수에
비례하지 않는다** — 는 그대로다. 요청당 상수가 2 에서 3 이 됐을 뿐이다.

### ②는 게시글에서 시작한다 — ①과 반대다

①은 활동 테이블에서 시작해야 한다(ADR-0036). ②까지 같은 모양으로 쓰면 옵티마이저가 통계에 따라
`idx_vote_user_activity(user_id)` 로 **내 활동 전체를 훑고 `IN` 으로 거를** 수 있다. 게시글에서 시작하면
`post.id IN (…)` 이 기본 키 범위로 조각 크기만큼만 읽고, 활동 행은 `(post_id, user_id)` 유니크 키로
한 줄씩 붙는다(`eq_ref`). `FROM` 이 조인 순서를 강제하지는 않는다 — 기본 키 범위가 가장 싼 진입점이라는
근거를 옵티마이저에 줄 뿐이다. 그래서 실행계획 테스트가 인덱스 **이름**이 아니라 **접근 방식**(기본 키 범위 +
유니크 키 단건 조회)을 고정한다. 이름만 보면 유니크 키 전량 스캔과 구분되지 않는다.

### 두 문장은 한 스냅샷을 본다 — 새로 생긴 전제

한 문장일 때는 없던 조건이다. 두 문장 사이에 게시글이 지워지거나 인기 점수가 바뀌면 ②가 ①과 다른
세상을 본다. InnoDB REPEATABLE READ 에서 트랜잭션의 첫 읽기가 스냅샷을 잡으므로, **호출자가 트랜잭션을
열면** 두 문장은 같은 행을 본다. `JpaActivityQueryStore` 가 `@Transactional(readOnly = true,
isolation = REPEATABLE_READ)` 로 열고, 저장소는 진입 시점에 `isActualTransactionActive()` 를 단언한다 —
누가 애노테이션을 지우면 조용히 어긋나는 대신 즉시 깨진다. 격리 수준 명시는 MySQL 기본값과 같아 실제로
바뀌는 것이 없지만, 낮추는 변경이 이 파일을 지나가게 한다. 한계는 있다 — 바깥 트랜잭션에 참여하면 그쪽
격리 수준을 따르고 Spring 은 그것을 검증하지 않는다. 지금 호출자는 서비스의 `readOnly` 트랜잭션뿐이다.

`hasNext` 는 ①의 행 수(`size + 1` 넘침)로 정하고 ②에는 `size` 건만 넘긴다. ②의 행 수로 정하면 위 전제가
깨졌을 때 "다음이 있다" 가 조용히 사라지고, 넘치는 한 건에 대표 사진 서브쿼리를 헛되이 돈다.

### 실측 — 활동 5,000건 · 게시글 20,000 · MySQL 8.4 · `EXPLAIN ANALYZE`

같은 시드에서 옛 네이티브 한 문장과 새 두 문장을 나란히 쟀다. 커서는 활동의 한가운데(2,500번째)를 가리킨다.

| 경로 | 전 (한 문장) | 후 ① 키 | 후 ② 행 | 계획 |
|---|---|---|---|---|
| 투표 최신순 첫 조각 | 0.031 ms | 0.020 ms | ≈0.04 ms | `Covering index lookup … idx_vote_user_activity` **11행**. 전후 동일 |
| 투표 최신순 둘째 조각 | 0.258 ms | 0.233 ms | 0.037 ms | 행 값 비교가 `Filter` 로, 커서 앞 2,512행을 인덱스에서 읽는다. **전후 동일** |
| 댓글 최신순 둘째 조각 | 0.218 ms | 0.227 ms | 0.035 ms | `idx_commenter_user_activity`. 전후 동일 |
| 투표 인기순 둘째 조각 | 3.45 ms | 3.87 ms | 0.046 ms | `Sort` + 5,000행. ADR-0036 이 받아들인 Θ(내 활동 수). 전후 동일 |

**계획이 바뀐 곳이 없다.** `Sort:` 가 새로 나타난 경로도, 인덱스를 잃은 경로도 없다. ②는 네 경우 모두
`Index range scan on PRIMARY (10 ids)` → `Single-row index lookup using uk_*_post_user` 이고 대표 사진
서브쿼리는 정확히 10번 돈다.

부수 관찰 — 행 값 비교는 옛 SQL 에서도 인덱스 **범위**가 아니라 인덱스 위의 `Filter` 였다. 둘째 조각부터는
커서 앞의 인덱스 항목을 지나쳐 읽는다(Θ(커서 위치)). 이 결정이 만든 성질이 아니고 이 결정으로 바뀌지도
않았으므로 여기서 다루지 않는다.

### 회귀 방지

`ActivityControllerIT.QueryPlan` 이 **Hibernate 가 실제로 내보낸 SQL** 을 `StatementInspector` 로 붙잡아
같은 값으로 바인딩해 `EXPLAIN FORMAT=TREE` 한다. 손으로 베낀 SQL 을 EXPLAIN 하면 저장소가 바뀌어도
테스트가 초록색으로 남는다 — QueryDSL 전환 뒤로 SQL 은 사람이 쓰지 않으므로 특히 그렇다.
정렬 튜플의 두 번째 자리를 `p.id` 로 바꿔 위반을 주입했을 때 `voteLatestSliceUsesActivityIndex` 와
`voteOldestSliceReadsTheSameIndexForward` 가 `Sort:` 를 보고 실패하는 것을 확인했다.

## 결과

- 저장소가 271줄 네이티브 SQL 문자열 조립에서 QueryDSL 프로젝션이 된다. `Object[]` 0건, 컬럼 인덱스 상수
  0개, `.formatted(` 0건. 잘못된 별칭·밀린 인덱스가 런타임에야 드러나던 구조가 사라진다.
- 요청당 SQL 이 2 → 3 (키 · 행 · 탈퇴 차단 관문). 행 수에 비례하는 문장은 여전히 없다.
- 호출자가 트랜잭션을 열어야 한다는 전제가 생겼다. 저장소가 단언한다.
- `summarize` 도 QueryDSL 이다 — `FROM` 없는 문장이 JPQL 에 없어 회원 행 하나에 스칼라 서브쿼리 셋을 얹는다.
  회원 기본 키 조회는 `const` 라 비용이 없다.

### 포기한 것

**왕복 하나.** 같은 커넥션에서 연달아 나가는 두 문장이라 네트워크 왕복 하나가 순증분이다. 로컬 실측에서
② 는 0.03~0.05 ms 다. 화면 한 조각을 그리는 비용에서 보이지 않는 크기다.

**"한 문장" 이라는 단순함.** 옛 코드는 SQL 하나를 읽으면 전체가 보였다. 이제 두 문장의 관계(같은 `FROM`
방향이 아니라는 것, 같은 스냅샷을 봐야 한다는 것)를 알아야 한다. javadoc 이 그 관계를 적는다.

## 검토한 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **네이티브 유지 + `Object[]` 만 프로젝션으로 교체** (승인된 후퇴안) | 이 이슈의 최대 이득인 SQL 문자열 조립이 그대로 남는다. 실행계획 회귀가 나왔을 때만 쓰기로 한 안이고, 실측에서 회귀가 없었다 |
| **JPQL 한 문장** — 대표 사진 서브쿼리를 정렬·LIMIT 과 같은 문장에 | 인기순·내 글처럼 `Sort` 가 남는 경로에서 서브쿼리가 잘리기 전의 행 전체에 대해 돌 위험이 있다. 파생 테이블이 막던 바로 그 함정이다 |
| **Blaze-Persistence** 로 FROM 절 서브쿼리 표현 | 저장소 하나를 위해 의존성 하나를 들인다. `tech-adoption-gate` 의 "측정이 이 해법을 가리키는가" 에 답할 측정이 없다 — 두 문장이 이미 같은 계획을 낸다 |
| **②를 ①과 같은 방향(활동 테이블에서 시작)으로** | 옵티마이저가 `idx_*_user_activity` 를 골라 내 활동 전체를 훑을 수 있다. 통계 의존이라 테스트 시드에서는 보이지 않다가 운영에서 나타난다 |
| **②의 정렬을 Java 에서** (①의 id 순서로 재배열) | 스냅샷 전제를 없앨 수 있지만, 정렬 하나를 두 곳(SQL 과 Java)에 두게 된다. 전제를 없애는 대신 **단언**하는 쪽을 골랐다 — 전제가 깨지면 조용히 어긋나지 않고 즉시 깨진다 |
| **`ActivityPostView` 에 `popularityScore` 추가** (인기순 커서용) | 화면 계약인 도메인 뷰에 응답에 없는 값이 들어간다. 저장소 안의 `ActivityRow(view, popularityScore)` 로 감싸 패키지를 벗어나지 않게 했다 |
| **keyset 을 `a < ? OR (a = ? AND b < ?)` 로 풀어쓰기** | HQL 이 튜플 비교를 지원하므로 필요가 없다. 풀어쓰면 MySQL 이 인덱스 범위를 접지 못한다는 것이 `PostListRepository` 가 피한 형태다. 실행계획 테스트가 행 값 비교 형태를 정규식으로 고정한다 |
