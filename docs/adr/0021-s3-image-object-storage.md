# ADR-0021 — 이미지 객체는 S3에 저장한다

**상태**: Accepted

## 맥락

상품과 댓글의 이미지 메타데이터를 담는 `item_container`·`item_resource` 스키마는 이미 있다.
`item_resource`는 파일 크기, 원본 파일명, 객체 키와 접근 URL을 저장하지만,
이미지 바이너리를 어디에 두고 어떻게 검증할지는 정해지지 않았다.

develop 환경은 단일 EC2를 사용한다(ADR-0012). 이 인스턴스의 로컬 디스크에 이미지를 두면
인스턴스 교체와 애플리케이션 재배포가 파일 수명에 영향을 준다. DB에 바이너리를 넣으면
백업·복구와 쿼리 부하가 이미지 트래픽에 묶인다. 이미지 객체의 수명은 애플리케이션 프로세스와
관계형 데이터베이스에서 분리할 필요가 있다.

또한 객체 저장소와 MySQL은 하나의 트랜잭션에 참여하지 않는다. 객체 업로드 뒤 DB 저장이
실패하거나 여러 파일 중 일부만 업로드되면 S3에 고아 객체가 남을 수 있다. 실제 AWS를 호출하는
테스트는 느리고 자격증명·네트워크에 의존하므로, 같은 S3 API를 로컬에서 실제로 호출해 검증할
경계도 필요하다.

## 결정

### 업로드 API와 저장 위치

인증된 사용자만 `POST /api/images`를 호출할 수 있다. API는 JPEG와 PNG만 받으며,
파일 하나의 최대 크기는 5 MB다. 서버는 AWS SDK for Java v2로 S3에 객체를 업로드한다.

DB에는 바이너리를 넣지 않는다. 기존 구조를 그대로 사용한다.

- `item_container`: 업로더와 부착 용도, 리소스 묶음을 나타낸다
- `item_resource`: 파일 크기, 원본 파일명, S3 Object Key, 접근 URL을 저장한다

S3 버킷은 이미지 객체 전용이어야 한다. **Terraform 원격 상태를 저장하는 state 버킷을
이미지 버킷으로 재사용하지 않는다.** 상태 버킷은 접근 권한·수명 주기·감사 목적이 애플리케이션
파일과 다르며, 두 데이터를 섞으면 애플리케이션 권한이 인프라 상태까지 닿는다.

### AWS 의존성 격리

서비스는 AWS SDK 타입을 직접 사용하지 않는다. 객체 업로드와 삭제를 나타내는
AWS 비의존 포트를 두고, 인프라 어댑터만 AWS SDK v2와 S3의 bucket·key·region을 안다.
포트의 입력과 결과는 파일 내용, 크기, 콘텐츠 유형, 객체 키처럼 애플리케이션 용어로 표현한다.

이 경계 덕분에 서비스 정책과 DB 저장 흐름은 S3 구현 세부사항에 묶이지 않는다.
다만 운영 저장소는 S3로 고정하며, 포트는 여러 저장소를 동시에 지원하려는 플러그인 체계가 아니라
AWS SDK가 서비스 계층으로 새는 것을 막는 경계다.

### 접근 URL

객체의 안정적인 식별자는 `item_key`다. 접근 URL은 다음 우선순위로 만든다.

1. 공개 base URL이 설정되어 있으면 `{public-base}/{item-key}`를 사용한다.
   이후 CloudFront나 별도 공개 도메인을 붙여도 DB/API 계약을 유지할 수 있다.
2. 공개 base URL이 없으면 bucket·region·item key로 구성한 정규 S3 URL을 사용한다.

URL 생성은 LocalStack endpoint를 외부 접근 URL로 저장하지 않는다. 접근 URL이 만들어졌다는 사실은
운영 객체가 공개 읽기 가능하다는 뜻이 아니다. 실제 공개 정책 또는 CDN 연결은 배포 인프라가
별도로 제공해야 한다.

### 부분 실패 보상

S3와 DB 사이에 분산 트랜잭션을 도입하지 않는다. 한 요청에서 업로드에 성공한 object key를
추적하고, 뒤 파일 업로드 또는 `item_container`·`item_resource` 저장이 실패하면 이번 요청에서
만든 S3 객체를 보상 삭제한다. DB 트랜잭션은 롤백하고 객체 삭제는 best effort로 수행한다.

보상 삭제 자체가 실패하거나 프로세스가 중단되면 고아 객체가 남을 수 있다. 이 잔여 위험은
실패 로그와 object key를 통해 운영에서 추적하고, 필요하면 별도 정리 작업으로 회수한다.
이번 결정은 정상적인 예외 경로의 고아 생성을 줄이는 것이며 S3와 MySQL의 원자성을 보장하지 않는다.

### 통합 테스트

테스트에서 실제 AWS 계정이나 자격증명을 사용하지 않는다. `IntegrationTest`와
`ContainerConfig`의 기존 Testcontainers 구성을 따라 Docker에서 LocalStack S3를 띄우고
테스트 버킷을 만든다.

`ImageUploadIT` 같은 통합 테스트는 mock 저장소 호출로 끝내지 않고 다음 수직 경로를 검증한다.

1. 인증을 포함한 실제 `POST /api/images` 요청
2. AWS SDK v2를 통한 LocalStack S3 업로드
3. LocalStack에서 object key로 객체를 다시 조회해 내용과 메타데이터 확인
4. MySQL의 `item_container`·`item_resource` 저장 확인

이 테스트는 S3 프로토콜과 애플리케이션 배선을 검증하지만, 실제 AWS의 IAM 정책·버킷 정책·리전·
CloudFront 설정까지 검증하지는 않는다.

### 배포 경계

**실제 S3 버킷, 애플리케이션 IAM 권한, 버킷 정책, 수명 주기와 CDN/공개 도메인 프로비저닝은
이 API PR의 범위 밖이다. 그러나 배포 전에 반드시 준비하고 실제 환경에서 검증해야 한다.**

애플리케이션 역할에는 이미지 버킷의 필요한 object prefix에 대한 최소한의 업로드·조회·삭제 권한만
부여한다. Terraform state 버킷 권한을 애플리케이션 역할에 부여해서는 안 된다.

## 결과

- 이미지 바이너리 수명이 EC2 교체와 MySQL 백업·복구에서 분리된다
- AWS SDK 의존성이 인프라 어댑터에 머물러 서비스와 테스트 계약이 AWS 타입에 오염되지 않는다
- LocalStack 통합 테스트로 자격증명 없이 실제 S3 요청과 DB 저장까지 검증할 수 있다
- 공개 base URL을 두어 S3 직접 URL에서 CDN/도메인으로 전환할 때 API 계약 변경을 줄인다
- 객체 저장과 DB 저장에 원자적 트랜잭션은 없다. 보상 삭제로 일반 실패를 처리하지만
  프로세스 중단이나 삭제 실패 시 고아 객체 가능성은 남는다
- 서버가 파일 본문을 받아 S3로 전달하므로 네트워크 대역폭과 메모리/스트리밍 관리 부담이 생긴다.
  5 MB 제한과 허용 형식 제한으로 MVP에서 이 비용을 통제한다
- LocalStack 성공은 운영 권한과 공개 URL의 성공을 증명하지 않는다. 배포 전 AWS 인프라 검증이
  별도로 필요하다

## 검토한 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| EC2 로컬 디스크 | 인스턴스 교체·재배포와 파일 수명이 결합되고 수평 확장 시 파일이 노드마다 갈린다. 별도 EBS를 붙여도 애플리케이션이 파일 서버 운영과 백업을 맡게 된다 |
| MySQL BLOB | 이미지 트래픽이 DB I/O와 백업 크기를 키우고, 관계형 데이터 복구와 대용량 바이너리 복구가 결합된다. 기존 `item_resource`의 object key 모델과도 맞지 않는다 |
| 자체 운영 MinIO | S3 호환 API는 얻지만 단일 EC2에서 저장소 프로세스·볼륨·백업·장애 복구를 직접 운영해야 한다. 6주 MVP에서 S3 비용보다 운영 복잡도가 크다 |
| 클라이언트 presigned 직접 업로드 | 서버 대역폭을 줄이고 대용량 업로드에 유리하다. 그러나 미부착 업로드 회수, 업로드 완료 확인, 키 발급 권한과 클라이언트 상태 머신이 추가된다. 파일당 5 MB인 이번 MVP는 서버 경유 API가 더 단순하다. 트래픽이나 파일 크기가 커지면 다시 검토한다 |
