# ADR-0049 — 내 활동 목록은 유형별 경로와 응답 타입으로 갈리고, 커서는 유형을 싣는다

**상태**: Accepted

**관련**: [ADR-0004](0004-spring-data-paging-types.md) 가 커서 타입을,
[ADR-0034](0034-security-requirement-on-authenticated-endpoints.md) 가 인증 표시를,
[ADR-0043](0043-activity-list-two-statement-split.md) 가 키·행 두 문장 분할을 정했다.
세 문서는 그대로 선다.

**부분 대체**: [ADR-0036](0036-my-activity-list-reads-posts-through-activity-index.md) ·
[ADR-0046](0046-post-detail-single-type-with-nested-vote-section.md).
두 문서의 **응답 타입에 관한 항목만** 대체하며, 원본 본문은 고치지 않는다 —
ADR 은 불변이고 결정이 바뀌면 새 번호로 대체한다(`docs/adr/README.md`).
대체 범위는 아래 "무엇을 대체하는가" 에 적는다.

## 맥락

`GET /users/me/activities?type=VOTE|COMMENT|POST` 는 유형을 쿼리 파라미터로 받아
세 활동을 한 응답 타입(`ActivityController.ActivityItem`)으로 돌려준다.
기능명세서 v0.4 §9.1·§9.2 를 다시 읽으면서 그 전제가 깨졌다.

### 명세가 유형마다 다른 것을 요구한다

§9.2 는 유형별 **추가 데이터**를 적었다.

| 유형 | 명세가 추가로 요구하는 것 |
|---|---|
| 투표 활동 | 각 항목의 투표율(%), 내가 선택한 항목 |
| 댓글 활동 | 내가 남긴 댓글(1줄 넘으면 줄임표), 받은 원픽 갯수 |
| 게시글 활동 | 없음 |

세 유형이 한 응답 타입을 공유하면 **유형에 따라 `null` 이 되는 필드가 늘어난다.**
투표 활동에만 있는 두 필드와 댓글 활동에만 있는 두 필드가 한 스키마에 얹히면,
어느 필드가 언제 채워지는지를 타입이 말해주지 못하고 클라이언트가 유형을 보고
직접 판단해야 한다. 계약이 흐려지는 자리다.

### 그런데 유형은 이미 화면이 알고 있다

§9.1 은 "마이페이지 메인화면에서 어떤 유형을 탭해서 들어왔는지에 따라 기본 칩이 변경"
이라 적었다 — **칩은 항상 하나가 활성이고 "전체" 가 없다.** 목록 요청은 언제나
유형 하나를 들고 온다. 유형이 요청마다 고정이라면 그것은 경로가 표현할 수 있는 값이다.

### 커서에 유형이 없다

지금 커서는 `(정렬키, post.id)` 두 값뿐이다. 경로가 하나일 때는 유형이 늘 같은
요청에서 왔으므로 문제가 되지 않았다. 세 경로로 갈리면 `/votes` 에서 받은 커서를
`/posts` 에 넣는 호출이 **도달 가능**해진다.

**기존 정렬 축 가드로는 막지 못한다.** `ActivityListCursor.from` 은 커서의 **키 이름**으로
판별하는데, 세 유형이 쓰는 키 이름이 서로 같다(`activityAt` 또는 `popularityScore`, 그리고 `id`).
게다가 최신순과 오래된순은 `activityAt` 키를 **일부러 공유한다**(`timeSortsShareTheSameCursor` 가
그 성질을 고정한다). 즉 키 이름 매칭으로는 정렬 방향도 유형도 가릴 수 없다.
다른 유형에서 만든 커서는 **구조상 유효해 보여 그대로 통과**한다.

## 결정

### 1. 유형을 경로로 올린다

```
GET /users/me/activities/votes?sort=&cursor=&size=
GET /users/me/activities/comments?sort=&cursor=&size=
GET /users/me/activities/posts?sort=&cursor=&size=
```

`sort`·`cursor`·`size` 규약은 그대로다. `/users/me/activities/summary` 와
`/users/me/posts/recent` 는 손대지 않는다.

### 2. 응답 타입을 유형별 셋으로 나눈다

`VoteActivityItem` · `CommentActivityItem` · `PostActivityItem`.

**이 이슈에서는 필드 구성이 셋 다 현 `ActivityItem` 과 같다 — 골격만 세운다.**
투표 카드의 선택·득표율(#157)과 댓글 카드의 내 댓글·원픽 수(#158)가 뒤이어 붙으며,
그때 세 타입이 실제로 갈린다. 지금 같다는 것이 합칠 근거가 되지 않는 이유는
**갈릴 것이 이미 명세에 적혀 있기 때문**이다. 한 타입으로 두었다가 후속 이슈에서
쪼개면 그 시점에 클라이언트 파싱이 한 번 더 깨진다.

### 3. 커서에 유형 판별자를 싣고, 경로와 다르면 400 이다

커서 맵에 `type` 키를 더해 활동 유형을 **이름으로** 싣는다.
SQL 조건에는 쓰지 않는다 — 오직 경로 교차를 판별한다.

```
{"type":"VOTE","activityAt":"2026-09-03T16:13:10","id":42}
```

경로가 고정한 유형과 다르면 `INVALID_REQUEST`(400) 로 돌려준다.
기존 정렬 불일치와 **같은 방식·같은 계열 메시지**다.

**조용히 첫 조각을 주지 않는다.** 그 이유는 정렬 가드가 이미 적어 둔 것과 같다 —
조용히 처음으로 돌아가면 클라이언트는 **무한 스크롤이 되감기는 것**을 본다.
틀린 데이터를 주는 것보다 낫지만, 사용자에게는 목록이 고장 난 것으로 보인다.

**유형이 없는 커서도 거절한다.** 판별자가 생기기 전에 발급한 커서이거나 키를 지워
보낸 요청인데, 없는 것을 통과시키면 `/votes` 커서에서 `type` 만 떼어 `/posts` 에
넣는 경로가 그대로 열려 막으려던 구멍이 되살아난다.

**구 경로(`?type=`)가 발급한 커서도 함께 무효가 된다.** 판별자를 구 경로에만 빼는
예외를 두지 않았다 — 예외를 두면 "판별자 없는 커서" 가 유효한 상태로 남아 위 구멍이
그대로 열린다. 커서는 한 세션의 스크롤 안에서만 쓰이는 값이라 무효화 비용이 짧고,
클라이언트는 400 을 받고 첫 조각부터 다시 읽는다.

### 4. 구 경로는 지우지 않고 deprecated 로 표시한다

`GET /users/me/activities?type=` 는 동작을 그대로 두고 OpenAPI 에만 `deprecated: true`
로 표시한다. SPEC 에 공개된 계약이고 FE 가 OpenAPI 로 계약을 가져가는 구조라
**미사용을 증명할 수 없다.** 소비 클라이언트 전환을 확인한 뒤 별도 이슈로 제거한다.

### 5. 유형 fold 는 구 경로에만 남는다

`ActivityType.from(String)` 의 "모르는 값은 VOTE 로 접는다" 는 쿼리 파라미터 전용
방어였다. 경로가 유형을 고정하면서 **세 새 경로에는 접을 값 자체가 없다** —
`ActivityQueryService.findSlice` 는 `String` 대신 `ActivityType` 을 받는다.
`ActivitySort.from` 은 그대로 남으므로 SPEC §5.2 의 "모르는 값은 400 이 아니다" 계약이
**절반만 참**이 된다(정렬은 접고, 유형은 접을 자리가 없다). SPEC §3.10 에 다시 서술했다.

`ActivityType` enum 자체는 남는다 — 저장소의 `switch` 키이고, 값이 셋뿐이라는 성질을
`hasExactlyThreeChips` 가 계속 지킨다.

## 무엇을 대체하는가

### ADR-0036 — "세 유형의 결과 모양이 같다"

0036 은 §9.2 의 조회 데이터가 세 유형 모두 같다("게시글 유형 / 상품명 / 설명 /
댓글 수 / 투표 수 / 작성 시간 / 상품 사진")는 사실을 근거로 **단일 목록**을 택했다.
v0.4 가 유형별 추가 데이터를 요구하면서 **그 전제가 깨졌다.**

**0036 의 나머지는 그대로 선다.** 대체되는 것은 "결과 모양이 같으므로 한 목록" 이라는
응답 형태 판단뿐이다. 읽기 경로의 핵심 — 활동 테이블에서 시작할 것, 정렬 튜플의 두 번째
자리를 활동 테이블 쪽 `post_id` 로 읽을 것, `COMMENT` 를 `post_commenter` 로 읽을 것,
`POST` 최신순과 인기순의 정렬 잔존을 받아들일 것 — 은 이 결정이 건드리지 않는다.
**항목 단위가 여전히 게시글이고 게시글당 한 행**이므로 키·행 2문장 분할(ADR-0043)도
그대로 유효하다.

0036 이 "커서에 판별자를 더해야 한다" 를 UNION 안을 **기각하는 근거**로 들었던 것은
짚어둘 만하다. 그 문장은 활동 행을 항목으로 삼았을 때 **테이블마다 독립된 `id` 시퀀스**
때문에 판별자가 필요하다는 뜻이었다. 여기서 더하는 판별자는 다른 이유에서 온다 —
항목은 여전히 게시글이고 `id` 는 하나의 시퀀스이며, 판별자는 **경로 교차를 막기 위한 것**이다.
SQL 조건에 쓰이지 않으므로 0036 이 피하려던 비용(인덱스가 서지 않는 UNION)은 생기지 않는다.

### ADR-0046 — "쪼개지 않을 목록" 에 올라 있던 `ActivityItem`

0046 은 게시글 상세를 단일 응답 타입으로 정하면서, 쪼개지 **않을** 선례 표에
`ActivityController.ActivityItem` 을 올리고 근거를 이렇게 적었다 —
*"쪼개면 파싱 분기가 생기는데 목록은 칩 하나로 한 유형만 담으므로 그 분기가 쓰이지도 않는다."*

**경로가 유형을 고정하면서 이 근거가 그대로 분리의 근거로 뒤집힌다.**
칩 하나로 한 유형만 담기 때문에 **유형을 경로로 올릴 수 있고**, 경로가 유형을 정하면
클라이언트는 어느 타입을 파싱할지 요청 시점에 이미 안다 — 분기가 필요 없는 이유가
분리를 **싸게** 만든다. 0046 이 "분기가 쓰이지 않는다" 를 합치는 근거로 읽은 자리에서,
같은 사실이 "분기 없이 나눌 수 있다" 로 읽힌다.

0046 이 **스스로 진단한 것**과도 맞는다. 그 문서는 선례 둘의 근거가 서로 반대인 것을
두고 *"적힌 근거가 실제 결정 원리가 아니라는 신호"* 라 적고, 진짜 공통점은
**갈리는 것이 필드 두 개뿐**이었다는 데 있다고 짚었다. §9.2 의 추가 데이터가 붙으면
갈리는 것이 더 이상 두 필드가 아니다.

**0046 의 본체(게시글 상세)는 그대로 선다.** 대체되는 것은 선례 표의
`ActivityController.ActivityItem` 행 하나이며, `PostDetailResponse` 의 단일 타입 결정,
중첩 투표 섹션, 미투표자에게 집계를 감추는 판단은 이 결정과 무관하다.

## 결과 (트레이드오프)

### 응답 타입이 셋으로 늘고, 지금은 필드가 같다

OpenAPI 스키마가 하나에서 셋으로 늘었는데 내용이 동일하다 — 이 시점만 보면 중복이다.
#157·#158 이 붙기 전까지는 그렇게 보이며, **골격만 먼저 넣는 선택의 비용**이다.
받아들이는 이유는 이 이슈가 #157·#158 을 막고 있어서다. 필드 보강까지 한 PR 에 담으면
되돌리기 비싼 계약 결정과 화면 데이터 보강이 한 리뷰에 섞인다.

### 기존 커서가 모두 무효가 된다

배포 시점에 무한 스크롤 중이던 클라이언트는 다음 조각 요청에서 400 을 받고 첫 조각부터
다시 읽는다. 커서는 세션 안에서만 쓰이는 값이라 영향이 짧고, 조용히 되감기는 대안보다 낫다.
**구 경로 커서까지 함께 무효화한 근거는 결정 3 에 적었다.**

### 경로가 넷이 된다 (구 경로 포함)

`?type=` 을 남기므로 같은 데이터를 읽는 경로가 당분간 넷이다. 문서에 deprecated 로
표시해 새 클라이언트가 고르지 않게 하고, 제거는 전환 확인 후 별도 이슈로 미룬다.
**지우지 않는 대신 계약이 넷인 기간을 감수**한다.

### 인증 경로 목록 세 곳을 함께 고쳐야 한다

`SecurityConfig` 의 `.anyRequest()` 관문이 새 경로를 자동으로 막으므로 **보안 설정과
공개 목록은 바뀌지 않는다.** 다만 보호 사실을 **증명하는** 목록이 테스트 세 곳에
하드코딩돼 있어(`GuestAccessPolicyIT` · `WithdrawnUserAuthorizationIT` ·
`ActivityControllerIT`) 함께 고친다. 빠뜨리면 새 경로가 인증 검증 없이 통과한다.

## 검토한 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **현행 유지 — 한 경로·한 타입에 nullable 필드로 추가** | §9.2 의 추가 데이터가 붙으면 유형에 따라 `null` 이 되는 필드가 넷 늘어난다. 어느 필드가 언제 채워지는지를 타입이 말해주지 못해 클라이언트가 유형을 보고 판단하게 된다 — 계약이 흐려지는 것이 정확히 이 이슈가 푸는 문제다 |
| **경로는 하나로 두고 응답 타입만 `oneOf` 로 분기** | 유형이 쿼리 파라미터로 남아 커서 교차 문제가 그대로다. 게다가 `oneOf` 는 클라이언트에 판별자 기반 파싱 분기를 강제하는데, 경로로 가르면 그 분기 자체가 없다 |
| **구 경로를 이번에 제거** | SPEC 에 공개된 계약이고 FE 가 OpenAPI 로 가져가는 구조라 미사용을 증명할 수 없다. 증명 없는 제거는 되돌리기 비싼 파손이다 |
| **커서 교차를 막지 않고 두기** | 세 경로가 같은 키 이름을 쓰므로 다른 유형의 커서가 구조상 유효해 보여 통과한다. 사용자는 `/posts` 에서 투표 활동의 위치로 잘린 목록을 보게 되는데, **틀렸다는 신호가 어디에도 없다** |
| **커서 교차 시 조용히 첫 조각 주기** | 클라이언트가 무한 스크롤이 되감기는 것을 본다. 기존 정렬 가드가 같은 이유로 이미 400 을 택했고(`ActivityListCursor` 주석), 같은 계열 문제에 다른 답을 두면 규약이 갈린다 |
| **유형 판별자를 `id` 나 정렬 값에 인코딩** | 커서 맵은 이미 이종 값을 담는 구조라 키를 하나 더하는 데 비용이 없다. 값에 접어 넣으면 `toLong`·`toLocalDateTime` 의 타입 복원이 그 인코딩을 알아야 해 두 관심사가 엉킨다 |
| **`CursorCodec` 에 판별자를 넣어 모든 목록에 적용** | 그 클래스는 게시글 목록·검색·랜딩 등 **다른 엔드포인트와 공용**이다. 활동 목록 하나의 사정으로 공용 인코딩을 바꾸면 무관한 커서가 전부 무효가 된다 |
| **구 경로 커서만 판별자 없이 계속 받기** | "판별자 없는 커서" 가 유효한 상태로 남아, 그 모양을 만들어 `/posts` 에 넣으면 교차 사용이 그대로 된다. 막으려던 구멍이 예외를 통해 되살아난다 |
| **응답 타입 셋이 공통 부모·인터페이스를 공유** | 지금은 필드가 같아 그럴듯하지만 #157·#158 이 각기 다른 필드를 더하면 공통부가 곧 비어 간다. 공유를 먼저 만들어 두면 그때 해체 비용을 치른다(YAGNI) |
