# ADR-0020 원픽의 유일성 범위는 게시글이다

**상태**: Accepted
**보완**: [ADR-0018](0018-onepick-as-behavior.md) — 원픽을 행위로 본 판단은 유지된다

## 맥락

`comment_pick` 의 유일성 키가 `UNIQUE(user_id, comment_id)` 였다.
"같은 사람이 같은 댓글을 두 번 픽하지 않는다"(R-26)만 막는다.

**그 범위가 기획과 다르다.** 기능명세서 v0.2 p.21은 "원픽 취소 불가(**한 게시글에 하나의
원픽만 가능**)"라고 적는다. 세는 단위가 댓글이 아니라 **게시글**이다.

현재 키로는 이 시나리오가 통과한다.

```
(user=7, post=3, comment=100)   ← OK
(user=7, post=3, comment=101)   ← 통과한다. 같은 사람이 같은 게시글에서 두 번 픽
```

한 사람이 한 게시글의 댓글 다섯 개를 픽하면 댓글 작성자들에게 +10P 가 다섯 번 나간다.
포인트가 걸린 규칙이라 뚫리면 되돌리기 어렵다.

### 판정이 한 번 뒤집혔다

2026-08-30에는 이 모델을 **"게시글 작성자가 하나만 채택한다"**(`post.picked_comment_id`)로
읽고 되돌리는 작업까지 진행했다. 근거는 기능명세서 v0.2 p.21의
"게시글의 작성자는 원픽 댓글을 선정할 수 있다" 였다.

그 문장은 **작성자에게 원픽 권한이 있다**는 뜻이지 **작성자만 할 수 있다**는 뜻이 아니었다.
화면설계서 COM_03의 "타인의 댓글에는 원픽 가능"은 주어가 없어 양쪽으로 읽혔고,
`[댓글 설정 - 게시글 작성자 관점]` 이라는 **섹션 제목**을 행위자 한정으로 읽은 것이 오독이었다.

**교훈**: 문서의 위계나 섹션 제목이 아니라, **행위자와 범위가 함께 적힌 문장**이 판정 근거다.
"한 게시글에 하나"는 범위를 말한 문장이고, 그 범위의 주체가 사용자라는 것이 최종 확인 사항이었다.

## 결정

**유일성 범위를 `(user_id, post_id)` 로 바꾼다.** 테이블 구조는 그대로 둔다.

```sql
UNIQUE KEY uk_pick_user_post (user_id, post_id)
```

| 규칙 | 내용 | 지키는 곳 |
|---|---|---|
| R-05 | 한 사람은 한 게시글에서 댓글 하나만 원픽한다 | `UNIQUE(user_id, post_id)` |
| R-06 | 원픽은 취소하거나 변경할 수 없다 | `comment_pick` 에 UPDATE·DELETE 경로 없음 |
| R-07 | 자기 댓글은 원픽할 수 없다 | `Comment.pick(pickerId)` |

원픽은 **게시글 작성자만의 권한이 아니다.** 댓글 작성자 본인만 아니면 누구나 픽할 수 있다.

### 판정을 스키마가 하는 이유

"이 사람이 이 게시글에서 픽했나"를 조회해서 판단하면 확인과 삽입 사이에 틈이 생긴다.
동시 요청 두 건이 모두 "없음"을 보고 각자 삽입한다. 유니크 키는 그 틈이 없다.

저장소는 `saveIfAbsent` 로 **"삽입됐는가"라는 사실만** 돌려주고,
그것을 R-05 위반으로 해석하는 것은 서비스의 몫이다 (ADR-0019).

### 조회 조건에 comment_id 를 넣지 않는다

```java
// ✗ 대상 댓글이 조건에 있으면 "다른 댓글을 픽하는 경우" 를 못 잡는다
existsByUserIdAndPostIdAndCommentId(userId, postId, commentId)

// ✓ 세는 단위는 게시글이다
existsByUserIdAndPostId(userId, postId)
```

같은 이유로 유니크 키에도 `comment_id` 를 넣지 않는다.
세 컬럼을 모두 넣으면 튜플이 유일해져서 오히려 **제약이 느슨해진다** —
`(7, 3, 100)` 과 `(7, 3, 101)` 이 서로 다른 행으로 통과한다.

## 결과

- R-26("같은 사람이 같은 댓글을 두 번 픽하지 않는다")은 **R-05 에 흡수된다.**
  게시글당 하나면 같은 댓글 재픽은 자동으로 불가능하다. 별도 규칙으로 세지 않는다
- `DuplicatePickException` 은 그대로 쓰되 식별자가 `commentId` → `postId` 로 바뀐다.
  "이미 원픽한 댓글" 이 아니라 "이 게시글에서 이미 원픽했다" 가 정확한 메시지다
- 포인트(R-12·R-13)는 그대로다 — 댓글 작성자 +10P, 픽한 사람 +5P.
  멱등키 `(comment_pick_id, reason)` 도 유지된다. 픽 1건이 여전히 지급 1회의 단위다
- `post ↔ comment` 순환 FK 가 생기지 않는다. 원픽 상태가 게시글 컬럼이 아니라
  별도 테이블에 있으므로 `ALTER TABLE` 로 뒤늦게 FK 를 붙일 필요도 없다
- 복합 FK `(comment_id, post_id) → comment(id, post_id)` 는 유지한다.
  다른 게시글의 댓글을 픽하는 것을 DB 가 막는다

## 검토한 대안과 기각 사유

**`post.picked_comment_id` 로 회귀 (ERD 초안의 설계).**
게시글에 컬럼 하나를 두고 작성자가 채택하는 모델. 초안이 불가역성 트리거까지 만들어
검증했고 PR #11 동료 리뷰도 확인한 경로다.
기각 — **행위자를 잘못 읽은 모델이다.** 원픽은 게시글 작성자 전용이 아니다.
컬럼이 하나뿐이라 여러 사용자가 각자 픽하는 것을 표현할 수 없다.

**`UNIQUE(user_id, post_id, comment_id)`.**
세 컬럼을 모두 넣어 "이 사람의 이 게시글의 이 댓글" 을 유일하게 만든다.
기각 — 제약이 **느슨해진다.** 튜플이 유일해질 뿐이라 같은 사람이 같은 게시글의
다른 댓글을 픽하는 것을 막지 못한다. 사실상 `(user_id, comment_id)` 와 같은 동작이다.

**DB 트리거로 불가역성(R-06) 강제.**
초안이 `trg_post_pick_immutable` 로 막았던 방식.
기각 — **MySQL 8.4 에서 만들 수 없다.** binlog 가 기본으로 켜져 있고
`log_bin_trust_function_creators=0` 이라 트리거 생성에 `SUPER` 가 필요하다(오류 1419).
앱 사용자에게도 RDS 마스터 계정에도 없어, 통합테스트 전체가 마이그레이션 단계에서 죽었다.
`comment_pick` 모델에서는 애초에 필요 없다 — UPDATE 경로를 두지 않으면 행이 바뀌지 않는다.

**응용 계층에서만 검증.**
조회해서 이미 픽했으면 거부한다.
기각 — 확인과 삽입 사이에 틈이 있어 동시 요청에서 뚫린다.
유니크 키가 같은 판정을 원자적으로 한다.
