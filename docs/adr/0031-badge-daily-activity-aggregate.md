# ADR-0031 — 뱃지 판정은 날짜별 집계 테이블에서 하고, 뱃지 이름은 데이터로 둔다

**상태**: Accepted
**보완**: [ERD 초안](../erd/ERD-초안.md) §5.3·§8.6 이 설계해 두고 [ERD 2차](../erd/ERD-2차.md) §1.2 가
"코어 흐름 밖" 이라며 유예했던 세 테이블(`badge`·`user_badge`·`user_daily_activity`)을 이 문서가 되살린다.
DDL 의 형태는 초안을 따르고, 구현으로 드러난 것(ERD 3차)을 반영해 타입과 인덱스를 조정했다.

## 맥락

뱃지 8종(정책 요약표 §3)은 획득 조건의 유형이 셋이다 (R-18).

| 유형 | 조건 | 판정에 필요한 것 |
|---|---|---|
| 누적 투표 | 10 / 100 / 500 / 1,000회 | 누적 투표 횟수 |
| 일일 투표량 | 하루 20 / 30개 | **날짜별 투표 수** |
| 연속 참여 | 7 / 30일 | **날짜별 투표 유무의 연속성** |

두 가지가 함께 결정돼야 했다. **어디서 판정하는가**와 **뱃지 정의를 어디에 두는가**다.
둘 다 되돌리기 비싸다 — 전자는 스키마이고 후자는 API 응답 구조를 가른다.

### 전제 하나가 비어 있다 — `users.vote_count` 는 아무도 채우지 않는다

설계 전에 확인한 사실이다. `users.vote_count` 는 V3 에 있고 주석도 "vote 건수" 지만,
**애플리케이션 어디도 이 컬럼에 쓰지 않는다.** `UserEntity` 는 이 필드를 매핑조차 하지 않고,
투표 경로인 `VoteService.castFirst()` 는 `post.vote_count` 와 `post_option.vote_count` 만 올린다.
곧 오늘 이 스키마에서 모든 회원의 값은 0 이다.

[ADR-0028](0028-author-ranking-precompute.md) 이 `users.point` 에서 똑같은 것을 발견하고
"영원히 동작하지 않는 코드" 라 부른 상황과 같다. 누적 투표 횟수의 정본이 없으므로
그것부터 정해야 한다.

## 결정 1 — 일일·연속·누적을 모두 `user_daily_activity` 에서 유도한다

**날짜별 투표 수를 집계 테이블에 쌓고, 세 유형의 판정이 모두 그 테이블을 읽는다.**

### 왜 `vote` 를 직접 읽으면 안 되는가

`vote` 에는 이미 `idx_vote_user_created (user_id, created_at)` 가 있어 누적 카운트는 싸다.
문제는 나머지 둘이다.

| 판정 | `vote` 직접 조회 | 원인 |
|---|---|---|
| 하루 20개 | 그날 투표 행 전부 | `DATE(created_at)` 가 컬럼을 감싸 인덱스가 죽는다. 범위로 풀어써도 그날 행을 다 읽는다 |
| 7일 연속 | **그 회원의 투표 전체** | `DISTINCT DATE(...)` 로 날짜를 만들려면 전부 훑어야 한다 |

**1,000회 투표한 사람의 "7일 연속" 을 판정하려고 1,000행을 읽는 꼴이다.**
그리고 이 판정은 **투표할 때마다** 일어난다 — 명세 §2.3 이 "투표 시 미션 2의 상태바가
즉시 변경됨" 을 요구하므로 미룰 수도 없다. 쓰기 핫패스에 선형 증가 비용이 붙는다.

집계 테이블은 회원당 **활동한 날 수**만큼만 행을 갖는다. "하루 20개" 는 행 하나,
"30일 연속" 은 최근 31행이면 끝난다. 투표가 아무리 쌓여도 판정 비용이 늘지 않는다.

실행 계획으로 확인했다(`BadgeJudgementQueryIT`, 41명 × 100일 = 4,100행).

| 판정 | type | key | Extra |
|---|---|---|---|
| 연속 | `range` | `uk_daily_user_date` | **Using index; Backward index scan** |
| 누적 합계 | `ref` | `uk_daily_user_date` | — |

`Using index` 는 커버링이라 테이블 접근이 없다는 뜻이고, `Backward index scan` 은
`ORDER BY activity_date DESC` 를 인덱스 역방향으로 읽어 정렬 비용이 0 이라는 뜻이다.
`(user_id, activity_date)` 컬럼 순서가 이 둘을 함께 만든다.

> **측정 중 배운 것.** 같은 쿼리가 100행짜리 테이블에서는 `type=ALL`, `key=null` 이었다.
> 옵티마이저가 인덱스 왕복보다 풀스캔이 싸다고 **옳게** 판단한 것이다.
> 그 상태의 계획을 결함으로 읽고 코드를 고쳤다면 없는 문제를 고치는 셈이었다 —
> 그래서 검증 테스트가 데이터 규모를 고정한다.

### 누적도 같은 테이블에서 유도한다

`users.vote_count` 를 채우지 않고 일별 행의 `SUM(vote_count)` 을 쓴다.

- **같은 사실을 두 곳이 표현하면 어긋난다.** V5 가 정확히 그 문제(닉네임 반납 기준이
  `deleted_at` 과 `state` 두 곳)를 고치느라 컬럼 하나를 걷어냈다. 일별 행이 이미 그날의
  투표 수를 갖고 있으므로 누적은 그것의 합계이지 별개의 사실이 아니다.
- **비용이 활동 일수에 비례한다** — 투표 수가 아니다. 매일 투표해도 1년에 365행이고
  커버링 인덱스로 읽는다. 자기 행만 보는 **지역** 집계라, 20만 명 전역 정렬이 필요했던
  랭킹(ADR-0028)과 성격이 다르다. 그 선례를 여기 끌어오면 잘못된 유추다.
- 나중에 느려지면 카운터 컬럼을 추가하고 `SUM` 으로 백필하면 된다 — **되돌리기 싼 결정**이다.

`users.vote_count` 는 건드리지 않고 남겨 둔다. 등급(#25)이 같은 값을 필요로 하므로
그쪽이 자기 방식으로 채우게 두고, 뱃지는 자기 애그리거트 안에서 완결한다.

### R-22 는 호출 지점이 지킨다

재투표는 일별 활동을 늘리지 않는다. 스키마로는 표현할 수 없다 —
"이 투표가 첫 투표인가" 는 `vote` 를 봐야 알고 `CHECK` 는 다른 행을 보지 못한다.
`VoteService` 가 이미 첫 투표(`castFirst`)와 선택 변경(`changeChoice`)을 갈라 두었으므로
**첫 투표 경로에만** 붙인다. 두 경로가 이미 갈려 있어 호출을 잊을 자리가 없다.

## 결정 2 — 뱃지 이름은 데이터, 조건 유형은 코드

**`badge` 테이블에 8행을 두고 `code` 로 식별한다. 표시명은 그 행의 컬럼이다.**

정책 정본의 표 제목이 **"3. 뱃지 정책 (뱃지명은 추후 수정됩니다)"** 다.
기획이 변경을 예고한 값이므로 이름은 불안정하고 조건이 안정 계약이다.

- **이름이 바뀌면** `UPDATE badge SET name = ...` 한 줄이다. 코드도 마이그레이션도 손대지 않는다.
- **`code` 는 조건에서 딴 이름**이다(`TOTAL_VOTE_10`). 표시명에서 따면(`VOTE_SPROUT` 같은)
  이름이 바뀌는 순간 코드와 화면이 어긋난 채 남는다. 조건은 바뀌지 않으므로 함께 낡지 않는다.
- **조건 유형 셋은 enum** 이다(R-18). 유형은 정책이 바꾼다고 예고하지 않았고,
  판정 로직이 유형별로 갈리므로 코드가 알아야 한다. 여덟 개의 **인스턴스**는 데이터이고
  세 개의 **유형**은 코드다 — 이 축이 안정과 불안정을 가른다.

`display_order` 도 데이터다. 3X3 고정 배치(§12.2)라 노출 순서가 API 계약이다.

## 결정 3 — 기존 투표를 백필한다

V9 가 집계 테이블을 만들면서 `vote` 에서 일별 집계를 채운다.

**이걸 빠뜨리면 기능 전체가 조용히 틀린다.** 빈 테이블로 두면 배포 직후 모든 회원의
누적 투표가 0 이 되어 500회 투표한 사람이 `0/10` 을 본다. 그런데 에러는 나지 않는다 —
API 는 200 을 주고 테스트도 빌드도 통과한다. 사용자가 신고해야 발견되는 결함이다.

백필에서만 `DATE(created_at)` 을 쓴다. 판정 경로에서 이 함수를 쓰면 인덱스가 죽지만,
이건 일회성 변환이고 `created_at` 은 애플리케이션이 이미 `Asia/Seoul` `Clock` 으로 쓴 값이라
세션 타임존이 끼어들지 않는다.

**집계만 채우는 것으로는 절반이다.** 판정은 투표 시점에만 돌므로, 집계를 백필해도
이미 조건을 넘긴 회원의 뱃지는 미획득으로 남는다. 500회 투표한 회원이 진행률
"500/1000" 은 제대로 보면서 10·100·500 뱃지는 없는 상태가 되고, 다음 투표를 해야
세 개가 한꺼번에 지급된다. **오히려 이쪽이 발견이 늦다** — 진행률이 맞아 화면이
그럴듯해 보이기 때문이다. 그래서 V9 가 세 유형을 각각 SQL 로 판정해 **소급 지급**까지 한다.

소급이 맞는 이유는 뱃지에 회수 개념이 없고(`user_badge` 에 DELETE 경로가 없다)
조건이 과거 기록만으로 판정되기 때문이다. 누적은 총계라 시점과 무관하고,
일일·연속도 "그날 20개를 채웠다"·"7일 이어졌다" 는 사실이 집계에 남아 있다.
연속은 gaps and islands(날짜에서 행 번호를 빼면 연속 구간이 같은 값이 된다)로
최장 구간을 구한다. 임계값은 `badge` 테이블을 조인해 읽는다 — 숫자를 SQL 에 다시
적으면 정책이 바뀔 때 고칠 자리가 둘이 된다.

## 결과

**얻는 것**

- 판정 비용이 투표 수와 무관해진다. 3년 매일 투표한 회원도 연속 판정에 31행만 읽는다.
- 뱃지 이름 변경이 배포를 부르지 않는다. 기획이 예고한 변경이라 실제로 일어난다.
- 세 유형이 한 테이블에서 나와, 정본이 하나다.

**치르는 것**

- **투표 트랜잭션이 길어진다.** UPSERT 하나와 뱃지 8행 조회가 붙는다.
  비동기로 빼지 않은 이유는 아래 대안 표에 있다. 동시 투표 8건을 겹쳐도
  전부 성공하는 것은 확인했다(`BadgeControllerIT` 동시 투표).
- **집계와 `vote` 가 어긋날 수 있다.** 유도 값이라 원본에서 재계산할 수는 있지만,
  어긋났다는 사실을 알아챌 장치가 지금은 없다. 정합성 점검 배치는 범위 밖으로 미뤘다.
- **연속 일수를 31 에서 자른다.** 최대 임계값이 30 이라 판정에는 영향이 없지만,
  "며칠째 연속인가" 를 화면에 그대로 보여주는 요구가 생기면 상한을 올려야 한다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| **`vote` 를 직접 집계** (새 테이블 없음) | 연속 판정이 그 회원의 투표 전체를 훑는다. `DATE()` 가 인덱스를 무력화하고, 이 판정은 투표마다 일어난다. R-19 가 명시적으로 금지한 형태다 |
| **`users.vote_count` 를 누적 정본으로** | 일일·연속을 못 푼다(날짜 정보가 없다). 그 컬럼을 채우면 등급(#25)과 같은 컬럼을 두 워커가 건드린다 |
| **누적 카운터 컬럼 신설** | 같은 사실을 두 곳이 표현해 어긋난다(V5 의 전례). 활동 일수 규모에서 `SUM` 이 충분히 싸고, 필요해지면 나중에 추가·백필하면 되는 **되돌리기 싼 결정**이다 |
| **뱃지 8종을 enum 상수로** | 정책이 이름 변경을 명시적으로 예고했다. enum 이면 이름 하나 바꾸는 데 배포가 필요하다 |
| **`badge` 테이블에서 조건 컬럼 제거**(표시 자원만) | 판정이 "이 유형의 이 임계값" 을 찾는 구조라 조건이 어딘가엔 있어야 한다. 코드에 두면 8종을 코드가 나열하게 되어, 임계값이 바뀔 때 고칠 자리가 둘이 된다 |
| **스프링 이벤트로 결합** | 이벤트의 실익은 의존 방향을 끊는 것인데 그건 `vote` 가 선언한 포트 인터페이스로 이미 끊긴다. 이 저장소에 없던 발행·구독 패턴을 새로 들이지 않는다. `OnePickService` 가 포인트 지급을 직접 부르는 기존 관행과도 어긋난다 |
| **판정을 `AFTER_COMMIT` 이나 `@Async` 로** | 투표는 커밋되고 활동 기록만 유실되면 R-19 의 정본이 조용히 어긋난다. 30일을 찍고 31일째 쉬면 영구 손실이다. 되돌릴 방법은 있어도 어긋났다는 사실을 아무도 모른다 |
| **판정을 조회 시점에 지연 계산** | 명세 §2.3 이 "투표 시 미션 2의 상태바가 즉시 변경됨" 을 요구한다. 획득 시각도 남길 수 없어 획득 모달(§12.3)이 새 뱃지를 가리지 못한다 |
| **뱃지 지급을 "확인 후 삽입" 으로** | **실측이 이 안을 기각했다** — 아래 참조 |
| **뱃지 지급에서 무결성 예외를 삼키기** | 투표 트랜잭션 안이라 rollback-only 로 표시되어 커밋 시 `UnexpectedRollbackException` 이 나고 **투표가 통째로 실패한다**. `INSERT IGNORE` 도 FK 위반까지 삼켜 답이 아니다 (layer-responsibility) |

### 지급을 "확인 후 삽입" 으로 두었다가 실측으로 뒤집었다

처음 구현은 `existsByUserIdAndBadgeId` 로 거른 뒤 저장하는 형태였다. UNIQUE 를 최종
방어선으로 두었으니 그 틈은 "같은 사람이 같은 순간에 두 번 투표하는 희귀 경로" 라고 적었다.

**틀렸다.** 같은 회원이 8개 요청으로 임계값을 동시에 넘기는 시나리오를 실제로 돌렸더니
**1건만 성공하고 7건이 500(`SYSTEM_ERROR`)** 이 됐다. 원인은 희귀 경합이 아니라 구조다 —
8개 요청이 **아무도 아직 삽입하지 않은 시점에** 모두 조회하므로 전부 "없다" 를 보고
전부 삽입을 시도한다. 하나만 이기고 나머지는 무결성 위반으로 죽는다.

그리고 그 실패가 **투표를 통째로 죽였다.** 이 문서가 "뱃지는 투표의 부가 효과라
인질로 잡으면 안 된다" 고 써놓고 정확히 그렇게 만들어 둔 것이다.

`layer-responsibility` 룰이 "확인 후 삽입은 동시 요청에서 뚫린다" 고 경고한 형태 그대로였다.
UNIQUE 를 최종 방어선으로 둔 것까지는 맞았지만, **뚫렸을 때 무엇을 할지**가 틀렸다.

고친 형태는 `INSERT ... ON DUPLICATE KEY UPDATE user_id = user_id` 다.
중복이 **예외가 아니라 "아무것도 바꾸지 않음"** 이 되어 트랜잭션이 살아 있고,
R-17 은 여전히 UNIQUE 가 지킨다 — 달라진 것은 그 제약이 예외를 던지는 대신
삽입을 무시하게 만든 것뿐이다. 같은 시나리오에서 **8건 모두 성공**하고 보유 행은 하나다.

`INSERT IGNORE` 는 쓰지 않는다. 그쪽은 FK 위반까지 삼켜, 없는 회원에게 뱃지를 주려던
버그가 흔적 없이 사라진다.

대가로 저장소가 "이번에 새로 줬는가" 를 알려주지 못한다 — 영향 행 수는
드라이버·설정에 따라 갈리기 때문이다(ERD 3차 §1.3). 그 판단은 지급 전 보유 목록을
아는 서비스가 하고, 동시 판정에서는 양쪽이 같은 뱃지를 "새로 얻었다" 고 볼 수 있다.
지금 그 값을 쓰는 곳이 없어 문제되지 않지만, 획득 모달(§12.3)이 붙으면
알림이 두 번 갈 수 있으므로 그때 판정 방식을 다시 정한다.

> **교훈.** "희귀할 것" 이라는 추정을 근거로 실패 경로를 남겨두지 않는다.
> 동시성은 측정 전까지 빈도를 알 수 없고, 이 경우 추정(희귀)과 실측(8건 중 7건)의
> 차이가 두 자릿수였다.

## 열린 질문

1. **집계와 `vote` 의 정합성 점검.** 유도 값이라 어긋날 수 있는데 지금은 알아챌 장치가 없다.
   주기 대사(對査) 배치를 둘지, 어긋남이 실제로 관측될 때 만들지 정하지 않았다.
2. **연속 뱃지를 미션 슬롯에 넣을지.** 명세 §2.3 이 슬롯을 둘(누적·일일)로 못박아 지금은 빼두었다.
   기획이 세 번째 슬롯을 원하면 계약이 바뀐다.
3. **뱃지 일러스트.** §12.2 가 일러스트를 요구하지만 자산이 아직 없다. `badge` 행에 URL 컬럼을
   더하면 되도록 이름을 데이터로 둔 구조가 그대로 받아준다.
