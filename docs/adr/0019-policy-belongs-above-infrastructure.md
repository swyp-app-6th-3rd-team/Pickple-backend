# ADR-0019 — 정책 판단을 인프라에서 걷어낸다

**상태**: Accepted

## 맥락

코어 도메인을 구현하면서 **인프라 계층이 도메인 정책을 여러 곳에서 침범했다.**
의도한 설계가 아니라 편의를 따라가다 쌓인 것이라, 무엇이 왜 잘못됐는지 남긴다.

침범은 세 형태로 나타났다.

**첫째, 저장소가 정책 예외를 던졌다.**

```java
// JpaOnePickStore
catch (DataIntegrityViolationException e) {
    throw new DuplicatePickException(pick.commentId(), pick.pickerId());
}
```

`UNIQUE(user_id, comment_id)` 위반은 인프라 사실이다.
그것이 "이미 원픽했다"는 **정책 위반**이라는 해석은 다른 층의 판단이다.
`JpaPointHistoryStore`도 같은 형태로 `DuplicateGrantException`을 던지고 있었다.

**둘째, 서로 다른 원인을 같은 예외로 뭉갰다.**

`DataIntegrityViolationException` 하나에 여러 원인이 섞인다. 처음엔 전부 잡아 중복으로 보고했더니,
**다른 게시글의 댓글을 픽했을 때(복합 FK 위반) "이미 원픽한 댓글입니다"라고 답했다.**
통합 테스트가 잡았다. 원인과 메시지가 어긋나면 디버깅할 때 엉뚱한 곳을 보게 된다.

**셋째, 여러 도메인에 걸친 규칙이 갈 곳을 잃었다.**

R-12(원픽 1건 → 댓글 작성자 +10P, 픽한 사람 +5P)는 댓글·원픽·포인트 세 도메인이 얽힌다.
어느 애그리거트도 혼자 판정할 수 없다. 서비스 계층이 없다 보니 이 규칙은 **어디에도 구현되지 않았다.**
R-13(재지급 금지)도 스키마의 멱등키만 있고 그것을 정책으로 해석하는 자리가 없었다.

근본 원인은 하나다 — **"어디에 둘 것인가"의 기준이 없었다.**
규칙을 만나면 가장 가까운 곳, 즉 그 규칙이 처음 문제가 된 지점에 넣었다.
동시성 때문에 유니크 키를 쓰기로 한 판단은 옳았지만, 거기서 멈추지 않고 해석까지 인프라에 넣은 것이 잘못이다.

## 결정

**판정에 필요한 정보의 범위로 가른다.** 규칙의 종류가 아니다.

| 판정에 필요한 것 | 두는 곳 |
|---|---|
| 애그리거트 **하나**의 상태 | 도메인 객체 |
| 애그리거트 **여럿**의 협력 | 서비스 |
| **동시성**이 걸린 유일성·참조 무결성 | 스키마(UNIQUE·FK) |
| 저장·조회 | 저장소 — **정책 판단 금지** |

우선순위는 도메인 → 서비스다. "애그리거트 하나로 되나?"를 먼저 묻고, 된다면 올리지 않는다.
규칙이 객체 안에 있으면 그 객체를 쓰는 모든 경로가 자동으로 지키고, 찾을 때도 한 곳만 보면 된다.

**저장소는 사실만 알린다.**

```java
// 저장소 — 삽입됐는지 여부만
Optional<Long> saveIfAbsent(OnePick pick);

// 서비스 — 그 사실을 정책으로 해석
Long pickId = pickStore.saveIfAbsent(pick)
        .orElseThrow(() -> new DuplicatePickException(commentId, pickerId));
```

**무결성 위반을 뭉뚱그리지 않는다.** 중복인지 FK 위반인지에 따라 원인이 다르므로,
같은 예외로 바꾸면 디버깅 때 엉뚱한 곳을 본다. 유일성만 사전 확인으로 가르고
나머지 위반은 그대로 올린다.

**행 개수 규칙은 저장 경로에 붙박는다.** `CHECK`는 다른 행을 셀 수 없어
R-02(상품 수)·R-04(선택지 수)를 스키마가 막지 못한다. 도메인 검증이 유일한 방어선인데
호출을 잊으면 소용없으므로, `PostStore.save()`가 `verifyPublishable()`을 강제 호출한다.

## 결과

- 정책이 바뀌어도 인프라를 고치지 않는다. 저장소는 "삽입됐다/안 됐다"만 말한다
- 저장소를 다른 맥락에서 재사용할 수 있다 — "중복이면 넘어가는" 배치가 예외를 삼킬 필요가 없다
- 규칙을 찾을 위치가 예측 가능해진다. 애그리거트 하나면 그 객체, 여럿이면 서비스
- 대가: 서비스 계층이 필요해진다. R-12·R-13 때문에 원래 필요했던 것이라 순비용은 아니다
- 대가: 저장소 시그니처가 `Optional`·`boolean`이 되어 호출부가 한 줄 늘어난다.
  그 한 줄이 "여기서 정책을 해석한다"를 드러내므로 받아들인다

**구현하며 드러난 함정 둘.**

*예외를 잡아 사실로 바꾸는 것이 같은 트랜잭션 안에서는 성립하지 않는다.*
`@Transactional` 안에서 `DataIntegrityViolationException` 이 나면 스프링이 트랜잭션을
rollback-only 로 표시한다. 예외를 삼켜 `Optional.empty()` 를 돌려줘도
커밋 시점에 `UnexpectedRollbackException` 이 난다.
저장소 단독 호출에서만 드러났다 — 서비스 테스트는 예외가 밖으로 나가 롤백이 정상 경로였다.

*`INSERT IGNORE` 는 너무 많이 삼킨다.* 대안으로 시도했더니 유일성 위반뿐 아니라
**FK 위반까지 경고로 낮춰** 다른 게시글의 댓글을 픽해도 조용히 넘어갔다.
잘못된 요청이 신호 없이 사라지는 것이 중복 예외보다 나쁘다.

→ **존재를 먼저 확인하고 저장한다.** 확인과 삽입 사이에 틈이 있지만 유니크 키가 최종 방어선이라
데이터는 깨지지 않는다. 그 좁은 창에서 겹치면 뒤쪽이 예외로 실패하고, 재시도로 해결된다.
(`post_commenter` 의 첫 댓글 판정은 예외다 — 거기선 유일성만 걸려 있어 `INSERT IGNORE` 가 안전하다)

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 저장소가 정책 예외를 던지는 현행 유지 | 정책이 인프라에 묶인다. 재사용도 막히고, 정책 변경이 인프라 수정을 부른다 |
| 모든 규칙을 서비스로 올린다 | 도메인이 빈 데이터 홀더가 된다. R-07처럼 객체 하나로 판정되는 규칙까지 밖으로 나가면 우회 경로가 생긴다 |
| 모든 규칙을 도메인 객체에 넣는다 | R-12는 세 도메인이 얽혀 어느 애그리거트도 혼자 판정할 수 없다. 억지로 넣으면 애그리거트가 서로를 참조하게 된다 |
| 중복 검사를 도메인에서 조회 후 판정 | 확인과 삽입 사이에 틈이 있어 동시 요청에서 뚫린다. 유니크 키가 원자적이다 |

## 검증

- `JpaOnePickStoreIT` — 저장소는 중복이면 빈 값을, 다른 게시글의 댓글을 픽하면
  `DataIntegrityViolationException` 을 낸다. 원인과 결과가 맞는지 확인한다
- `OnePickServiceIT` — 서비스가 빈 값을 `DuplicatePickException` 으로 해석하는지,
  R-12 로 두 사람에게 지급되는지, 중복이 막히면 포인트도 안 늘어나는지
- 저장소에 도메인 예외(`throw new *Exception`)가 없는지 확인한다
- 새 규칙을 넣을 때 "이게 왜 여기 있나"를 한 문장으로 답할 수 있어야 한다
