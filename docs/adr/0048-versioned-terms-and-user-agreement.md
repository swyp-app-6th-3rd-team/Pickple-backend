# ADR-0048: 약관 본문은 버전별로, 사용자 동의는 버전의 최초 수락으로 저장한다

- 상태: Accepted (DB 기반 구조에 한정)
- 날짜: 2026-09-10
- 관련 이슈: #123, #147
- 보완: ADR-0003의 초 단위 Asia/Seoul 시각 계약을 따른다. ADR-0040의 개인정보 파기 원칙을 대체하지 않는다.

## 맥락

#123에서 약관 동의 이력을 서버에 저장하기로 결정했다. 기능명세서 v0.4 §1.6은 전체 동의와 노션 링크 열기를 규정하지만 항목별 필수 여부·버전·재동의·보존 정책은 완성되어 있지 않다. 이번 사용자 요청은 원 이슈의 범위를 확장하여 약관 본문 테이블도 만들도록 한다.

PM 제공 MD에는 시행일·업체·담당자 자리표시자가 남아 있다. 사용자는 테이블을 먼저 만들고 최종본 수령 후 본문을 등록하도록 확정했다. V14까지의 DB에는 관련 테이블이 없으며, 회원 탈퇴는 `users`를 물리 삭제하지 않고 INACTIVE로 전환한다.

## 결정

1. V15에서 `terms`, `user_agreement` 두 테이블만 추가한다. 기존 마이그레이션·회원 데이터는 변경하지 않는다. 본문·동의 시드는 없다.
2. `terms` 한 행은 한 종류의 한 버전이다. 전체 Markdown 본문, 제목, 필수 여부, 시행 시각, 등록 시각을 보존한다. 종류·버전과 종류·시행 시각 각각에 UNIQUE를 둔다. 필수 여부에는 기본값을 두지 않고 0/1만 허용한다.
3. 현재 버전은 종류별로 `effective_at <= now` 중 시행 시각이 가장 늦은 행이다. 문자열 버전이나 등록 시각으로 정렬하지 않는다. 최종 승인된 문서만 등록하며 초안 상태 관리는 이번 범위에 없다.
4. 공개 이후 본문·제목·필수 여부·시행 시각을 덮어쓰지 않고 새 버전을 추가한다. FK는 과거 버전 삭제를 막지만 임의 UPDATE까지 막지는 않는다. 이 불변성은 후속 저장 경로와 운영 권한에서 지켜야 한다.
5. `user_agreement`는 사용자·약관 버전별 최초 수락 사실이다. 사용자와 약관 ID, 최초 동의 시각을 저장하고 UNIQUE(user_id, terms_id)와 두 FK를 둔다. 동의 시각은 후속 서버의 Clock에서 명시 입력한다.
6. 같은 버전 재요청에서 최초 시각을 보존하는 멱등 처리, 인증 사용자/ACTIVE 검증, 현재 동의 대상 검증, 필수 항목의 원자적 저장은 후속 API 책임이다. UNIQUE는 UPDATE나 다른 버전 중복을 막는 장치가 아니다. 무결성 예외 전체를 중복 성공으로 처리하지 않는다.
7. 사용자 물리 삭제에는 CASCADE, 참조 중인 약관 삭제에는 RESTRICT를 적용한다. **soft delete는 CASCADE를 실행하지 않는다.** 동의 이력 보존 기간을 이 FK 규칙으로 결정하지 않는다. 실제 동의 수신 기능을 켜기 전에 철회·탈퇴 보존/파기 정책 및 서비스 연동을 확정해야 한다.
8. 이메일·IP·기기 식별자와 거절/OS 권한 상태는 저장하지 않는다. 행의 존재는 최초 수락 기록이며 현재의 철회되지 않은 동의 상태까지 뜻하지 않는다. 철회·재수락 전체 이력이 필요하면 별도 순방향 확장으로 설계한다.
9. 개인정보처리방침과 별도 수집·이용 동의문을 같은 대상으로 간주하지 않는다. PM의 실제 항목·문안·필수 여부·버전·시행일·정본 링크 대응을 확인한 뒤 데이터를 등록한다. 기존 노션 링크와 공개 조회 계약은 바꾸지 않는다.

## 결과

사용자별 본문 복제 없이 언제 어떤 버전에 동의했는지 연결할 기반이 생긴다. 새 버전을 추가해도 과거 동의의 FK는 원래 본문을 가리킨다. 중복·유실 참조는 실제 MySQL 제약으로 거부한다.

HTTP API나 가입 차단은 추가하지 않으므로 실제 동의 수집이 시작되지는 않는다. 공개 문서의 불변성, 필수 항목 전체 수락, 탈퇴 파기는 DDL만으로 완성되지 않는다. 현재 두 테이블은 철회 이벤트 원장·다국어·공지 게시 워크플로를 지원한다고 약속하지 않는다.

MySQL DDL의 부분 적용 가능성을 인정한다. 실패 시 실제 생성 테이블과 Flyway 이력을 조사하고 승인된 복구를 수행한다. `IF NOT EXISTS`나 자동 DROP/repair로 드리프트를 숨기지 않는다. 성공한 추가 테이블은 이전 애플리케이션 버전에서도 남겨 둘 수 있다.

## 검토한 대안과 기각 사유

| 대안 | 판단 |
|---|---|
| 저장하지 않음 | #123 결정과 사용자 요청을 충족하지 못한다 |
| users에 동의 시각 하나 | 항목·버전 및 당시 본문을 식별하지 못한다 |
| URL과 문자열 버전만 저장 | 링크 변경/삭제 후 본문 복원 및 FK 보장이 어렵다 |
| 문서 그룹·개정·게시·동의 이벤트를 모두 분리 | 현재 확정되지 않은 철회·운영 흐름까지 설계 비용이 커진다. 요구 확정 시 재검토한다 |

## 검증 계약

`TermsMigrationIT`에서 빈 DB 적용, V14 업그레이드와 기존 데이터 보존, 본문 왕복, 필수값·UNIQUE·FK 거부, 동시 중복 INSERT, 버전별 동의 및 시행 경계, 물리 삭제/soft delete 차이를 검증한다. 기존 Spring Context의 JPA validate와 탈퇴 회귀도 확인한다. 앱 E2E·운영 배포 검증은 포함하지 않는다.
