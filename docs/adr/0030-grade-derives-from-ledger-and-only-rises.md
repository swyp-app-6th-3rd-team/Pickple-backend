# ADR-0030 — 등급은 원장에서 판정하고, 도달한 등급만 저장한다

**상태**: Accepted
**보완**: [ADR-0028](0028-author-ranking-precompute.md) 이 확정한 "`users.point` 는 캐시,
`point_history` 가 정본" 이라는 위치를 등급 판정에 적용한다. 랭킹과 등급은 같은 원장을
읽지만 **읽는 시점이 다르다** — 그 차이가 이 문서의 핵심이다.

## 맥락

등급(Grade) 도메인이 아직 없다. 규칙만 문서에 있다 — 정책 요약표 §2 가 임계값을 정하고
도메인 모델이 R-15·R-16 으로 옮겨 적었다.

| 등급 | 승급 조건 (정책 요약표 p.1 §2) |
|---|---|
| LV.1 | 가입 시 기본 부여, 0P |
| LV.2 | 누적 200P + 투표 20회 |
| LV.3 | 누적 1,000P + 투표 100회 |
| LV.4 | 누적 3,500P + 투표 300회 |
| LV.5 | 누적 10,000P + 투표 1,000회 |

판정에 필요한 입력은 둘이다 — **누적 포인트**와 **누적 투표 횟수**. R-15 는 이 둘을
**AND** 로 묶는다. 포인트만 채워도 오르지 않는다.

### 입력값이 "이미 있다" 는 말은 절반만 맞다

착수 전에 두 캐시 컬럼의 상태를 전수 확인했다. V3 는 `users` 에 둘 다 선언해 뒀다.

| 컬럼 | V3 선언 | 실제로 쓰는 코드 |
|---|---|---|
| `users.point` | `INT UNSIGNED NOT NULL DEFAULT 0` — 주석 "point_history 합계" | **랭킹 배치만**(`JpaRankingStore.SYNC_POINTS`, 5분 주기) |
| `users.vote_count` | `INT UNSIGNED NOT NULL DEFAULT 0` — 주석 "vote 건수" | **없음.** `src/main/java` 전수 grep 0건 |

`users.vote_count` 는 ADR-0028 이 `users.point` 에서 짚었던 것과 **같은 종류의 함정**이다.
컬럼은 있고 주석도 그럴듯한데 아무도 채우지 않는다. 여기서 읽으면 모든 회원의 투표 횟수가
0 이라 **아무도 승급하지 못한다** — 컴파일도 되고 테스트도 초록인 채로.

`users.point` 쪽은 채워지긴 하지만 **최대 5분 낡는다**(`RANKING_BATCH_CRON` 기본 `0 */5 * * * *`).
기능명세 §7.3 은 "포인트를 획득하면 **실시간으로** 포인트와 게이지 바가 변경" 을 요구한다.
배치 주기만큼 늦게 오르는 게이지는 그 요구를 만족하지 않는다.

### 랭킹이 배치인 이유는 등급에 적용되지 않는다

ADR-0028 이 배치를 고른 근거는 **순위가 전역 집계**라는 것이었다 — "앞에 몇 명이 있는가" 는
회원 전체를 정렬해야 답이 나오고(200k 기준 97.6ms/조각), 인덱스로 줄일 수 있는 비용이 아니다.

**등급의 입력값은 전역 집계가 아니다.** 둘 다 `user_id` 하나로 좁혀지는 로컬 집계이고,
그 선행 컬럼을 가진 인덱스가 V3 에 이미 있다.

| 입력값 | 쿼리 | 쓰이는 인덱스 (V3) |
|---|---|---|
| 누적 포인트 | `SUM(amount) WHERE user_id = ?` | `idx_point_user_created (user_id, created_at DESC)` |
| 누적 투표 횟수 | `COUNT(*) WHERE user_id = ?` | `idx_vote_user_created (user_id, created_at)` |

한 사람이 가진 행 수만 읽는다. 배치를 정당화한 Θ(전체 회원 수) 가 여기엔 없다.

### 누적 투표 횟수에서 재투표가 빠지는 것은 스키마가 이미 지킨다

R-22 는 재투표가 누적 투표 횟수를 늘리지 않는다고 정한다. 이 규칙을 위해 쿼리에
따로 조건을 달 필요가 없다 — `vote` 테이블에 `UNIQUE KEY uk_vote_post_user (post_id, user_id)`
가 걸려 있어 **한 사람이 한 게시글에 가질 수 있는 행이 최대 1개**이고,
`VoteService.changeChoice()` 는 선택 변경을 UPDATE 로 처리한다(새 INSERT 가 없다).

곧 `COUNT(*) WHERE user_id = ?` 는 **행을 세는 것만으로 이미 사람 단위**다.
재투표를 빼는 별도 조건은 중복 방어가 된다.

## 결정

### 1. 승급 판정의 입력값은 캐시가 아니라 원장에서 읽는다

`users.point` · `users.vote_count` 를 읽지 않는다. 조회 시점에
`point_history` 와 `vote` 에서 직접 집계한다.

R-14 가 이미 정한 위치를 그대로 따르는 것이다 — **저장된 포인트는 캐시이고 원장이 근거다.**
등급은 사용자에게 보이는 판정이므로 근거 쪽을 읽는다.

`users.vote_count` 는 **이 작업에서 채우지 않고 그대로 둔다.** 아무도 읽지 않는 컬럼이라
비어 있어도 지금 깨지는 것이 없고, 채우기로 하면 지급 경로에 쓰기가 하나 더 붙는다.
컬럼을 지우지도 않는다 — 뱃지(#27)가 같은 입력값을 쓰므로 그쪽 결정과 함께 정리할 자리다.

### 2. 등급 기준은 코드 enum 이 소유한다. 기준 테이블을 만들지 않는다

`Grade` enum 이 LV.1~LV.5 와 각자의 임계값을 들고, 판정은 그 안의 순수 함수다.

**임계값을 DB 에 두면 정본이 둘이 된다.** `docs/requirement/README.md` 의 정본 위계에서
수치의 정본은 정책 요약표다. DB 행은 그 복제본이 되고, 복제본은 어긋날 수 있다 —
기획이 임계값을 바꾸면 코드 배포와 데이터 마이그레이션이 따로 놀 여지가 생긴다.
5개 고정값이고 릴리스 주기에 묶여 있으므로 코드가 정본에 더 가깝다.

### 3. 도달한 최고 등급만 저장한다 (`users.highest_grade`)

R-16(등급은 내려가지 않는다)을 위해 **도달 사실**을 남긴다.
계산값과 저장값 중 **높은 쪽**이 현재 등급이다.

오늘 이 컬럼은 아무 차이를 만들지 않는다. 포인트가 줄어들 경로가 없기 때문이다 —
`PointReason` 은 `PICKED(+10)` · `PICKING(+5)` 둘 다 양수이고, 원장에 삭제 경로가 없으며,
R-06 이 원픽 취소를 금지해 재지급·회수가 생길 자리도 없다. 즉 **계산값은 단조 증가**다.

그럼에도 저장하는 이유는 **R-16 을 우연이 아니라 명시로 만들기 위해서다.**
저장하지 않으면 R-16 은 "회수 경로가 없어서 저절로 참" 인 상태로 남고, 회수가 생기는 날
등급이 조용히 내려간다. 컴파일도 통과하고 테스트도 초록인 채로 — 이 저장소가
`users.point` 에서 이미 한 번 겪은 실패 형태다.

이슈 #25 의 완료 판정이 이 지점을 정확히 겨눈다: **"포인트가 줄어도 등급이 내려가지 않음"**.
저장 없이는 이 판정을 **검증할 수단 자체가 없다** — 차감해도 계산값이 그냥 따라 내려가므로
테스트가 무엇을 확인하는지 말할 수 없다. 검증 가능한 불변식으로 만들려면 저장이 필요하다.

## 결과

### 얻는 것

- 포인트를 얻는 즉시 게이지와 등급이 움직인다(§7.3). 배치 주기를 기다리지 않는다.
- 승급 판정이 **아무도 채우지 않는 컬럼에 의존하지 않는다.** 기능이 조용히 죽는 경로를 지운다.
- R-16 이 테스트로 확인 가능한 불변식이 된다.
- 임계값의 정본이 하나다.

### 대가

- **조회마다 집계 쿼리 2회가 붙는다.** 한 사람 몫이라 인덱스 레인지 스캔이지만 공짜는 아니다.
  이 비용이 문제가 되는 지점은 **한 사람이 가진 행 수가 커질 때**다 — 투표 1,000회가
  LV.5 조건이므로 상위 사용자는 `vote` 에 네 자리 행을 갖는다. `COUNT(*)` 는 그 만큼을 훑는다.
  지금 규모에서 측정할 값이 아니라고 판단해 미룬다. 필요해지면 그때
  `users.vote_count` 를 되살리는 것이 정석적인 다음 수다(컬럼을 지우지 않는 이유이기도 하다).
- **`users.highest_grade` 는 오늘 아무 일도 하지 않는다.** 회수 정책이 오기 전까지
  계산값과 항상 같다. 죽은 컬럼처럼 보이는 대가를 치르고 R-16 의 명시성을 얻는다.
- **승급 시점에 쓰기가 생긴다.** 조회가 순수 읽기가 아니게 된다 — 등급이 올랐으면
  `highest_grade` 를 갱신해야 하므로. 갱신은 **오를 때만** 일어나므로 정상 상태에서는
  읽기뿐이고, 조건부 UPDATE(`WHERE highest_grade < :level`)라 동시 요청이 겹쳐도
  낮은 값이 높은 값을 덮지 못한다.

### 아직 순위가 없는 회원처럼, 아직 등급이 없는 회원은 없다

`users.highest_grade` 는 `NOT NULL DEFAULT 1` 이다. 정책표가 "LV.1 가입 시 기본 부여" 라고
정했으므로 **미산정 상태가 존재하지 않는다.** ADR-0028 의 `ranking` 이 `NULL`(미산정)을
가진 것과 다르다 — 그쪽은 배치가 채우기 전이라는 시간 구멍이 있지만, 등급은 가입 즉시 확정된다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| **캐시 컬럼(`users.point`·`users.vote_count`)을 읽는다** | `vote_count` 는 아무도 채우지 않아 전원 0 이 되고, `point` 는 5분 낡아 §7.3 의 실시간 요구를 깬다. 두 컬럼을 채우는 일부터 해야 하는데, 그건 등급이 아니라 지급·투표 경로의 변경이다 |
| **등급도 랭킹처럼 배치로 사전 계산한다** | 배치를 고른 근거(전역 집계 Θ(회원 수))가 등급에 없다. 등급은 `user_id` 로 좁혀지는 로컬 집계다. 얻는 것 없이 최대 한 주기의 지연만 사온다 |
| **`grade` 기준 테이블 + `users.grade_id` FK** | 임계값의 정본이 정책 요약표와 DB 두 곳이 된다. 5개 고정값을 릴리스와 분리해 바꿀 요구가 없고, 분리하면 코드 배포와 데이터가 어긋날 여지만 생긴다 |
| **아무것도 저장하지 않고 매번 계산만 한다** | R-16 이 "회수 경로가 없어서 저절로 참" 인 상태로 남는다. 이슈의 완료 판정("포인트가 줄어도 등급 유지")을 검증할 수단이 없어진다 |
| **승급 시점에 이벤트를 발행해 등급을 갱신한다** | 지급 경로(`OnePickService`)에 등급 관심사가 붙는다. #27(뱃지)도 같은 입력값을 쓰므로 지급 경로가 후속 판정의 허브가 된다. 조회 시점 판정이면 각 애그리거트가 자기 안에서 완결된다 |

## 열린 질문

- **회수 정책이 생기면** R-16 을 재검토한다(도메인 모델 "강등" 항목). 이 문서의 `highest_grade` 는
  그때 실제로 일하기 시작한다.
- **투표 행이 많은 사용자의 `COUNT(*)` 비용**은 측정하지 않았다. 등급 조회가 마이페이지 진입에만
  쓰여 호출 빈도가 낮다고 보고 미뤘다. 지표가 나오면 `users.vote_count` 복구를 검토한다.
- **뱃지(#27)와의 중복** — 누적 투표 횟수를 두 애그리거트가 각자 센다. 지금은 각자 완결하는 쪽을
  택했다. 양쪽이 자리 잡은 뒤 공용 조회로 묶을지 판단한다.
