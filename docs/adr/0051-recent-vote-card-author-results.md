# ADR-0051 — 최근 투표 카드는 작성자의 투표 여부와 무관하게 본인 글의 집계를 제공한다

**상태**: Accepted

**관련**: Issue #159·기존 API 누락 검토서 B06, 기능명세서 v0.5 §7.4(이 작업 범위는 v0.4와 동일).
[ADR-0046](0046-post-detail-single-type-with-nested-vote-section.md)의 집계 노출 정책을
**`GET /users/me/posts/recent` 에 한해 보완**한다. 상세의 미투표자 집계 감춤 결정과
랜덤 카드의 기존 정책은 유지하며 ADR-0046 본문은 변경하지 않는다.
[ADR-0049](0049-activity-list-splits-by-type-into-paths-and-response-types.md)의 유형별 활동 목록 계약도 유지한다.

## 맥락

마이페이지의 최근 투표 카드는 최근 7일 안에 본인이 작성한 투표 게시글 최대 10건을 보여준다.
기존 응답은 총 투표 수인 `voteCount` 와 대표 사진인 `thumbnailUrl` 만 가지고 있어
선택지별 득표율과 A/B 상품 사진 두 장을 그릴 수 없다. B06이 지적한 누락은 이 조회 데이터다.

투표 활동 목록은 #157에서 `products`, `options`, `selectedOptionId` 를 추가했지만,
최근 투표 카드는 **내가 작성한 글**이고 투표 활동은 **내가 투표한 글**이다.
작성자는 자기 글에 투표하지 않았을 수 있으므로 투표 활동의 조회자 전제를 그대로 적용할 수 없다.
상세·랜덤 카드의 집계 감춤 정책을 그대로 적용하면 최근 카드에서도 다른 사용자의 투표 결과가 빠진다.

## 결정

### 1. 본인의 최근 투표 카드에서는 미투표 작성자에게도 집계를 제공한다

기존 인증 경로 `GET /users/me/posts/recent` 의 요청·오류 계약을 유지한다.
인증된 회원의 식별자로 **본인이 작성한, 삭제되지 않은 투표 게시글만** 조회하며
`AGREE` 와 `A_B` 만 대상이다. 작성 시각이 요청 시각에서 7일을 뺀 값보다 큰 글을
`createdAt DESC, id DESC` 로 최대 10건 반환한다. 정확히 7일이 지난 글은 제외하고 커서는 두지 않는다.

조회자가 직접 투표했는지와 무관하게 선택지별 `voteCount` 와 `percentage` 를 채운다.
이것은 최근 카드에만 적용하는 작성자 예외다. 다른 사람의 글을 이 경로에서 조회할 수 없으며
상세·랜덤 카드의 미투표자 응답이나 다른 활동 목록의 집계 노출 조건을 넓히지 않는다.

### 2. 최근 카드 전용 응답 타입을 두고 중첩 어휘와 계산을 공유한다

`RecentVotePostItem` 은 기존 `ActivityItem` 의 공통 10필드를 유지한다:
`id`, `type`, `category`, `title`, `description`, `commentCount`, `voteCount`,
`thumbnailUrl`, `createdAt`, `activityAt`. 최상위 `voteCount` 는 **총 투표 수**이고
`activityAt` 은 본인이 작성한 시각이다. `thumbnailUrl` 도 그대로 제공한다.

다음 두 필드만 추가한다.

| 필드 | 원소 | 의미 |
|---|---|---|
| `products` | `VoteActivityProduct(displayOrder, imageUrl)` | 찬반은 대표 상품 사진 1장, A/B는 표시 순서 1·2의 상품 사진 2장 |
| `options` | `VoteActivityOption(optionId, label, displayOrder, voteCount, percentage)` | 표시 순서대로 선택지 2개와 각 선택지의 득표 결과. `label` 은 찬반 라벨이고 A/B는 null |

`selectedOptionId` 는 추가하지 않는다. 작성 카드의 요구 데이터에 내 선택은 없으므로
최근 카드 전용 타입을 사용한다.
중첩 타입은 기존 투표 활동 카드의 상품·선택지 타입을 재사용한다.

득표율은 상세·투표 직후·투표 활동 응답과 같은 `VotePercentage` 로 계산한다.
총 투표 수가 0이면 각 선택지는 0%이고, 그 외에는 가장 가까운 정수 퍼센트로 반올림한다.
선택지마다 반올림하므로 합이 100이 아닐 수 있다. 저장소는 집계값을 조회하고
퍼센트 변환은 응답 경계에서 수행한다.

### 3. 최근 게시글을 확정한 뒤 상품과 선택지를 배치로 붙인다

기존 최근 게시글 키 조회와 기본 행 조회를 유지하고, #157의 `attachVoteDetail` 로
확정된 게시글 ID 전체에 대해 상품·선택지를 각각 `IN` 조회한다.
결과가 있으면 키·기본 행·상품·선택지의 네 문장이고, 최근 게시글이 없으면 키 조회에서 끝난다.
게시글별 추가 조회나 상품과 선택지를 함께 조인하는 행 증식을 도입하지 않는다.
상품 배치는 검색 API와 같이 `post_product LEFT JOIN item_resource` 로 사진 후보를 읽고,
사진 ID 오름차순에서 상품별 첫 행만 채택한다. 사진이 없는 상품도 null 사진으로 유지한다.
기본 행에서는 대표 사진을 따로 읽지 않고 상품 배치의 표시 순서 1번 사진으로 채운다.
따라서 최근 카드의 네 SQL 문장에는 서브쿼리가 없으며, A 사진이 없어도 B 사진으로 대체하지 않는다.
총 투표 수와 선택지별 득표 수가 같은 시점을 보도록 기존 읽기 트랜잭션의
REPEATABLE READ 스냅샷 전제를 유지한다.
상세·검색 조회와 같은 방식으로 명시적인 READ COMMITTED 이하의 외부 트랜잭션은
조회 전에 거부한다. 격리 수준을 명시하지 않은 경우는 MySQL 기본값을 따른다.

기존 상품·선택지·집계 컬럼을 읽으므로 DB 스키마, 인덱스, Flyway 변경은 없다.

## 결과 (트레이드오프)

- 작성자는 직접 투표하지 않아도 최근 카드에서 본인 글의 결과와 A/B 사진 두 장을 확인할 수 있다.
- 기존 최상위 필드를 유지하는 추가 필드 방식이므로 총 투표 수와 대표 사진을 사용하던 호출자는
  같은 의미의 값을 받는다. 클라이언트는 새 필드와 전용 OpenAPI 스키마를 반영해야 한다.
- 같은 작성자가 최근 카드에서 확인한 결과를 상세에서는 미투표 상태로 감춰 볼 수 있다.
  화면별 노출 정책의 차이를 받아들이고, 이 예외를 최근 카드 경로와 문서에 명시한다.
- 비어 있지 않은 최근 카드 조회는 두 문장에서 네 문장으로 늘어난다. 추가 두 문장은 목록 전체를
  배치로 읽으므로 1건과 10건에서 문장 수가 같다. 사진 후보는 상품당 사진 수만큼 읽은 뒤
  Java에서 첫 행을 선택한다. 이 구조만으로 지연시간 개선을 입증하는 것은 아니다.
- 전용 최상위 응답은 공통 10필드를 반복하지만 최근 카드의 작성자 예외와 투표 활동의
  내 선택 계약을 구분한다. 중첩 DTO·득표율 계산·배치 조립은 공유한다.

## 검토한 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| 기존 응답 유지, 카드마다 상세 API 호출 | 카드 데이터가 목록 응답에서 완결되지 않고 호출이 게시글 수만큼 늘어난다. 미투표 작성자의 상세는 결과를 감추므로 B06 요구도 충족하지 못한다 |
| 최근 카드에서도 투표한 작성자에게만 집계 공개 | 본인이 올린 투표의 결과를 확인하는 화면에서 직접 투표하지 않은 작성자의 결과가 누락된다 |
| 상세·랜덤 카드를 포함해 작성자에게 모두 공개 | B06이 요구한 최근 카드 밖으로 노출 정책을 확대한다. 다른 경로의 기존 감춤 계약을 바꿀 근거가 없다 |
| `VoteActivityItem` 을 최근 카드에도 그대로 사용 | 최근 카드에 필요 없는 `selectedOptionId` 와 투표 활동의 의미를 함께 노출한다. 최상위 타입은 구분하고 중첩 어휘와 계산만 공유한다 |
| 최상위 `voteCount` 를 득표율로 바꾸거나 삭제 | 기존 총 투표 수 계약을 깨고 하나의 숫자로 선택지별 비율도 표현하지 못한다 |
| 상품·선택지를 기본 행에 함께 조인 | A/B의 상품 2개와 선택지 2개가 곱해져 게시글 한 건이 여러 행으로 늘어난다. 별도 배치 조립이 이미 있어 이 중복을 도입할 이유가 없다 |
| 게시글마다 상품·선택지를 따로 조회 | 추가 SQL 문장 수가 카드 수에 비례한다. 확정된 최대 10개 ID를 한 번에 읽을 수 있다 |
