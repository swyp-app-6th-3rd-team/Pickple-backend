# ADR-0040 — 게시글 상세는 단일 응답 타입에 투표 섹션만 중첩하고, 미투표자에게는 집계를 부재로 감춘다

**상태**: Accepted
**관련**: [ADR-0028](0028-author-ranking-precompute.md) 이 "지어낸 값을 내려보내지 않는다" 를,
[ADR-0034](0034-security-requirement-on-authenticated-endpoints.md) 가 인증 표시를,
[ADR-0035](0035-withdrawn-user-central-authorization.md) 가 비활성 신원의 강등을 정했다.
이 문서는 게시글 상세(#20)의 **응답 계약**을 정한다.

## 맥락

기능명세 v0.4 §6.2 는 상세 화면에 작성자 정보(프로필 이미지·닉네임·작성 시간·게시글 유형·등급)와
게시물 정보를 요구하고, §6.3 은 투표 영역(상품 사진·투표 인원 수·상품명·가격·URL)을 요구한다.
**유형에 따라 형태가 달라진다** — 찬반은 설명, A/B 는 주제와 설명, 일반은 제목과 설명이며,
투표 영역은 *"일반 게시글은 존재하지 않는 기능"* 이다.

응답을 ①단일 스키마에 nullable 필드로 둘지 ②유형별로 쪼갤지(oneOf)가 이 사이클의 결정이다.
배포 뒤에는 클라이언트 파싱이 여기 묶이므로 되돌리기가 비싸다.

### 선례가 말하는 것과 말하지 않는 것

이 저장소는 같은 갈림길을 두 번 지났고 두 번 다 ①을 골랐다. 그런데 **근거가 서로 반대다.**

| 위치 | 근거 |
|---|---|
| `PostController.PostListItem` | 쪼개면 파싱 분기가 생기는데 **목록은 세 유형이 섞여 내려오므로** 그 분기가 항목마다 필요해진다 |
| `ActivityController.ActivityItem` | 쪼개면 파싱 분기가 생기는데 **목록은 칩 하나로 한 유형만 담으므로** 그 분기가 쓰이지도 않는다 |

"섞여 있으니까 ①" 과 "안 섞여 있으니까 ①" 이 같은 결론을 냈다. 모순이 아니라,
**적힌 근거가 실제 결정 원리가 아니라는 신호**다. 두 경우의 공통점은 따로 있다 —
유형별로 갈리는 것이 **필드 두 개뿐**이었다(`voteCount`·`thumbnailUrl`).
차이가 두 필드면 쪼개는 비용이 얻는 것보다 크다.

**상세는 차이의 크기가 다르다.** 갈리는 것이 필드 둘이 아니라 **구조 덩어리 하나**다.
`PostType.GENERAL(0, 0, 0)` 이라 `productCount()` 도 `optionCount()` 도 0 이고,
`PostProduct` 의 javadoc 이 못박듯 *"일반 게시글은 이 객체 자체가 만들어지지 않으므로
'사진 없는 상품' 이라는 상태가 없다"*. 일반과 나머지의 차이는 "필드가 null" 이 아니라
**"섹션이 존재하지 않는다"** 이다. 그래서 선례를 그대로 베끼지 않고 다시 판단한다.

### 같은 게이지를 두 경로가 그린다

`VoteController` 의 javadoc 이 남긴 사실이 이 결정을 좌우한다 —
*"카드에서 버튼을 누르면 페이지 이동 없이 결과 게이지로 바뀌므로, 투표 응답이 곧 결과 화면의 데이터다."*

클라이언트는 **같은 게이지 UI** 를 두 경로로 받는다: 상세 진입(`GET /posts/{id}`)과
투표 직후(`POST /posts/{id}/votes`). 두 응답의 투표 영역이 다른 모양이면
같은 게이지를 두 가지로 파싱한다.

## 결정

### 1. 단일 응답 타입을 쓰되, 투표 섹션만 중첩 nullable 객체로 둔다

세 유형이 하나의 스키마다. 클라이언트 분기는 불리언 둘뿐이다 —
`vote == null`(투표 영역을 그리는가)과 `vote.voted`(버튼인가 게이지인가).
찬반과 A/B 는 **분기가 아니라** `products` 배열 길이와 `label`/`productId` 중
어느 쪽이 채워졌는지로 갈린다.

```jsonc
{
  "id": 102, "type": "AGREE", "category": "DIGITAL",
  "title": "무선 이어폰 프로", "description": "사도 될까요?",
  "createdAt": "2026-09-06T11:00:00", "createdAgo": "3시간 전",
  "commentCount": 12,
  "authorId": 9, "authorNickname": "지민",
  "authorProfileImageUrl": "https://…/9.png",
  "authorGradeLevel": 3, "authorGradeName": "LV.3",
  "authorRanking": 88,
  "mine": false,
  "vote": {                       // 일반 게시글이면 null
    "voted": false,               // 상태는 값으로 말한다
    "selectedOptionId": null,
    "voterCount": 87,             // 총 인원은 미투표자에게도 준다
    "products": [ { "id": 501, "name": "…", "price": 219000,
                    "linkUrl": "…", "imageUrl": "…", "displayOrder": 1 } ],
    "options": [                  // 미투표자에게는 voteCount·percentage 가 없다
      { "optionId": 900, "label": "사자", "productId": null, "displayOrder": 1 },
      { "optionId": 901, "label": "말자", "productId": null, "displayOrder": 2 }
    ]
  }
}
```

투표한 사용자면 `options[]` 의 각 원소에 `voteCount`·`percentage` 가 붙고
`voted: true`·`selectedOptionId` 가 채워진다.

**`vote` 는 일반 게시글에서 `null` 로 명시하고 필드를 빼지 않는다.**
투표 없음은 감추는 것이 아니라 **사실**이고, 클라이언트가 유형 분기 없이
`vote == null` 한 줄로 판정하게 하는 편이 단순하다. 필드 부재는 아래 결정 3에서
"자격이 없어 감췄다" 의 표식으로 예약한다 — 두 의미를 같은 표현에 겹치지 않는다.

**`products` 는 `vote` 안에 둔다.** `PostType.productCount() > 0` 과 `hasVoting()` 이
완전히 일치하므로(일반만 0·false) 둘은 같은 조건으로 나타나고 사라진다.
밖에 두면 "`vote` 는 null 인데 `products` 는 빈 배열" 이라는 중복 표현이 생긴다.
§6.3 도 상품 정보와 투표 버튼을 한 기능으로 묶었다.

**작성자는 중첩하지 않는다.** `PostListItem`·`CommentResponse`·`RankingItem` 이
만장일치로 작성자를 평면(`authorId`·`authorNickname`)으로 둔다. 상세에서만
`author.nickname` 이면 목록 → 상세라는 **같은 화면 흐름**에서 클라이언트가
같은 개념을 두 모양으로 다룬다. 비대칭의 기준은 명확하다:

| 섹션 | 통째로 사라지는가 | 내부 컬렉션 | 형태 |
|---|---|---|---|
| 작성자 | 아니오 (항상 있다) | 없음 | 평면 (`author*` 접두사) |
| 투표 | **예** (일반 게시글) | `products[]`·`options[]` | **중첩 nullable** |

`vote.options[]` 는 `VoteController.OptionResponse` 와 같은 모양을 유지하되
**`productId` 하나를 더 갖는다.** 투표 직후에는 상품 카드가 이미 화면에 있어 연결이
필요 없지만, 상세는 A/B 에서 "이 버튼이 어느 상품 카드인가" 를 처음 연결해야 한다.

### 2. 작성 시간은 시각과 문자열을 함께 준다

§6.2 와 §6.4 는 조회 데이터에 *"작성 시간(0분전, 0시간 전, 0일 전, 0년 전으로 통일)"* 을
**같은 문구로** 명시한다. §4.2 목록에는 그 문구가 없다. 그래서 상세는
`PostListItem`(`createdAt` 만)이 아니라 `CommentResponse`(`createdAt` + `createdAgo`)를 따른다.

§6.2 와 §6.4 는 **한 화면**이다 — 게시글 헤더의 "3시간 전" 과 바로 아래 댓글의 "3시간 전" 이
나란히 놓인다. 한쪽만 클라이언트가 포맷하면 같은 화면의 두 시각이 다른 규칙으로 계산되고,
§6.2 가 요구한 "**통일**" 이 깨진다. 시계가 틀린 기기에서 `"-5분 전"` 이 나오는 것도
서버가 포맷하면 한 곳에서 막힌다(`relativeTime` 이 이미 음수를 `ZERO` 로 접는다).

`createdAt` 을 함께 주는 것이 **전환 여지**다. 다국어가 필요해지면 클라이언트가
`createdAgo` 를 무시하면 되고 서버는 필드 하나를 지우면 된다. 이 장치 때문에
이 결정만으로는 ADR 을 따로 쓸 이유가 없어 여기 한 절로 흡수했다.

### 3. 미투표자에게는 `voteCount` 와 `percentage` 를 **둘 다** 뺀다

`percentage` 만 빼고 `voteCount` 를 주면 클라이언트가 `voteCount / voterCount` 로
직접 계산한다. 더 나쁜 것은 **선택지가 정확히 둘(R-04)이고 1인 1표(R-09)라
`voterCount` 와 한쪽 `voteCount` 만으로 나머지가 완전히 복원된다**는 것이다 —
`option2 = voterCount − option1`. R-09 가 이 산술을 정확하게 만든다.
하나만 빼는 것은 보안 연극이므로 둘 다 뺀다.

**`voterCount`(총 투표 인원)는 준다.** §6.3 이 미투표 화면의 조회 데이터로
"투표 인원 수" 를 명시하고, `PostListItem.voteCount` 가 이미 게스트에게 총 인원을 공개한다.
총계 하나만으로는 분해가 결정되지 않는다 — `voterCount = N` 이면 `(0, N)` 부터 `(N, 0)` 까지
모든 조합이 가능하다. 새는 것은 **총계와 한쪽 값의 짝**이지 총계 자체가 아니므로,
막아야 할 것은 선택지별 값이고 총계는 명세대로 공개한다.
(`N = 0` 이면 양쪽이 0 으로 자명해지지만, 그것은 공개하기로 한 총계에서 따라오는 것이지
우회 경로가 아니다.)

**0 으로 채우지 않는다.** ADR-0028 이 같은 판정을 이미 내렸다 —
지어낸 값은 실제 값과 구분되지 않는다. 여기서 `percentage: 0` 은 "아직 자격 없음" 과
"정말 0표" 를 구분 불가능하게 만드는데, `VoteController.OptionResponse` 가
**0 의 의미를 이미 "아무도 투표하지 않았으면 0" 으로 예약했다.**

부재는 `@JsonInclude(NON_NULL)` 을 필드에 명시해서 만든다.
전역 `default-property-inclusion` 설정이 없어 Jackson 기본이 `ALWAYS` 이므로,
붙이지 않으면 `null` 이 그대로 실려 나가 감춤이 조용히 깨진다.
선례는 `RankingController.MyRankingResponse.ranking` 이다.

**`voted` 불리언을 명시적으로 준다.** 필드 부재만으로는 "미투표라 감췄다" 와
"서버가 안 내려줬다" 를 구분할 수 없다. **상태는 값으로 말하고, 감춘 것은 부재로 말한다.**

## 결과

- 클라이언트 파싱 분기가 유형 셋이 아니라 불리언 둘이다. 유형이 늘어도 값이 하나 느는 것으로 끝난다.
- 상세와 `POST /posts/{id}/votes` 의 투표 영역이 같은 모양이라 게이지 렌더링 코드를 공유한다.
- 미투표자가 비율을 역산할 경로가 없다.
- 게스트는 별도 분기 없이 미투표자와 같은 응답을 받는다 — R-11 로 게스트는 투표 이력을
  가질 수 없으므로 `voted: false` 가 기능 저하가 아니라 정확한 답이다.

### 포기한 것

- **목록과 상세의 모양이 완전히 같지는 않다.** 목록은 `voteCount` 가 최상위 평면,
  상세는 `vote.voterCount` 다. 두 화면의 매퍼를 공유할 수 없다.
  **같은 화면 안의 일치**(상세 ↔ 투표 응답)를 화면 간 일치보다 우선한 대가다.
- **`vote.options[]` 가 가변 스키마다.** 같은 배열의 원소가 `voted` 에 따라 필드 둘을
  갖거나 안 갖는다. 강타입 클라이언트는 둘을 optional 로 선언해야 하고,
  OpenAPI 는 "조건부 required" 를 약하게만 표현하므로 `@Schema(description=)` 의
  글로 보완해야 한다 — **문서 서술에 의존하는 부분이 남는다.**
- **`@JsonInclude(NON_NULL)` 이 필드 단위라 누락 가능하다.** 새 필드를 추가하며 빠뜨리면
  감춤이 조용히 깨진다. 통합 테스트가 키 부재를 `doesNotExist()` 로 못박는 이유다.
- **컴파일 타임 보호가 없다.** ②를 골랐다면 "일반 게시글 응답에서 투표 필드 접근" 을
  타입이 막았을 것이다. 런타임 null 검사에 의존한다.
- **`createdAgo` 가 응답을 시간 의존으로 만든다.** ETag·조건부 GET 여지가 사라지지만,
  응답이 이미 `voted`·`voterCount` 로 개인화·휘발성이라 실손실은 없다.

## 검토한 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **완전 평면 + nullable (목록과 동일)** | 목록은 항목 안에 컬렉션이 없어 자연스러웠지만 상세는 선택지 2 × 4필드 + 상품 최대 2 × 5필드다. 평면화하면 `option1Percentage`·`product2Name` 같은 인덱스 접미사가 생겨 **R-04("선택지 정확히 둘")를 필드명에 하드코딩**한다. 규칙이 이름에 새겨지면 규칙이 바뀔 때 계약이 깨진다. 더 큰 문제는 `VoteResponse.options[]` **배열과 모양이 어긋난다**는 것이다 |
| **유형별 분기 (oneOf · 폴리모픽)** | 얻는 것(타입 안전)을 `type` 필드 + nullable 섹션으로 더 싸게 얻는다. ⑴ 저장소에 `@JsonTypeInfo`·`@JsonSubTypes`·`@Schema(oneOf=)` 가 한 줄도 없어 첫 도입이고, 세 문서 표면(Swagger·Scalar·llms.txt)이 같은 스펙을 읽으므로 렌더링 리스크가 3중이다. ⑵ `type` 이 이미 응답에 있어 클라이언트는 어차피 그것으로 분기한다 — oneOf 는 같은 분기를 타입으로 중복 표현할 뿐이다. ⑶ **찬반과 A/B 는 구조가 같다**(배열 길이만 다르다). 실질 2갈래를 위해 폴리모픽 직렬화를 들이는 것은 과설계다 |
| **전면 중첩 (`author`·`content`·`vote` 모두 그룹핑)** | `author` 중첩은 하우스 선례 셋을 만장일치로 거스른다. `content` 그룹핑은 감싸는 값이 `title`·`description` 둘뿐이라 얻는 게 없다. **통째로 사라지는 섹션에만 중첩을 쓴다** |
| **일반 게시글에서 `vote` 필드를 omit** | `null` 이 낫다. `vote == null` 한 줄이 "키가 있는지 확인 후 값 확인" 보다 단순하고, 부재는 결정 3에서 "감춤" 의 표식으로 예약했다 |
| **`products` 를 최상위에 둔다** | `productCount() > 0` 과 `hasVoting()` 이 완전히 일치해 같은 조건으로 나타나고 사라진다. 밖에 두면 "`vote` 는 null 인데 `products` 는 빈 배열" 이라는 모순 가능 표현이 생긴다 |
| **미투표자에게 `percentage` 만 빼고 `voteCount` 는 준다** | R-04 + R-09 로 `option2 = voterCount − option1` 이 **완전히 복원된다.** 감춘 것이 아니라 한 단계 계산을 시킨 것뿐이다 |
| **미투표자에게 `percentage: 0` 을 준다** | "자격 없음" 과 "정말 0표" 가 구분되지 않는다. `VoteController` 가 0 의 의미를 이미 후자로 예약했다(ADR-0028 과 같은 판정) |
| **작성 시간을 `createdAt` 만 주고 클라이언트가 포맷** | §6.2·§6.4 가 "통일" 을 명시하는데 플랫폼 셋이 각자 경계 규칙(0분 전·365일→1년 전)을 재구현하면 그 요구가 깨진다. 기기 시계 오차가 `"-5분 전"` 을 만드는 것도 막지 못한다 |

## 열린 질문

- **게스트의 3표와 게이지 노출.** §6.3 은 게스트에게 3표를 허용하고 이후 로그인 모달을 띄운다.
  R-11 로 그 표는 서버에 남지 않으므로, 게스트가 투표한 뒤 상세를 다시 부르면 `voted: false` 가
  돌아와 게이지가 사라진다. **다만 이는 이 사이클이 만든 문제가 아니다** —
  `POST /posts/{id}/votes` 가 인증 필수라 게스트는 애초에 서버에서 집계를 받지 못한다.
  기본값은 "게스트에게는 게이지를 주지 않는다" 로 두고, 기획이 게스트 게이지를 요구하면
  별도 사이클에서 다룬다.
- **`authorRanking` 의 null 표현.** `PostListItem` 은 `authorRanking: null` 을 그대로 싣고
  `MyRankingResponse` 는 뺀다. 상세는 **목록 쪽(null 노출)에 맞춘다** — 같은 필드명이
  두 API 에서 다르게 동작하면 안 된다. 저장소에 이미 있는 비일관이라 짚어둔다.
