# ADR-0047 — 게시글 수정 요청은 수정 가능한 세 필드만 받는 화이트리스트 스키마이고, 수정·삭제는 행을 잠그고 한다

**상태**: Accepted

**관련**: [ADR-0008](0008-domain-entity-separation.md) 이 도메인과 엔티티의 분리를, [ADR-0019](0019-policy-belongs-above-infrastructure.md) 가
정책의 위치를, [ADR-0034](0034-security-requirement-on-authenticated-endpoints.md) 가 인증 표시를,
[ADR-0039](0039-explicit-http-exception-boundary.md) 가 요청 오류와 내부 오류의 경계를,
[ADR-0046](0046-post-detail-single-type-with-nested-vote-section.md) 이 상세 응답 계약을 정했다.
이 문서는 게시글 수정·삭제(#31)의 **요청 계약**과 **쓰기 경로의 잠금**을 정한다.

## 맥락

§6.1 `[더보기]` 의 "작성자 본인이면 수정/삭제" 분기에 서버 API 가 없다. 이슈는 #32("투표가 시작된 뒤
상품을 수정할 수 있는가")에 막혀 있었고, 기획이 **투표 유무와 무관하게 상품(상품명·가격·URL·사진)은 언제나
불변, 카테고리·주제/제목·설명만 수정 가능**으로 답해 닫혔다(R-33,
[#32 코멘트](https://github.com/swyp-app-6th-3rd-team/Pickple-backend/issues/32#issuecomment-5570120403) 2026-09-07).
유형은 원래부터 불변이다(R-01).

> **정본에 대하여.** 기능명세서 v0.4 §6.1 `[더보기]` 분기는 v0.2·v0.3 과 글자 그대로 같다 — 기획문서 갱신본은 아직 없다.
> 이 결정은 기획 담당자의 코멘트를 근거로 한다. 갱신본이 다르면 갱신본을 따르고 이 문서는 `Superseded` 가 된다.

결정할 것은 둘이다.

1. **상품 필드를 요청 스키마에서 아예 받지 않을 것인가, 받고 거절할 것인가.** 받지 않으면 클라이언트가 보낸 값이
   조용히 무시되고, 받고 거절하면 명시적 실패를 주되 절대 설정할 수 없는 필드가 공개 스키마에 남는다.
   느슨한 계약을 나중에 조이는 것은 하위호환이 깨지는 변경이라 되돌리기 비싸다.
2. **수정·삭제가 경합할 때 무엇이 지키는가.** `PostEntity.deletedAt` 은 카운터와 달리 **보통의 갱신 가능 컬럼**이고
   저장소에 `@DynamicUpdate` 가 없어 Hibernate 의 `UPDATE post` 는 갱신 가능 컬럼 전부를 SET 절에 넣는다.
   `PostStore` 인터페이스가 바뀌는 결정이라 여기서 정한다.

### 코드가 말하는 사실

- `Post.edit(title, description, category)` 가 이미 있고 **유형 파라미터가 없다.** `Post.delete()` 도 있으나
  **호출자가 0곳**이다 — `deleted_at IS NULL` 필터와 `ActivePostGuard` 의 게시글 분기는 지금까지 한 번도 실행된 적 없는
  잠자는 코드다. 이 API 가 그 경로를 처음 깨운다.
- **찬반 게시글의 `title` 은 상품명이다.** `PostService.resolveTitle` 이 작성 시 상품명을 제목으로 쓰고, 상세 응답도
  "찬반=상품명" 으로 내려준다. 세 유형이 한 컬럼을 공유하므로 스키마는 찬반만 골라 막을 수 없다.
- 편집 화면은 작성 폼을 재사용한다(§6.1 "수정 클릭 시 `COM_02_XX` 로 이동"). 클라이언트가 폼 전체를 보낼 가능성이 높다.
- 저장소에 `fail-on-unknown-properties` 설정이 없다. Spring Boot 기본값대로 모르는 키는 무시된다.
- `post.title` 은 `NOT NULL`, `description` 은 nullable 이다. 작성은 빈 설명을 `nullIfBlank` 로 `NULL` 에 정규화한다.
- 댓글은 같은 문제를 이미 풀었다 — `CommentService.findActiveForUpdate` 가 `PESSIMISTIC_WRITE` 로 읽고,
  그 뒤에 404 → 403 → 도메인 전이 → 저장 순서를 밟는다.

## 결정

### 1. 요청 DTO 는 `category` · `title` · `description` 셋뿐이다. 스키마 밖의 키는 무시한다

상품 필드와 `type` 은 계약에 존재하지 않는다. 보내도 바인딩되지 않으며 저장 값이 바뀌지 않는다.
**스키마가 계약을 표현한다** — 상품명·가격·URL·사진·유형의 불변성은 런타임 검사가 아니라 타입으로 보장된다.

무시되는 필드가 **영구히 불변인 것들뿐**이라는 점이 이 선택을 안전하게 만든다. "지금은 무시하지만 나중에 의미를 갖는"
필드가 없으므로 계약이 조용히 바뀔 여지가 없다. 작성 폼을 그대로 보내는 클라이언트도 깨지지 않는다.

대가는 정직하게 적는다: 작성 폼을 재사용한 클라이언트는 상품을 고쳐 보내도 **200 과 함께 그 변경이 조용히 버려진다.**
완화는 둘이다 — `@Operation(description)` 에 "상품 정보와 유형은 이 API 로 바꿀 수 없으며 함께 보내도 무시된다" 를
명시하고, 응답이 저장된 `type`·`category`·`title`·`description` 을 되돌려 줘 클라이언트가 결과를 확인하게 한다.

### 2. 찬반 게시글의 제목 변경은 **도메인이** 거절한다 — 단, 실제로 바뀔 때만

`title` 은 스키마 안에 있으면서 찬반에서는 상품 필드다. 구조적 보장의 틈이며, 여기만 런타임 가드가 필요하다.
판정에 필요한 것이 자기 유형 하나뿐이라 `Post.edit` 에 둔다([계층별 책임](../domain/계층별%20책임.md) —
"애그리거트 하나의 상태 → 도메인"). 규칙이 객체 안에 있으면 그 객체를 쓰는 모든 경로가 자동으로 지킨다.

**같은 값을 다시 보내는 것은 변경이 아니다.** 상세 응답의 `title` 로 채운 편집 폼은 찬반에서 상품명을 그대로 되돌려
보내므로, "제목이 있으면 거절" 로 하면 아무것도 바꾸지 않은 저장이 400 을 먹는다. 현재 제목과 다를 때만 거절한다.
`IllegalArgumentException` → `GlobalExceptionHandler` → `INVALID_REQUEST`(400) 경로를 그대로 탄다.

### 3. 부분 갱신이다. 빈 설명은 비우고, 빈 제목은 무시한다

없거나 `null` 인 필드는 그대로 둔다. `description: ""` 는 **비움**이고 `title: ""` 는 **무시**다 — 비대칭의 근거는
스키마다. `title` 은 `NOT NULL` 이라 비울 수 없고 `description` 은 nullable 이라 비우는 길이 있어야 한다(선택 입력).

정규화(빈 문자열 → `NULL`)는 **서비스**가 한다. 작성의 `nullIfBlank` 가 서비스에 있으므로 같은 필드를 연산에 따라
다른 계층이 정규화하는 일을 만들지 않는다. 도메인은 `edit(...)` 의 "null = 유지" 계약을 지키고, 비움은 별도 동사
`clearDescription()` 으로 표현한다 — 한 파라미터에 "유지" 와 "비움" 두 뜻을 싣지 않는다.

### 4. 수정·삭제는 행을 `PESSIMISTIC_WRITE` 로 잠그고 시작한다

`PostStore.findByIdForUpdate` 를 더한다. `CommentStore.findByIdForUpdate` 와 같은 장치다.

**왜 필요한가.** `deleted_at` 이 보통의 갱신 가능 컬럼이라 다음이 성립한다.

```
T1 수정   BEGIN; SELECT post → deletedAt = NULL 스냅샷
T2 삭제   BEGIN; SELECT; UPDATE post SET deleted_at = now; COMMIT
T1        flush → UPDATE post SET title = …, deleted_at = NULL, …   ← 삭제된 글이 되살아난다
```

`PostEntity.applyState` 의 `if (post.isDeleted() && this.deletedAt == null)` 은 메모리의 필드를 지킬 뿐이고, 그 필드가
이미 낡은 `NULL` 이다. 서비스의 `isDeleted()` 검사도 REPEATABLE READ 스냅샷 위에서는 같은 낡은 값을 본다.
`SELECT … FOR UPDATE` 는 **현재 읽기**라 커밋된 `deleted_at` 을 본다 — 두 번째 트랜잭션은 `isDeleted()` 로 404 를 받는다.

작성자 한 사람만 두 동작을 할 수 있어 발생 가능성은 낮다(기기 둘, 타임아웃 뒤 재시도). 그러나 결과가 "지운 글이 돌아온다" 라
심각하고, 저장소 안에 똑같은 템플릿이 있어 비용이 여섯 줄이다.

순서는 댓글과 같다: **잠금 조회 → 없거나 삭제됨 404 → 작성자 아님 403 → 도메인 전이 → 저장.**
404 가 403 보다 먼저인 것은 지운 글의 존재를 남에게 알리지 않기 위해서다.

### 5. 삭제는 소프트 삭제이며 카운터를 건드리지 않는다. 내 활동 요약은 목록과 같은 필터를 쓴다

`Post.delete()` → `deleted_at`. 행·상품·선택지·투표·댓글은 남는다. `JpaPostStore.save` 경로를 그대로 쓴다 —
`applyState` 는 카테고리·제목·설명·`deleted_at`·`updated_at` 만 쓰고 카운터는 `updatable = false` 라 덮어쓰지 않으며,
`syncChildren` 은 id 가 있는 자식을 건너뛰어 no-op 이고, 복원된 A/B 선택지는 상품 id 로 가리키므로 `verifyPublishable()` 을 통과한다.

**카운터를 줄이지 않는다.** 댓글 삭제가 `comment_count` 를 줄이는 것과 다르다 — 게시글이 조회에서 빠지면 그 카운터를
읽을 곳이 없고(`popularity_score` 는 게시글 행을 통해서만 읽힌다), 복구 경로가 없어 되돌릴 일도 없다.

**내 활동 요약(`ActivityQuerydslRepository.summarize`)의 투표·댓글 수에 `post` 조인과 `deleted_at IS NULL` 을 더한다.**
목록의 키 문장(`keys()`)은 이미 삭제된 글을 빼는데 요약은 활동 테이블만 세고 있어, 삭제가 생기는 순간 "내가 투표한 글 12" 아래
11장이 뜬다. 지금까지는 삭제가 없어 닿지 않던 불일치다. 요약이 목록을 따른다 — 사용자가 보는 것은 카드이지 행이 아니다.

## 결과

- R-01 과 상품 불변은 타입이 보장하고, 찬반 제목만 도메인이 지킨다. 투표 수를 세는 분기가 없다.
- 작성 폼을 그대로 보내는 클라이언트가 깨지지 않는다. 대신 상품 변경이 조용히 버려진다 — 문서와 응답 에코로 완화한다.
- `PostStore` 에 잠금 조회가 하나 는다. 쓰기 경로는 댓글과 같은 모양이라 읽는 사람이 한 패턴만 알면 된다.
- 지운 글의 이미지 컨테이너는 `post_product` 행이 남아 `uk_product_container` 에 계속 잡힌다. **다른 게시글에서 재사용할 수
  없다** — PR #76 리뷰 합의와 일치한다. 객체(S3)도 남는다. 정리 배치는 이 사이클 밖이다.
- 삭제된 글의 하위 자원은 404 가 아니라 **400** 이다(`ActivePostGuard` 가 `INVALID_REQUEST`). 상세는 404, 댓글 목록·투표·댓글·원픽은 400 —
  이 비대칭은 이 사이클이 만든 것이 아니라 드러낸 것이다. 열린 질문에 둔다.
- `Post.delete()` 의 이중 삭제 `IllegalStateException` 은 서비스 경로에서 닿지 않는다(잠금 뒤 `isDeleted()` 가 먼저 404).
  방어 가드로 남기되 정확성의 근거로 삼지 않는다. 닿으면 핸들러가 500 으로 분류한다는 점은 적어 둔다.
- 요약 쿼리의 투표·댓글 수가 게시글 기본 키 조인을 하나씩 얻는다. `eq_ref` 라 활동 수에 비례한 PK 조회이며, 목록 키 문장이
  이미 같은 조인을 한다.

### 포기한 것

- **상품 필드를 보낸 클라이언트에게 명시적 실패를 주지 않는다.** 화면이 폼을 재사용하는 한 400 은 저장 자체를 막는다.
- **`verifyPublishable()` 이 삭제 경로에도 걸린다.** 데이터 수선으로 깨진 게시글은 삭제도 400 이다. 조건부 `UPDATE … WHERE deleted_at IS NULL`
  로 우회할 수 있었으나 애그리거트를 비켜 가므로 택하지 않았다. 실제로 깨진 행이 생기면 그때 다시 본다.
- **낙관적 잠금(`@Version`)을 두지 않는다.** 컬럼 추가와 409 계약이 따라오는데, 경합 주체가 작성자 한 명이라 그 비용을 정당화하지 못한다.

## 검토한 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **상품 필드를 스키마에 두고 400** | 편집 화면이 작성 폼을 재사용한다는 §6.1 과 정면 충돌한다 — 폼을 그대로 보내면 저장이 불가능해져 서버가 클라이언트에 폼 분해를 강제한다. 절대 설정할 수 없는 필드가 공개 스키마에 남아 문서가 거짓말을 한다 |
| **상품 필드를 스키마에 두고 409** | 이 저장소의 409 는 "요청은 옳으나 리소스 상태와 충돌" 이다(`ALREADY_PICKED`·`ITEM_CONTAINER_ALREADY_IN_USE`). 상품 불변은 상태가 아니라 계약이라 투표 수와 무관하게 **항상 같은 답**이다. 상태 의존이 없는데 409 를 쓰면 클라이언트가 재시도할 여지가 있다고 읽는다 |
| **화이트리스트 DTO + `@JsonIgnoreProperties(ignoreUnknown = false)`** | 오탈자와 미래 필드를 구분하지 못해 전방 호환성을 깬다. 이 엔드포인트 하나를 위해 저장소 전역의 역직렬화 관례(모르는 키 무시)를 뒤집는다 |
| **찬반 제목 가드를 서비스에** | 판정에 필요한 것이 `type` 하나라 애그리거트를 넘지 않는다. 서비스에 두면 `Post.edit` 을 직접 부르는 경로(테스트·배치)가 규칙을 비켜 간다 |
| **찬반은 `title` 이 있기만 하면 거절** | 상세로 채운 편집 폼이 상품명을 그대로 되돌려 보내므로 아무것도 안 바꾼 저장이 400 이다. PATCH 는 멱등해야 한다 |
| **`description: null` 을 비움으로** | `title: null` 은 유지인데 `description: null` 만 비움이면 한 API 안에서 `null` 의 뜻이 갈린다. 빈 문자열이 "지웠다" 는 의도를 더 잘 실어 나른다 |
| **잠금 없이 서비스의 `isDeleted()` 검사만** | REPEATABLE READ 스냅샷 위의 검사라 경합에서 낡은 `NULL` 을 보고 `deleted_at` 을 되돌린다. 댓글이 이미 잠금으로 푼 문제를 반쪽만 베끼는 셈이다 |
| **조건부 쓰기 `UPDATE post SET deleted_at = now WHERE id = ? AND deleted_at IS NULL`** | 이중 삭제가 0행으로 자연스럽게 떨어지고 `verifyPublishable()` 결합도 풀리지만, 애그리거트를 비켜 가 `Post.delete()` 가 죽은 코드가 된다. 카운터의 전용 UPDATE 는 원자 증가라는 이유가 있었고 여기엔 그 이유가 없다 |
| **삭제 시 이미지 컨테이너 해제** | #31 코멘트(PR #76 리뷰)가 "지운 글의 이미지는 재사용하지 않는다" 로 정했다. 해제하면 그 합의를 뒤집는다 |
| **삭제 시 카운터 감소** | 읽을 곳이 없다. 게시글 행이 조회에서 빠지므로 카운터가 화면에 닿지 않고, 복구가 없어 되돌릴 일도 없다 |
| **활동 요약은 그대로 두고 문서화만** | 사용자가 보는 숫자다. "12" 아래 11장은 버그로 읽힌다. 조인 비용은 목록 키 문장이 이미 내고 있는 것과 같다 |

## 열린 질문

- **삭제된 글의 하위 자원이 400 인 것.** `ActivePostGuard` 는 "활성 게시글을 찾을 수 없다" 를 `INVALID_REQUEST` 로 낸다.
  상세가 404 인데 그 글의 댓글 목록이 400 이면 클라이언트가 두 코드를 같은 화면("사라진 글")으로 접어야 한다.
  삭제가 사용자 동작이 된 지금 404 가 더 맞을 수 있으나, 세 서비스와 그 테스트가 걸려 있어 이 사이클 밖이다.
- **지운 글의 이미지 객체.** 행과 객체가 영구히 남는다. 정리 배치가 필요해지면 `post.deleted_at` 이 그 기준이다.
- **기획문서 갱신본.** 나오면 §번호를 여기와 PRD-025 에 인용한다. 다르면 이 문서를 대체한다.
