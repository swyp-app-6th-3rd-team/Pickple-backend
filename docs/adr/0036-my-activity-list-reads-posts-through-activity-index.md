# ADR-0036 — 내 활동 목록은 활동 인덱스로 게시글을 읽고, 커서는 (활동 시각, 게시글 id) 다

**상태**: Accepted
**관련**: [ADR-0004](0004-spring-data-paging-types.md) 가 커서 타입을,
[ADR-0034](0034-security-requirement-on-authenticated-endpoints.md) 가 인증 표시를 정했다.
이 문서는 마이페이지 "내 활동"(#30)의 **읽기 경로**를 정한다.

## 맥락

기능명세 §9.1·§9.2 는 마이페이지에서 활동 유형(투표·댓글·게시글)을 골라
목록을 무한 스크롤로 보게 한다. §7.2 는 그 갯수 요약을, §7.4 는 7일 이내에
올린 투표를 요구한다.

착수 시점의 가정은 **"세 활동이 각기 다른 테이블이므로 UNION 이 필요하다"** 였다.
그렇다면 테이블마다 독립된 `id` 시퀀스 때문에 커서에 판별자를 더해야 하고,
UNION 결과에는 인덱스가 서지 않아 정렬이 filesort 로 떨어진다.

**그 가정이 틀렸다.** 명세를 다시 읽고 확인한 것이 이 문서의 출발점이다.

### 목록의 항목은 활동이 아니라 게시글이다

§9.2 의 조회 데이터는 세 유형 모두 같다 —
"게시글 유형 / 상품명 / 설명 / 댓글 수 / 투표 수 / 작성 시간 / 상품 사진".
카드를 탭하면 게시글 상세(`COM_03`)로 간다. 즉 화면에 놓이는 것은
**내 활동이 향한 게시글**이지 활동 행이 아니다.

§9.1 은 한 걸음 더 나간다 — "마이페이지 메인화면에서 어떤 유형을 탭해서
들어왔는지에 따라 **기본 칩이 변경**". **칩은 항상 하나가 활성이고 "전체" 가 없다.**
요약 화면에서 세 영역 중 하나를 눌러야 목록에 닿으므로, 유형 없는 상태는
화면 흐름에 존재하지 않는다.

두 사실을 합치면 활동 유형이 가르는 것은 **결과의 모양이 아니라
게시글을 좁히는 조건**이다. UNION 이 필요 없다.

## 결정

### 1. 목록은 활동 테이블에서 시작해 게시글을 붙인다

```sql
FROM vote v JOIN post p ON p.id = v.post_id AND p.deleted_at IS NULL
WHERE v.user_id = ?
```

`post` 에서 시작해 `EXISTS` 로 좁히지 않는다. 내 활동은 전체 게시글의 극히 일부라
방향이 결정적이다 — 활동 테이블의 `(user_id, …)` 인덱스가 먼저 서야 한다.

`COMMENT` 는 `comment` 가 아니라 **`post_commenter`** 를 읽는다. 그 테이블은
`UNIQUE(post_id, user_id)` 로 게시글당 정확히 한 행이라(R-25) 한 글에 댓글을
여러 개 단 경우에도 목록에 한 번만 나온다. `comment` 로 읽으면 같은 글이
여러 번 나오고, `DISTINCT` 를 걸면 커서가 가리키는 행이 사라진다.

### 2. 커서는 `(활동 시각, 게시글 id)` 이고, 두 값 모두 활동 테이블에서 읽는다

정렬 키는 **내 활동 시각**이다. 게시글 작성 시각이 아니다.
화면 이름이 "나의 활동" 이고, 어제 올라온 글에 방금 단 댓글이 맨 위에 와야
사용자가 그것을 다시 찾는다.

튜플의 두 번째 자리도 활동 테이블에서 읽는다(`v.post_id`, `p.id` 가 아니라).
**값은 같지만 어느 테이블에서 읽느냐가 실행계획을 가른다** — 아래 실측 참조.

### 3. 정렬 인덱스를 새로 건다 (V11)

```sql
ALTER TABLE vote            ADD KEY idx_vote_user_activity      (user_id, created_at DESC, post_id DESC);
ALTER TABLE post_commenter  ADD KEY idx_commenter_user_activity (user_id, created_at DESC, post_id DESC);
```

`POST` 유형은 기존 `idx_post_user (user_id, deleted_at, created_at DESC)` 로 족하다.
§7.4 의 7일 이내 조회도 이 인덱스가 `Index range scan` 으로 받는다.

### 4. 요약은 스키마가 이미 세어둔 값을 읽는다

```sql
SELECT (SELECT COUNT(*) FROM vote           WHERE user_id = ?),
       (SELECT COUNT(*) FROM post_commenter WHERE user_id = ?),
       (SELECT COUNT(*) FROM post           WHERE user_id = ? AND deleted_at IS NULL)
```

**`DISTINCT` 가 없다.** `vote` 는 `UNIQUE(post_id, user_id)` 라 재투표가 INSERT 가
아니라 UPDATE 이고(R-22), `post_commenter` 는 같은 키로 게시글당 한 행이다(R-25).
**스키마가 이미 인원으로 세고 있으므로 조회가 다시 세면 정본이 둘이 된다.**
등급 판정(`JpaGradeStore.READ_INPUTS`)이 같은 셈법을 쓰고 있어, 다시 세면
마이페이지의 두 숫자가 어긋난다.

## 실측 — 게시글 100,000 · 투표 200,000 · 댓글작성자 200,000 · 회원 20,000 · MySQL 8.4

활동 500건을 가진 회원의 첫 조각(`LIMIT 11`)에 `EXPLAIN ANALYZE` 를 걸었다.

| 조회 형태 | 시간 | 실행계획이 말하는 것 |
|---|---|---|
| 투표 최신순 · `ORDER BY p.id` · `idx_vote_user_created` | 4.29 ms | `Sort` + 내 활동 **500행** 전량 |
| 투표 최신순 · `ORDER BY v.post_id` · 인덱스 그대로 | 0.335 ms | `Sort` 는 남지만 조인이 11번으로 줄었다 |
| 투표 최신순 · `ORDER BY v.post_id` · **`idx_vote_user_activity`** | **0.070 ms** | `Covering index lookup` **11행**. 정렬 없음 |
| 댓글 최신순 · `fk_commenter_user (user_id)` | 0.606 ms | `Sort` + **500행** |
| 댓글 최신순 · **`idx_commenter_user_activity`** | **0.035 ms** | `Covering index lookup` **11행** |

**속도보다 읽는 행 수가 중요하다.** 같은 회원의 활동을 5,000건으로 늘려 다시 쟀다.

| 활동 수 | 최신순: 읽는 행 | 인기순: 읽는 행 |
|---|---|---|
| 500 | 11 (0.070 ms) | 500 (15.8 ms) |
| 5,000 | **11** (1.16 ms) | **5,011** (10.5 ms) |

최신순은 활동이 10배가 되어도 11행이다 — 인덱스가 정렬을 통째로 맡는다.

**`p.id` 와 `v.post_id` 의 차이가 여기서 드러난다.** 값이 같은데도 `p.id` 로 쓰면
정렬 키 둘이 서로 다른 테이블에 있어 인덱스 하나로 정렬이 완결되지 않고,
MySQL 이 내 활동을 전부 읽어 정렬한다. 한 글자가 Θ(내 활동 수) 와
Θ(조각 크기) 를 가른다.

## 결과 (트레이드오프)

### 인기순은 Θ(내 활동 수) 로 남는다 — 의도한 한계다

정렬 키 `post.popularity_score` 는 활동 테이블에 없다. 조인해야만 알 수 있으므로
"내 활동" 으로 좁힌 집합 전체의 점수를 읽어야 정렬이 선다.
**인덱스로 해결할 수 없는 구조적 한계**이며, 5,000건에서 5,011행 · 10.5 ms 다.

받아들이는 이유:
- 활동 수는 사람이 손으로 만드는 값이라 상한이 낮다(5,000 투표 = 하루 10개씩 500일).
- 10 ms 는 화면 응답으로 견딘다.
- 대안인 **비정규화를 기각**했다 — `popularity_score` 는 남의 투표·댓글로 계속
  변하므로 활동 행에 복사해두면 게시글 하나가 갱신될 때 그 글에 활동한
  모든 사람의 행을 고쳐야 한다. 읽기 10 ms 를 아끼려고 쓰기를 폭발시킨다.

### 커서는 정렬 방향을 바꾸면 되감긴다

최신순과 오래된순은 같은 커서 키(`activityAt`)를 쓰고 부등호만 뒤집는다.
스크롤 도중 방향을 바꾸면 커서가 형식상 통과하고 **왔던 길을 되돌아간다.**
틀린 데이터는 아니다. 방향 전환은 화면이 처음부터 다시 읽는 동작이라
커서를 버리고 보내므로 실제로 일어나지 않는다.

### 게시글이 지워지면 목록에서 사라진다

조인 조건에 `p.deleted_at IS NULL` 을 두었다. 내가 투표한 글을 작성자가 지웠다면
그 카드는 탭했을 때 갈 곳이 없다. 요약의 `voteCount` 는 `vote` 행을 세므로
삭제된 글의 투표도 포함되어 **요약과 목록 길이가 어긋날 수 있다** —
요약은 "내가 한 활동" 이고 목록은 "지금 볼 수 있는 글" 이라 세는 대상이 다르다.

## 검토한 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **세 테이블 UNION 후 정렬** | 목록 항목이 게시글이라 애초에 불필요하다. 게다가 테이블마다 `id` 시퀀스가 독립이라 커서에 판별자를 더해야 하고, UNION 결과에는 인덱스가 서지 않아 filesort 가 확정된다 |
| **`post` 에서 시작해 `EXISTS` 로 좁히기** | 내 활동은 전체 게시글의 극히 일부다. 게시글 전체를 훑게 되어 인덱스가 무의미해진다 |
| **`COMMENT` 를 `comment` 테이블로 읽기** | 한 글에 댓글을 여러 개 달면 같은 글이 여러 번 나온다. `DISTINCT` 는 커서가 가리키는 행을 지워 조각 경계를 깨뜨린다. `post_commenter` 가 이미 게시글당 한 행이다 |
| **`PostSort` 에 `OLDEST` 를 추가해 재사용** | 공개 목록 `GET /posts` 의 계약이 조용히 넓어진다. 게다가 오래된순은 keyset 부등호와 `ORDER BY` 방향이 함께 뒤집히는 **새 축**이라 값 하나를 얹는 일이 아니다 |
| **활동 행에 `popularity_score` 비정규화** | 점수가 남의 활동으로 계속 변한다. 읽기 10 ms 를 아끼려고 게시글 갱신마다 활동 행 전체를 고치게 된다 |
| **정렬 키를 게시글 작성 시각으로** | 화면이 "나의 활동" 이다. 어제 글에 방금 단 댓글이 목록 아래로 밀려 다시 찾을 수 없다. 인덱스도 활동 시각 쪽에 놓여 있어 스키마 설계자의 의도와 어긋난다 |
| **게스트에게 0 을 응답** | 세 엔드포인트가 모두 인증을 요구하므로 게스트는 도달하지 않는다. 명세의 "0개로 고정" 은 같은 문단의 "클릭 제한" 과 짝이라 **로그인하지 않은 화면의 플레이스홀더**다. 서버가 0 을 주면 "활동 없는 회원" 과 "비로그인" 이 같은 응답이 되어 화면이 둘을 구분하지 못한다 |
