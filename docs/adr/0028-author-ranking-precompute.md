# ADR-0028 — 작성자 랭킹은 배치로 사전 계산하고 목록은 그 값을 읽는다

**상태**: Accepted
**보완**: [ADR-0004](0004-spring-data-paging-types.md) 위에 선 게시글 목록 조회(#19)가
"작성자 랭킹은 조회 시점에 구할 수 없다"고 남긴 미결 항목을 이 문서가 채운다.
조각을 먼저 확정하고 나중에 조인한다는 목록 쿼리의 형태는 그대로 유지된다.

## 맥락

게시글 목록(`GET /api/posts`)에 작성자의 TOP 피커 순위를 함께 내려야 한다.
랭킹의 정의는 이미 정본이 있다 — 용어사전의 "랭킹" 항목과 V3 의
`idx_users_ranking (point DESC, created_at)` 이 같은 것을 말한다:
**포인트 내림차순, 동점이면 가입이 빠른 쪽이 앞선다.**

#19 에서 조회 시점 계산을 시도했다가 비용 때문에 랭킹 필드 없이 닫았다.
이 작업은 그 측정값에서 출발한다. 같은 규모(회원 200,000 · 게시글 100,000)를
로컬 MySQL 8.4 에 시드해 `EXPLAIN ANALYZE` 로 재현했다.

| 방식 | 한 조각(LIMIT 11) | 실행계획이 말하는 것 |
|---|---|---|
| 랭킹 없음(현행) | 0.123 ms | `idx_post_latest_all` 에서 11행 → PK 조인 |
| 윈도 `RANK() OVER` 조인 | 97.6 ms | `Materialize rows=200000` — 11건을 위해 20만 명 순위를 전부 만든다 |
| 상관 서브쿼리 `COUNT(*)` | 26.4 ms × `loops=11` ≈ 290 ms | 조각의 행마다 20만 행을 다시 스캔한다 |

숫자보다 실행계획이 원인을 정확히 말한다. **순위는 "앞에 몇 명이 있는가" 라서
본질적으로 전역 집계다.** B+트리 인덱스는 *순서*를 주지만 *몇 번째인가*는 주지 않는다.
`idx_users_ranking` 이 covering index 로 걸려 테이블 접근이 사라진 뒤에도
20만 행 정렬과 윈도 집계는 그대로 남는다. 인덱스를 더 손봐서 줄일 수 있는 비용이 아니다.

곧, **조회 시점에 세는 한 어떤 쿼리 형태를 골라도 Θ(전체 회원 수)** 다.
남은 결정은 "언제 계산해 둘 것인가" 뿐이다.

### 전제 하나가 아직 비어 있다 — `users.point` 는 아무도 채우지 않는다

설계에 들어가기 전에 확인한 사실이다. `users.point` 컬럼은 V3 에 있지만
(`INT UNSIGNED NOT NULL DEFAULT 0`, 주석은 "point_history 합계"),
**애플리케이션 어디도 이 컬럼에 쓰지 않는다.** `UserEntity` 는 이 필드를 매핑조차 하지 않는다.
포인트의 정본은 원장이다 — `PointHistoryStore.sumByUser()` 의 주석이
"저장된 값이 아니라 원장의 합계다 (R-14)" 라고 못박고 있고, 실제 지급 경로인
`OnePickService.pick()` 은 `point_history` 에 행을 넣을 뿐 `users.point` 를 건드리지 않는다.

그래서 오늘 이 스키마에서 모든 회원의 `point` 는 0 이다.
랭킹을 `users.point` 에서 유도하도록 짜면 **영원히 동작하지 않는 코드**가 된다.
집계의 출발점은 `point_history` 여야 한다.

## 결정

**`users.ranking` 컬럼을 두고, 주기적 배치가 `point_history` 원장에서 전체를 재계산한다.
목록 조회는 이미 하고 있는 작성자 조인에서 그 값을 함께 읽는다.**

선택지 중 **B(주기적 배치)** 다. 구체적으로:

- `users` 에 `ranking INT UNSIGNED NULL` 을 추가한다. `NULL` 은 "아직 산정되지 않음" 이고,
  그대로 응답에 실려 나간다(§결과의 "아직 순위가 없는 회원" 참고).
- 배치는 두 단계다. 먼저 원장 합계를 `users.point` 에 반영하고
  (R-14 의 정본은 원장이므로 `users.point` 는 그 **캐시**라는 위치가 여기서 확정된다),
  그다음 `users.point` 기준으로 `ranking` 을 매긴다.
- 순위 함수는 `ROW_NUMBER() OVER (ORDER BY point DESC, created_at ASC, id ASC)` 다.
  `RANK()` 가 아니다 — 아래 "동점 처리" 참고.
- **변경된 행만 쓴다.** `WHERE u.ranking IS NULL OR u.ranking <> r.rk` 를 붙인다.
- 주기는 5분. 곧 **랭킹의 지연 상한은 5분**이고, 이것이 응답의 계약이다.
- 배치는 활성 회원(`state = 'ACTIVE'`)만 매긴다. 탈퇴자는 `ranking` 을 `NULL` 로 되돌린다.

### 동점 처리 — `RANK()` 가 아니라 `ROW_NUMBER()`

용어사전은 "동점이면 가입이 빠른 쪽이 **앞선다**" 라고 쓴다. 한쪽이 다른 쪽보다
*앞선다*는 것은 공동 순위가 아니라 **전순서**를 말한다. `RANK()` 는 동점에 같은 번호를 주고
다음을 건너뛰므로(1, 1, 3) 이 문장과 어긋난다.

시드 데이터에서 확인한 것: 포인트 동점자는 실제로 많다(0점 11,694명).
그런데 `(point, created_at)` 쌍의 중복은 **0건**이라 정렬키만으로 이미 전순서가 선다.
즉 오늘 데이터에서는 두 함수의 결과가 같고, 갈리는 것은 *미래의 실패 모드* 뿐이다 —
같은 초에 가입한 두 회원의 포인트가 같아지는 순간. 그때 공동 1위를 만들지 않으려면
`ROW_NUMBER()` 여야 한다. `id ASC` 를 마지막 정렬키로 덧붙여 그 경우에도
실행마다 순위가 흔들리지 않게 못박는다.

## 결과

**얻는 것.** 목록 조회에 랭킹이 실려도 비용이 늘지 않는다.

| | 이전 | 이후 |
|---|---|---|
| 목록 한 조각 + 랭킹 | 97.6 ms (윈도 함수) | **0.158 ms** (사전 계산 컬럼) |

실행계획이 랭킹 없던 때와 **같다**. 작성자 조인은 원래도 `Single-row index lookup on u
using PRIMARY` 로 이미 그 행을 읽고 있었고, `ranking` 은 그 행에 얹혀 따라올 뿐이라
추가 접근이 없다. 목록 쿼리가 "조각을 먼저 확정하고 나중에 조인" 하는 형태였던 것이
여기서 배당금을 낸다 — 조인이 이미 11행으로 좁혀진 뒤에 일어나기 때문이다.

**치르는 비용 — 순위가 최대 5분 낡는다.** 이것이 이 결정의 본질적인 대가다.
원픽으로 포인트를 받은 직후 목록을 보면 순위는 아직 이전 값이다.
랭킹을 "지금 이 순간의 정확한 등수" 로 읽는 화면이 있다면 이 결정은 맞지 않는다(§열린 질문).

**배치 비용은 예측 가능하고, 변동이 없으면 거의 쓰지 않는다.**

| 배치 형태 | 시간 | 기록된 행 |
|---|---|---|
| 무조건 `UPDATE` | 537~561 ms | 200,000 |
| 변경분만, 변동 없을 때 | 233 ms | **0** |
| 변경분만, 1명이 최상위로 점프한 뒤 | 553 ms | 75,747 |

`WHERE ranking <> rk` 한 줄이 정상 상태의 쓰기를 0 으로 만든다. 이게 없으면
아무 일이 없어도 5분마다 20만 행을 다시 써서 redo·undo·binlog 를 만들고,
그 부담이 로그인 경로가 함께 쓰는 `users` 테이블에 계속 얹힌다.
읽기 전용 스캔 233 ms 는 5분 주기에서 무시할 수 있다.

**감수한 위험 — 배치가 죽으면 조용하다.** 랭킹이 갱신되지 않아도 목록 조회는
정상 응답한다. 낡은 순위가 그대로 나갈 뿐이라 헬스체크로는 드러나지 않는다.
배치가 마지막으로 성공한 시각을 로그로 남겨 이 실패가 보이게 한다.
(모니터링 경보까지는 6주 MVP 범위 밖으로 둔다.)

**아직 순위가 없는 회원은 `null` 이다.** 가입 직후 다음 배치까지, 그리고 탈퇴 후에는
`ranking` 이 `null` 이다. 응답에서 이 필드는 nullable 이며, 화면은 "-" 등으로 비운다.
0 이나 "전체 회원 수 + 1" 같은 가짜 값을 만들지 않는다 — 지어낸 순위는
"실제로 꼴찌" 와 구분되지 않는다.

**전환 여지.** `ranking` 은 유도된 값이고 정본이 아니다(정본은 `point_history`).
언제든 지우고 다시 계산할 수 있으며, 주기를 바꾸는 것은 설정 한 줄이다.
아래 C 안(구간·티어)으로 옮기더라도 같은 배치가 구간을 계산하면 되므로
이 결정이 C 를 막지 않는다.

## 열린 질문 — 화면이 정확한 등수를 정말 필요로 하는가 (미해결)

이슈가 명시적으로 남긴 질문이고, **기획 확인 없이는 답할 수 없어 열어 둔 채로 진행한다.**
확인된 것처럼 쓰지 않는다.

정확한 등수(`1,234위`) 대신 구간(`상위 5%`·티어)만 노출해도 충분하다면 C 안이 더 낫다.
구간은 경계를 넘을 때만 바뀌므로 배치 주기를 훨씬 늘릴 수 있고, 순위 변동에 따른
쓰기 폭(위에서 측정한 75,747행)이 대부분 사라진다.

**기획 답변에 따라 뒤집히는 부분은 여기다.**

| 뒤집히는 것 | 남는 것 |
|---|---|
| 응답 필드 `authorRanking`(정수 등수) → `authorTier`/`authorPercentile` | 목록 조회가 사전 계산 값을 **읽기만 한다**는 구조 |
| 배치 주기 5분 → 훨씬 길게(예: 1시간·1일) | 배치가 `point_history` 원장에서 유도한다는 방향 |
| `ROW_NUMBER()` 전순서 → 구간 경계 계산 | `users` 에 유도 컬럼을 두고 읽기 경로는 조인으로 얹는다는 형태 |

곧 **뒤집히는 것은 표현(무엇을 보여주는가)이고, 남는 것은 구조(언제 계산하는가)** 다.
C 로 가더라도 이 ADR 의 배치·컬럼 구조는 재사용된다. 그래서 기획 답변을 기다리며
멈추는 대신 B 로 진행하되, 표현을 바꾸기 쉬운 형태로 둔다.

또 하나 열린 채로 둔다: **랭킹을 몇 위까지 의미 있게 볼 것인가.**
20만 명 중 187,432위 가 화면에서 어떤 의미인지는 기획 판단이다. 서버는 전 회원에게
순위를 매기지만, 특정 순위 아래를 감추는 것은 화면의 선택으로 남긴다.

## 검토한 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **A. 포인트 변동 시점에 즉시 갱신** | 순위는 전역 값이라 한 명의 포인트가 오르면 그 사람만 바뀌는 게 아니라 **밀려난 사람 전부**가 바뀐다. 측정으로 확인했다 — 회원 1명이 최상위로 점프하자 **75,747행**(전체의 38%)의 순위가 이동했다. 이걸 `OnePickService.pick()` 트랜잭션 안에서 하면 사용자가 버튼 하나를 누르는 동안 550 ms 짜리 대량 UPDATE 가 붙고, 그동안 `users` 행 락을 로그인 경로와 함께 잡는다. 정확도를 위해 쓰기 경로를 인질로 잡는 거래다 |
| **C. 구간·티어만 노출** | 기각이 아니라 **판정 보류**다. 갱신 비용은 확실히 더 낮지만, 정확한 등수를 버려도 되는지는 기획이 답할 질문이고 아직 답이 없다(§열린 질문). 확인 없이 표현을 축소하면 되돌릴 때 API 계약이 다시 깨진다. B 의 구조가 C 를 그대로 수용하므로, 지금 B 로 두고 답이 오면 표현만 바꾸는 편이 되돌리기 싸다 |
| **조회 시점 계산을 인덱스로 최적화** | 실행계획이 불가능하다고 말한다. `idx_users_ranking` 이 이미 covering index 로 걸려 테이블 접근이 없는 상태인데도 97.6 ms 다. 남은 비용은 20만 행 정렬과 윈도 집계이고, 이건 "앞에 몇 명" 이라는 질문 자체의 비용이라 인덱스로 없앨 수 없다 |
| **랭킹을 Redis 의 Sorted Set 으로** | `ZREVRANK` 가 O(log N) 이라 조회 시점 계산이 실제로 가능해지고 실시간성도 얻는다. 그러나 지금 이 시스템에 Redis 가 없다 — 인프라 한 종을 새로 들이는 결정이고, 원장(MySQL)과 랭킹(Redis)이 갈라지면서 정합성 복구 경로를 따로 만들어야 한다. 목록에 붙는 순위 하나를 위해 치를 비용이 아니다. 실시간 랭킹 화면이 별도로 생기면 그때 다시 꺼낼 대안이다 |
| **MySQL 생성 컬럼(generated column)** | `popularity_score` 처럼 스키마가 계산하게 두는 방식인데, 생성 컬럼은 **같은 행의 값만** 참조할 수 있다. 순위는 다른 행들을 봐야 정해지므로 표현 자체가 불가능하다 |
| **`users.point` 를 원장 대신 정본으로 승격** | 포인트 정본이 원장이라는 것은 R-14 의 결정이고, 멱등키 `(comment_pick_id, reason)` 로 중복 지급을 막는 구조가 그 위에 서 있다. 랭킹 편의를 위해 정본을 옮기면 그 방어가 무너진다. `users.point` 는 원장에서 유도한 **캐시**로만 둔다 |
