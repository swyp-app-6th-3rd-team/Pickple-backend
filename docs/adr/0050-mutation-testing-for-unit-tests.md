# ADR-0050 — 커버리지는 하한선으로 고정하고, 단언 강도는 뮤테이션 점수로 판정한다

**상태**: Accepted

**관련**: [ADR-0008](0008-domain-entity-separation.md) 이 도메인 객체를 JPA 엔티티에서 분리해
도메인 판정 로직을 프레임워크 없이 실행 가능하게 만들어 두었다. 이 문서는 그 위에서
"도메인 판정이 테스트로 실제 보호되는가" 를 측정하는 방법을 정한다.

## 맥락

JaCoCo 플러그인은 이미 적용돼 있고 `test` 가 `jacocoTestReport` 를 `finalizedBy` 로 호출한다.
그런데 **리포트를 만들 뿐 아무도 판정하지 않는다.** `jacocoTestCoverageVerification` 이 없고
CI 는 `build/reports/jacoco` 를 아티팩트로 올리기만 한다. 커버리지가 떨어져도 빌드는 초록이다.

측정한 현재 상태:

| 항목 | 값 |
|---|---|
| LINE | 3,745/4,085 = 91.7% |
| BRANCH | 1,280/1,573 = 81.4% |
| METHOD | 1,029/1,092 = 94.2% |
| 유닛(`*Test`) | 108 suite / 576 test / 34.8초 |
| 통합(`*IT`) | 46 suite / 407 test / 62.8초 |

여기서 두 가지 결핍이 갈린다.

**첫째, 하한선이 없다.** 수치는 이미 높은데 고정돼 있지 않아, 앞으로 들어오는 변경이
조용히 수치를 깎아도 신호가 없다.

**둘째, 커버리지는 단언 강도를 못 본다.** 라인 커버리지는 "그 줄이 실행됐다"까지만 말하고
"그 줄이 틀렸을 때 테스트가 잡는다"는 말하지 않는다. 이 저장소는 판정 로직이 도메인에 몰려 있다
(`Post.verifyPublishable` 의 R-01·R-02·R-04 검증, 유형별 상품 수·선택지 수 판정 등).
이런 코드는 **단언을 지워도 커버리지가 그대로다** — 호출은 여전히 일어나기 때문이다.
커버리지를 아무리 올려도 이 공백은 보이지 않는다.

### 왜 지금까지 안 풀렸나

커버리지 수치가 높아서다. 91.7% 는 "테스트가 충분하다"는 인상을 주고, 그 인상이
"무엇이 측정되지 않는가"를 묻지 못하게 막았다. 지표가 높을 때가 지표의 사각지대를 보기
가장 어려운 시점이다.

## 결정

**1. 커버리지는 현재 실측 바로 아래로 하한선을 박는다.** LINE 0.90 / BRANCH 0.80.
`jacocoTestCoverageVerification` 을 `check` 에 걸어 기존 `build` job 이 그대로 판정한다.
목표치(95/90)가 아니라 **실측 바로 아래**로 잡은 이유는, 이 게이트의 목적이 향상 강제가 아니라
**회귀 차단**이기 때문이다. 도입과 동시에 부채 상환을 강제하면 도입 자체가 막힌다.

제외 대상은 생성된 Q 클래스(`Q*`)·설정·엔트리포인트다 — 판정할 로직이 없어 분모만 키운다.

**2. 단언 강도는 PIT 뮤테이션 점수로 판정한다.** 대상은 도메인·서비스 한정,
테스트는 유닛만. `mutationThreshold = 60`.

**3. 유닛/통합은 클래스명 패턴으로 가른다.** `unitTest` 태스크를 신설하고 `*IT` 를 제외한다.

`app.pickple.support.IntegrationTest` 는 `@Tag` 가 아니라 `@SpringBootTest` 메타 애노테이션이라
JUnit Platform 태그 필터로는 고를 수 없다. 대신 ArchUnit 이
"`@IntegrationTest` 면 이름이 `IT` 로 끝난다"(`ArchitectureTest.TestNaming`)를 이미 강제하므로,
**이름 패턴 제외가 규약으로 보장된다.** 아키텍처 테스트가 네이밍을 지키는 한 이 분리는 새지 않는다.

`user.timezone=Asia/Seoul` 은 `unitTest` 에도 승계한다 — 빠지면 시간 판정이 9시간 밀린다(ADR-0003 맥락).

## 결과 (트레이드오프)

**얻는 것**
- 커버리지 회귀가 빌드에서 막힌다. 사람의 주의력에 맡기지 않는다.
- 단언이 빈 테스트가 점수로 드러난다. "커버리지는 높은데 아무것도 검증하지 않는" 상태가 보인다.
- 유닛 스위트(34.8초)가 통합과 분리돼, Docker 없이 도는 빠른 피드백 경로가 생긴다.

**포기하는 것**
- **CI 시간이 늘어난다.** PIT 는 뮤턴트마다 테스트를 다시 돌리므로 34.8초의 배수로 뛴다.
  실측 후 과도하면 주간 실행으로 내린다.
- **뮤테이션 대상이 좁다.** 컨트롤러·인프라의 단언 강도는 이번 범위 밖이다.
  통합 테스트를 대상에 넣으면 Testcontainers 가 뮤턴트마다 떠서 시간이 폭발한다.
- **임계값 60 은 첫 바닥값이지 목표가 아니다.** 60 을 넘겼다고 테스트가 좋다는 뜻은 아니다.
- 빌드에 도구 의존성이 하나 늘어난다. 다만 dev-time 도구라 플러그인 블록 삭제로 되돌릴 수 있다
  (런타임·스키마 의존이 아니다).

## 검토한 대안과 기각 사유

**A. 커버리지 임계값만 올린다 (95/90). 뮤테이션 도입 안 함.**
기각. 맥락에서 적은 결핍의 **둘째를 전혀 건드리지 못한다.** 단언을 지워도 커버리지는 그대로이므로,
임계를 올리면 "테스트를 늘리는" 게 아니라 "실행되는 줄을 늘리는" 압력만 생긴다.
게다가 현재 91.7/81.4 에서 95/90 은 즉시 실패라, 도입과 동시에 부채 상환을 강제해 도입이 막힌다.

**B. `@Tag("unit")` 을 모든 유닛 테스트에 붙여 태그로 가른다.**
기각. 108개 클래스에 애노테이션을 손으로 붙여야 하고, **새 테스트가 태그를 빠뜨리면 조용히 누락된다.**
반면 `*IT` 네이밍은 ArchUnit 이 이미 강제하고 있어 규약이 자동으로 유지된다.
강제 장치가 있는 규약을 쓰는 쪽이 싸다.

**C. 뮤테이션을 전체 테스트(통합 포함) 대상으로 돌린다.**
기각. Testcontainers 가 뮤턴트마다 MySQL·LocalStack 을 띄운다. 통합 62.8초 × 뮤턴트 수는
CI 예산을 넘는다. 뮤테이션의 목적은 **판정 로직의 단언 강도**이고 그건 도메인·서비스에 있다.

**D. 뮤테이션을 수동 실행(workflow_dispatch)으로만 둔다.**
기각. 아무도 안 돌려서 사문화된다. 이미 JaCoCo 가 "리포트는 있는데 판정이 없어" 방치된 전례가 있다
— 같은 실패를 반복하지 않는다.

**E. gradle-pitest-plugin 을 Maven Central 최신(1.15.0)으로 고정한다.**
기각. 1.15.0 은 2023년판으로 **현재 Gradle 9.2.1 에서 깨진다.**
Maven Central 이 1.15.0 에서 멈춘 것은 플러그인이 Gradle Plugin Portal 자체 저장소
(`plugins.gradle.org/m2`)에 배포되기 때문이고, 포털 기준 최신은 **1.19.0(2026-03-29)** 으로
Gradle 8.4+/9.0 을 지원한다. 저장소 하나만 보고 판단하면 2년 묵은 버전을 고정하게 된다.

### 기술 전제 (확인 완료)

- PIT 는 Java 25 를 지원한다 — 메인테이너 답변, [hcoles/pitest#1439](https://github.com/hcoles/pitest/issues/1439):
  "Pitest support java bytecode versions up [to and] including Java 26."
  이 저장소는 toolchain 25 를 쓰므로 이 확인이 선행 조건이었다.
- PIT 최신 1.30.0, `pitest-junit5-plugin` 1.2.3.
  `junit5PluginVersion` 으로 지정하면 `junit-platform-launcher` 수동 배선이 불필요하다
  (PIT 1.14/플러그인 1.2.0부터 호환 버전을 런타임에 고른다).
