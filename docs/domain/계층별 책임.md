# 계층별 책임 — 규칙을 어디서 지키는가

도메인 규칙(R-01~R-26)을 코드 어디에 둘지 정하는 기준이다.
"어떤 규칙인가"가 아니라 **"판정에 무엇이 필요한가"**로 가른다.

---

## 판정 기준

| 판정에 필요한 것 | 두는 곳 | 예 |
|---|---|---|
| 애그리거트 **하나**의 상태 | **도메인 객체** | R-07 자기 댓글 픽 금지 — 댓글 하나만 알면 된다 |
| 애그리거트 **여럿**의 협력 | **서비스** | R-12 원픽 1건 → 댓글 작성자 +10P, 픽한 사람 +5P |
| **동시성**이 있는 유일성 | **스키마** (UNIQUE·FK) | R-09 중복 투표, R-26 중복 픽 |
| 저장·조회 자체 | **저장소** | 없음 — 정책 판단을 하지 않는다 |

### 왜 이 순서인가

**도메인 객체가 1순위다.** 규칙이 객체 안에 있으면 그 객체를 쓰는 모든 경로가 자동으로 지킨다.
찾을 때도 한 곳만 보면 된다.

**서비스는 도메인이 혼자 판정할 수 없을 때만.** 계층을 늘리는 비용이 있으므로,
"애그리거트 하나로 되나?"를 먼저 물어야 한다. 된다면 서비스로 올리지 않는다.

**스키마는 동시성이 걸릴 때.** "확인한 뒤 삽입"하는 형태가 나오면 그 사이에 틈이 있다.
응용 계층 검증만으로는 동시 요청에서 뚫린다.

---

## 저장소는 정책을 판단하지 않는다

저장소(`Store` 구현)의 일은 **저장과 조회**다. 그 결과를 해석해 정책을 판단하는 것은 위층의 몫이다.

```java
// ✗ 저장소가 정책을 판단한다
public Long save(OnePick pick) {
    try {
        return repository.saveAndFlush(...).getId();
    } catch (DataIntegrityViolationException e) {
        throw new DuplicatePickException(...);   // "이미 픽했다" 는 정책 해석이다
    }
}

// ✓ 저장소는 사실만 알린다
public Optional<Long> saveIfAbsent(OnePick pick) {
    if (repository.existsByUserIdAndCommentId(pick.pickerId(), pick.commentId())) {
        return Optional.empty();       // 삽입되지 않았다는 사실
    }
    return Optional.of(repository.save(...).getId());
}

// ✓ 서비스가 그 사실을 정책으로 해석한다
public void pick(Long commentId, Long pickerId) {
    Comment comment = commentStore.findById(commentId).orElseThrow();
    OnePick pick = comment.pick(pickerId);              // R-07 은 도메인이
    Long pickId = pickStore.saveIfAbsent(pick)
            .orElseThrow(() -> new DuplicatePickException(commentId, pickerId));  // R-26 해석
    grantPoints(comment, pick, pickId);                 // R-12 는 서비스가
}
```

**왜 나누는가.** 저장소가 예외를 던지면 그 예외가 정책의 일부가 되어,
정책이 바뀔 때 인프라를 고쳐야 한다. 또 저장소를 다른 맥락에서 재사용할 수 없다 —
"중복이면 무시하고 넘어가는" 배치가 필요해지면 예외를 잡아 삼켜야 한다.

**예외를 잡아 사실로 바꾸지 말 것.** `@Transactional` 안에서 무결성 예외가 나면
스프링이 트랜잭션을 rollback-only 로 표시해, 예외를 삼켜도 커밋이 실패한다.
존재를 먼저 확인하고 저장한다. 확인과 삽입 사이의 틈은 유니크 키가 막는다.

### 무결성 위반을 뭉뚱그리지 않는다

`DataIntegrityViolationException` 하나에 여러 원인이 섞인다.
전부 같은 도메인 예외로 바꾸면 **원인을 엉뚱한 곳에서 찾게 된다.**

실제로 겪은 일 — 다른 게시글의 댓글을 픽했더니 복합 FK가 막았는데,
저장소가 그걸 "이미 원픽한 댓글입니다"로 보고했다.

`INSERT IGNORE` 로 바꿔봤더니 이번엔 **FK 위반까지 조용히 삼켰다.**
잘못된 요청이 신호 없이 사라지는 쪽이 더 나쁘다.
→ 유일성만 사전 확인으로 가르고, 나머지 위반은 그대로 올린다.

## 규칙 배치 현황

| 규칙 | 내용 | 지키는 곳 |
|---|---|---|
| R-01 | 게시글 유형 불변 | 도메인 — `Post`에 변경 수단을 두지 않음 |
| R-02 | 상품 수 0/1/2 | 도메인 — `Post.verifyPublishable()` |
| R-03 | 사진 장수 | 도메인 — `ItemContainer.verifyPhotoCount()` |
| R-04 | 선택지 정확히 2개 | 도메인 — `Post.verifyPublishable()` |
| R-07 | 자기 댓글 픽 금지 | 도메인 — `Comment.pick()` |
| R-09 | 게시글당 1인 1표 | 스키마 — `UNIQUE(post_id, user_id)` |
| R-10 | 교차 게시글 투표 금지 | 스키마 — 복합 FK |
| R-11 | 게스트 투표 미저장 | 도메인 — `Vote` 생성자가 거부 |
| R-12 | 원픽 1건 → 두 사람 지급 | **서비스** — 댓글·원픽·포인트 협력 |
| R-13 | 재지급 금지 | 스키마(`UNIQUE`) + **서비스**(해석) |
| R-22 | 재투표가 인원을 안 늘림 | 도메인 — `Vote.changeTo()` |
| R-25 | 댓글 인원 = 순 인원 | 스키마 — `UNIQUE` + `INSERT IGNORE` |
| R-26 | 중복 픽 금지 | 스키마(`UNIQUE`) + **서비스**(해석) |

## 저장 경로가 마지막 관문이다

도메인에 검증 메서드가 있어도 **호출을 잊으면 소용없다.**
실측했더니 찬반 게시글에 상품 2개, 선택지 0개인 행이 그대로 저장됐다.

개수 제약은 `CHECK`로 표현할 수 없어(다른 행을 셀 수 없다) 스키마가 막지 못한다.
검증 호출이 유일한 방어선이면 **저장 경로에 붙박는다.**

```java
public Post save(Post post) {
    post.verifyPublishable();   // 잊을 수 없게 한다
    ...
}
```
