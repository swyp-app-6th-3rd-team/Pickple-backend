# PRD-020 — 마이페이지 내 활동 조회 API

**이슈**: #30 · **ADR**: [0036](../adr/0036-my-activity-list-reads-posts-through-activity-index.md) ·
**작성**: 2026-09-04

## 무엇을 왜

마이페이지의 "내 활동" 화면 세 곳에 데이터를 내린다.

| 화면 | 명세 | 엔드포인트 |
|---|---|---|
| 활동 갯수 미리보기 | §7.2 | `GET /users/me/activities/summary` |
| 활동 목록 (무한 스크롤) | §9.1 · §9.2 | `GET /users/me/activities?type=&sort=&cursor=&size=` |
| 내가 올린 최신 투표 (가로 스크롤) | §7.4 | `GET /users/me/posts/recent` |

**새 도메인이 아니라 이미 쌓인 활동 위의 조회 계층이다.** 필요한 데이터가
전부 머지돼 있고, 이 작업은 그것을 화면 순서로 읽는 경로를 만든다.

| 이미 있는 것 | 위치 | 이 작업에서의 쓰임 |
|---|---|---|
| 투표 행 | `vote` (V3) | 내가 투표한 게시글. `UNIQUE(post_id, user_id)` 가 R-22 를 지킨다 |
| 댓글 작성자 | `post_commenter` (V3) | 내가 댓글 단 게시글. 게시글당 한 행이라 R-25 가 지켜진다 |
| 인기 점수 | `post.popularity_score` 생성 컬럼 (V3) | 인기순 정렬 키. 조회 시점에 집계하지 않는다 |
| 내 게시글 인덱스 | `idx_post_user (user_id, deleted_at, created_at DESC)` (V3) | `type=POST` 목록과 §7.4 |
| 커서 규약 | `PostListCursor` · `CursorCodec` (ADR-0004) | 그대로 따른다. 새 인코딩을 만들지 않는다 |
| 목록 성능 패턴 | `PostListRepository` (SPEC §3.3) | "먼저 자르고 나중에 붙인다" 를 그대로 적용 |

### 착수 중 드러난 사실 1 — UNION 이 필요 없다

착수 시점의 가정은 "세 활동이 각기 다른 테이블이라 UNION 커서가 필요하다" 였다.
명세를 다시 읽고 그 가정이 틀렸음을 확인했다.

§9.2 의 조회 데이터가 세 유형 모두 **게시글 카드**이고(탭하면 게시글 상세로 간다),
§9.1 은 "어떤 유형을 탭해서 들어왔는지에 따라 기본 칩이 변경" 이라
**칩이 항상 하나만 활성**이다("전체" 가 없다). 따라서 활동 유형은
결과의 모양이 아니라 **게시글을 좁히는 조건**만 바꾼다.

이 발견이 세 함정을 동시에 없앴다 — 테이블별 독립 `id` 시퀀스 때문에
커서에 판별자를 더하는 일, UNION 결과에 인덱스가 서지 않아 filesort 로
떨어지는 일, 기존 커서 규약을 깨는 일. 근거는 ADR-0036.

### 착수 중 드러난 사실 2 — 인덱스가 정렬을 못 맡는다

배정표는 "스키마 변경 불필요" 였다. `idx_vote_user_created (user_id, created_at)` 와
`fk_commenter_user (user_id)` 가 이미 있기 때문이다.

**실측이 그 가정을 깼다.** 활동 목록의 정렬 튜플은 `(활동 시각, 게시글 id)` 인데
기존 인덱스에는 두 번째 키가 없다. MySQL 이 내 활동을 전부 읽고 filesort 로 정렬했다 —
활동 500건에서 500행 · 4.29 ms. **활동 수에 비례**하므로 쌓일수록 느려진다.

V11 이 `(user_id, created_at DESC, post_id DESC)` 를 두 테이블에 추가한다.
읽는 행이 11로 고정되고(활동 5,000건에서도 11행), 0.070 ms 가 된다.

### 착수 중 드러난 사실 3 — 게스트 0 응답은 만들지 않는다

이슈는 "게스트: 모든 갯수 표시가 0개로 고정" 이라 적었다. 그러나 명세 원문의
같은 문단이 게스트에게 **"클릭 제한"** 도 함께 걸고, 프로필 자리를
"로그인해주세요" 로 바꾼다. 게스트는 활동 영역을 눌러 목록 화면에 갈 수 없다.

즉 0 은 **로그인하지 않은 화면이 그리는 플레이스홀더**이지 서버 응답 규약이 아니다.
세 엔드포인트 모두 인증을 요구하고 401 을 낸다. 서버가 게스트에게 0 을 주면
"활동이 없는 회원" 과 "비로그인" 이 같은 응답이 되어 화면이 둘을 구분하지 못한다.

## 범위

### 포함

- 활동 갯수 요약 3개 값 (§7.2)
- 활동 목록 — 유형 3종 필터 · 정렬 3종 · 커서 무한 스크롤 10개 단위 (§9.1 · §9.2)
- 7일 이내 올린 투표 게시글 (§7.4)
- 정렬 인덱스 마이그레이션 V11
- ADR-0036 · SPEC §3.10

### 제외

| 제외한 것 | 사유 |
|---|---|
| 게스트용 0 응답 | 위 "사실 3". 인증이 필요한 화면이라 게스트가 도달하지 않는다 |
| "아직 참여한 활동이 없어요" 문구 | 화면의 빈 상태다. 서버는 `[]` 를 준다 — `GET /posts` 가 세운 규칙과 같다 |
| 활동 유형 "전체" | §9.1 상 칩은 항상 하나가 활성이다. 서버가 표현할 상태가 아니다 |
| 작성자 닉네임 · 랭킹 | §9.2 의 조회 데이터에 없다. 내 활동 화면은 작성자를 보여주지 않는다 |
| 상대 시각 문자열("3분 전") | 화면이 `createdAt` 으로 만든다. `CommentQueryService` 가 그렇게 하고 있어 규칙이 이미 있다 |
| 인기순의 Θ(활동 수) 개선 | 정렬 키가 활동 테이블에 없어 인덱스로 풀리지 않는다. 비정규화는 쓰기 폭발이라 기각(ADR-0036) |
| `PostListRepository` 의 커서 필터 개선 | 기존 `GET /posts` 도 튜플 비교가 범위로 접히지 않아 4,224행을 훑는다(실측 7.94 ms). **이 작업 단위 밖**이라 손대지 않고 기록만 남긴다 |

## 완료 판정 (= GOAL 명세)

이슈의 완료 판정 표를 그대로 옮기고 측정 방법을 붙였다.

| # | 판정 | 검증 방법 | 증거 |
|---|---|---|---|
| 1 | 재투표해도 투표 참여 횟수가 늘지 않음 (R-22) | 재투표 전후 `summary.voteCount` 동일 | IT |
| 2 | 8일 전에 올린 투표가 최신 목록에 없음 | 경계값 **7일과 8일 양쪽** 테스트. 기준은 요청 시각, 경계는 반열린 구간 `(now-7d, now]` | IT |
| 3 | 활동 유형 필터가 쿼리에서 적용됨 | `EXPLAIN` 으로 실행계획 확인. 애플리케이션 레이어 filter 0건 | IT (`EXPLAIN FORMAT=TREE`) |
| 4 | 활동 0건일 때 빈 목록을 정상 응답 | 200 + `content: []` + `hasNext: false` | IT |
| 5 | 커서 순회 시 중복·누락이 없음 | 전체 조회 후 합집합 대조. 조각 안 중복도 함께 본다 | IT (`scrollAll`) |
| 6 | 목록이 SQL 한 번으로 나간다 | 하이버네이트 `prepareStatementCount` = 1 (조각 크기와 무관) | IT |
| 7 | 정렬이 인덱스로 끝난다 | `EXPLAIN` 에 `Sort` 없음 · `idx_vote_user_activity` 사용 | IT |
| 8 | 세 엔드포인트가 미인증을 401 로 막는다 | 토큰 없이 호출 | IT |
| 9 | 인기순이 `popularity_score` 를 읽는다 (R-24·R-25) | `COUNT(DISTINCT …)` 집계 쿼리 0건 | 코드 확인 + IT |

**빌드 green 은 대리지표다.** 완료 선언 전 `verifier` 를 fresh context 로 불러
이 표와 실제 증거(diff · 테스트 로그)를 대조시킨다.

## 열린 질문

| 질문 | 현재 판단 | 되짚을 계기 |
|---|---|---|
| 요약의 `voteCount` 는 삭제된 게시글의 투표도 센다. 목록은 그 글을 뺀다 — 두 숫자가 어긋난다 | 세는 대상이 다르다. 요약은 "내가 한 활동", 목록은 "지금 볼 수 있는 글" | 화면이 "요약 숫자 = 목록 길이" 를 기대한다는 피드백이 오면 |
| 활동 유형 기본값을 `VOTE` 로 두었다 | §7.2 의 조회 데이터 나열 순서가 "투표, 댓글, 게시글" 이라 첫 칩으로 본다. 화면은 언제나 유형을 실어 보내므로 기본값이 쓰일 일이 드물다 | 화면이 유형 없이 부르는 경로가 생기면 |
| 인기순 무한 스크롤은 최선 노력이다 | `GET /posts` 와 같다 — 스크롤 도중 점수가 올라 커서 위로 이동한 글은 그 회차에서 빠진다 | — (의도된 선택) |
