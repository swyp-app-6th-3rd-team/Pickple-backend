# PRD-014 — 작성자 랭킹 사전 계산

**이슈**: #73 · **ADR**: [0028](../adr/0028-author-ranking-precompute.md) · **작성**: 2026-09-03

## 무엇을 왜

게시글 목록(`GET /api/posts`)에 작성자의 TOP 피커 순위를 실어야 하는데, #19 에서
조회 시점 계산을 시도했다가 비용 때문에 랭킹 필드 없이 닫았다. 그 미결 항목을 채운다.

**증상은 "느리다" 이지만 원인은 "요청마다 전역 집계를 한다" 이다.**
같은 규모(회원 200,000 · 게시글 100,000)를 로컬 MySQL 8.4 에 시드해 재현했다.

| 방식 | 한 조각(LIMIT 11) | 실행계획이 말하는 것 |
|---|---|---|
| 랭킹 없음(현행) | 0.117 ms | `idx_post_latest_all` 에서 11행 → PK 조인 |
| 윈도 `RANK() OVER` | 102 ms | `Materialize rows=200000` — 11건을 위해 20만 명 순위를 전부 만든다 |
| 상관 서브쿼리 `COUNT(*)` | 28.9 ms × `loops=11` ≈ 318 ms | 조각의 행마다 20만 행을 재스캔 |

**순위는 "앞에 몇 명이 있는가" 라서 본질적으로 전역 집계다.** B+트리 인덱스는 *순서*는 주지만
*몇 번째인가*는 주지 않는다. `idx_users_ranking` 이 covering index 로 걸려 테이블 접근이
사라진 뒤에도 20만 행 정렬과 윈도 집계는 그대로 남는다 — 인덱스 튜닝으로 줄일 수 있는
비용이 아니므로, 남은 결정은 "언제 계산해 둘 것인가" 뿐이다.

**설계 도중 드러난 전제 결손** — `users.point` 는 V3 에 있지만 **애플리케이션 어디도 이 컬럼에
쓰지 않는다**(`UserEntity` 가 매핑조차 하지 않는다). 포인트의 정본은 원장이고
(`PointHistoryStore.sumByUser()` 주석의 R-14), 지급 경로 `OnePickService.pick()` 은
`point_history` 에만 행을 넣는다. 곧 오늘 모든 회원의 `point` 는 0 이다.
랭킹을 `users.point` 에서 곧바로 유도하면 **영원히 동작하지 않는 코드**가 되므로,
집계 출발점을 원장으로 잡고 `users.point` 를 그 캐시로 위치시킨다.

## 범위

**포함**
- ADR-0028 — 세 선택지(A 즉시 갱신 / B 주기 배치 / C 구간·티어) 비교와 결정
- `V7__users_ranking_precompute.sql` — `users.ranking INT UNSIGNED NULL` 추가
- `RankingStore`(domain) · `JpaRankingStore`(infra) — 원장 합계 반영 + 순위 재계산
- `RankingBatchService` · `SchedulingConfig` · `RankingProperties` — 5분 주기 배치
- 목록 조회 경로에 랭킹 노출 — `PostListRepository` · `JpaPostQueryStore` ·
  `PostQueryStore.PostListView` · `PostController.PostListItem`
- 통합 테스트 `JpaRankingStoreIT`(8) · `PostControllerIT` 랭킹 3건
- `docs/SPEC.md` §3.3·§4.2·변경 이력, `docs/domain/용어사전.md` 랭킹 항목

**제외**
- **랭킹 전용 조회 API**(TOP 피커 목록·내 순위 조회) — 이 작업은 *목록 응답에 얹는 것*까지다.
  전용 화면이 생기면 정렬·페이징 요구가 달라지므로 그때 설계한다.
- **구간·티어 표현**(상위 n%·LV 뱃지) — 기획 확인이 선행돼야 한다(§열린 질문 1).
  ADR-0028 이 C 안을 기각이 아니라 **판정 보류**로 남겼다.
- **등급(`Grade`)·뱃지** — 용어사전에 있으나 별도 도메인이고 이 사이클 밖이다.
- **`users.point` 를 지급 시점에 갱신하기** — 정본을 원장에서 옮기는 결정이라
  R-14 와 멱등키 방어 구조에 영향을 준다. 배치가 유도하는 형태를 유지한다.
- **배치 실패 경보(모니터링 연동)** — 로그로 남기는 데까지만 한다(§열린 질문 3).
- **분산 환경에서의 배치 중복 실행 방지** — 현재 develop 은 단일 EC2 다(ADR-0012).
  인스턴스가 늘면 리더 선출이나 잠금이 필요해진다(§열린 질문 2).

## 완료 판정

측정 가능한 것만 적는다. **빌드 green·테스트 통과는 대리지표라 포함하지 않는다.**

| # | 판정 | 검증 방법 | 결과 |
|---|---|---|---|
| 1 | `GET /api/posts` 응답에 작성자 랭킹이 포함된다 | `PostControllerIT` 가 배치 실행 후 DB 의 `users.ranking` 과 응답 `authorRanking` 을 대조 | ✅ 일치 |
| 2 | **회원 20만 기준 한 조각 조회 10ms 이내** | 실제 목록 SQL 을 `EXPLAIN ANALYZE` (users 200,000 · post 100,000) | ✅ **102 ms → 0.232 ms** (랭킹 없던 현행 0.117 ms) |
| 3 | 포인트가 바뀌면 **5분(지연 상한) 안에** 순위에 반영된다 | 배치 주기 `0 */5 * * * *` = 상한 5분. `JpaRankingStoreIT` 가 지급 후 배치 전에는 옛 순위, 배치 후 뒤집힘을 확인 | ✅ 배치 전 2위 → 배치 후 1위 |
| 4 | 배치 1회가 주기(5분)보다 충분히 짧다 | 200k 실측, 3회 반복 | ✅ 정상 상태 **181~186 ms**(순위) + **311~318 ms**(포인트 동기화) |
| 5 | **변동이 없으면 아무 행도 쓰지 않는다** | `recalculateRankings()` 반환값 = 기록된 행 수 | ✅ 2·3회차 **0행**. 조건 없는 형태는 550ms/200,000행 |
| 6 | 동점은 가입이 빠른 쪽이 앞선다(공동 순위 없음) | `JpaRankingStoreIT` 동점 테스트 | ✅ 1위·2위로 갈림 |
| 7 | 미산정·탈퇴 회원은 0 이 아니라 `null` | DB 값과 API 응답 양쪽 확인 | ✅ 양쪽 모두 `null`(응답에서 필드 부재) |
| 8 | 랭킹을 얹어도 쿼리 횟수가 1회로 유지된다(N+1 없음) | Hibernate `Statistics.getPrepareStatementCount()` | ✅ 1 |
| 9 | **반증** — 규칙을 깨면 해당 테스트만 실패한다 | `ROW_NUMBER`→`RANK` 치환 / 변경분 필터 제거 후 실행 | ✅ 각각 동점 테스트 1건 · 무기록 테스트 1건만 실패 |

### 측정 환경과 한계

- MySQL 8.4.11(Docker, 로컬 macOS). 실제 마이그레이션 V1·V3·V4·V5·V7 을 적용한 스키마에
  회원 200,000 · 게시글 100,000 · 포인트 원장 300,000 행을 시드했다. 시드 SQL 은 PR 본문에 있다.
- **이 수치는 로컬 개발 머신의 값이다.** dev EC2(t3 계열·공유 vCPU)에서는 절대값이 커질 수 있다.
  다만 판정 2 의 여유가 40배 이상이고, 판정의 근거는 절대값보다 **실행계획이 랭킹 없던 때와
  동일하다**는 사실이다(추가 테이블 접근이 없다).
- 배치 시간은 데이터 분포에 따라 달라진다. 순위 변동이 큰 날은 기록 행이 늘어난다 —
  1명이 최상위로 점프하는 극단에서 75,747행(38%)이 이동해 553 ms 가 걸렸다.
- **배포 환경에서의 실측은 아직 없다.** 이 PRD 의 수치는 전부 로컬이다.

## 열린 질문

1. **화면이 정확한 등수를 정말 필요로 하는가** (미해결 — 기획 확인 필요)
   이슈가 명시한 질문이고 내가 답할 수 없어 **확인된 척하지 않고 열어 둔다.**
   구간(상위 n%·티어)으로 충분하면 C 안이 더 낫다 — 경계를 넘을 때만 바뀌므로 배치 주기를
   크게 늘릴 수 있고 순위 변동에 따른 쓰기(측정된 75,747행)가 대부분 사라진다.
   **뒤집히는 것은 표현이고 남는 것은 구조다** — 응답 필드와 배치 주기는 바뀌지만,
   "미리 계산해 두고 읽기만 한다" 는 형태는 C 에서도 그대로 쓰인다.
   상세 대조표는 ADR-0028 의 §열린 질문 참조.
2. **인스턴스가 늘면 배치가 중복 실행된다.** 현재 develop 은 단일 EC2 라(ADR-0012) 문제가
   드러나지 않는다. 두 인스턴스가 같은 5분에 같은 UPDATE 를 돌리면 결과는 같지만(멱등하다)
   같은 행을 두고 락을 다툰다. 스케일아웃 시점에 리더 선출이나 `GET_LOCK` 을 검토한다.
3. **배치 실패가 조용하다.** 죽어도 목록 조회는 낡은 순위로 정상 응답하고 헬스체크도 초록이다.
   지금은 성공·실패를 로그로 남기는 데까지만 했다. "마지막 성공 시각" 을 지표로 노출하고
   경보를 걸지는 관측 과제로 남긴다(ADR-0027 의 `fetch-secrets` 후속과 같은 성격).
4. **몇 위까지 의미가 있는가.** 20만 명 중 187,432위 를 화면에 그대로 보여줄지는 기획 판단이다.
   서버는 전 회원에게 순위를 매기고, 특정 순위 아래를 감추는 것은 화면의 선택으로 남겼다.
