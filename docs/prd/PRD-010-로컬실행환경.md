# PRD-010 — 로컬 실행 환경변수 주입과 compose 일원화

**이슈**: #53 · **ADR**: [0024](../adr/0024-local-run-environment.md) · **작성**: 2026-09-03

## 무엇을 왜

IntelliJ 에서 `PickpleApplication` 을 실행하면 `JWT_SECRET_KEY` 미주입으로 기동이 실패한다.
`.env` 에 값은 정상적으로 있지만, `.env` 를 읽어 프로세스 환경에 넣어주는 주체가
**Docker Compose 뿐**이라 IDE 경로에서는 아무도 읽지 않는다.

`build.gradle` 에도 `bootRun` 배선이 없어 `./gradlew bootRun` 도 동일하게 실패한다.
즉 **로컬에서 앱을 띄우는 두 경로가 모두 막혀 있다.**

동시에 compose 파일 이름이 역할을 감추고 있다. `docker-compose-dev.yml` 이
`profiles: ["app"]` 트릭으로 사실상 local 역할을 하는데, 이 사실은 파일을 읽어야만 안다.
게다가 `-dev.yml` 과 `-prod.yml` 은 `diff` 결과 완전히 동일하고 둘 다 CI 참조가 0 건이다.

## 범위

**포함**
- `src/main/resources/application-local.yml` — `spring.config.import` 한 줄 추가
- `docker-compose-local.yml` — 신규(MySQL 만, `app` 서비스 없음)
- `docker-compose-dev.yml`·`docker-compose-prod.yml` — 삭제
- `docker-compose-ec2.yml` — 3 줄 주석 문구만 갱신(서비스 정의 무변경)
- `Caddyfile`, `docs/erd/ERD-초안.md` — 사라진 파일 언급 갱신
- `docs/adr/0012-develop-infra-single-ec2.md` — ADR-0024 대체 포인터 추가
- `.run/PickpleApplication.run.xml` — 공유 런 컨피그 신규(시크릿 없음)
- `.env.example` — Apple 기본값 주석 정비 + IDE 실행 안내
- `README.md` — 로컬 실행 절차 신규
- ADR-0024, PRD-010

**제외**
- `docs/SPEC.md` — API·스키마 변경이 아니다
- `application.yml` 플레이스홀더 수정 — import 방식이라 불필요
- `.gitignore` — `.env`·`.idea/` 가 이미 올바르게 잡혀 있다
- `.github/workflows/deploy-develop.yml` — 이미 `-ec2.yml` 만 참조하므로 변경 불필요
- **ADR-0012·PRD-007 본문 수정** — 동결 문서다. 아래 참조
- `AuthProperties` 의 오해 유발 메시지 분리(null vs 길이) — 별개 관심사, 별도 이슈로 분리
- `build.gradle` `bootRun` 배선 — import 방식이 CLI 도 함께 커버하므로 불필요

## 동결 문서 처리

삭제되는 `docker-compose-prod.yml` 은 동결 문서 2 곳에서 언급된다.

| 문서 | 위치 | 내용 |
|---|---|---|
| ADR-0012 | 32 줄 | "`docker-compose-prod.yml` 에 컨테이너 단위 실행이 완성돼 있다" |
| ADR-0012 | 70 줄 | "`docker-compose-prod.yml` volume(`mysql_data`)은 root EBS 위에 얹힌다" |
| PRD-007 | 23 줄 | "기존 `docker-compose-prod.yml` 을 수정하지 않음" |
| PRD-007 | 73 줄 | 오버레이 기각 사유 — "기존 `docker-compose-prod.yml` 을 건드리지 않는다" |

**두 문서 모두 손대지 않는다.** ADR 은 불변이고 PRD 는 동결이다. 이 문장들은 당시 판단의
근거이며 지금 고치면 "왜 그때 그렇게 정했는가"가 사라지고 사후 정당화가 된다.

대체 관계는 **대체하는 쪽인 ADR-0024 에만** 적는다. 대체되는 문서에 포인터를 덧붙이는 것도
결국 불변 문서를 수정하는 일이므로 하지 않는다.

## 수용한 위험

**1. 배포 경로가 단일 파일에 의존한다**
`docker-compose-ec2.yml` 이 유일한 배포 파일이 된다. 이 파일이 깨지면 대안이 없다.
다만 삭제되는 두 파일은 CI 참조가 0 건이라 **애초에 백업 역할을 하고 있지 않았다** —
위험이 새로 생기는 게 아니라 드러나는 것이다.

**2. `.env` 이중 용도**
Compose 변수 보간과 Spring 프로퍼티 소스를 겸한다. 값에 따옴표·공백이 들어가면
두 파서의 해석이 갈릴 수 있다. 현재 `.env` 에는 해당 값이 없다.

**3. EC2 에 옛 compose 파일이 물리적으로 남는다** (이종 리뷰 지적)
배포 워크플로는 `docker-compose-ec2.yml` 을 덮어쓸 뿐 `/opt/pickple` 의 다른 파일을 지우지 않는다.
저장소에서 dev·prod 를 삭제해도 **EC2 호스트에는 이전 배포 때 올라간 파일이 남아 있을 수 있다.**

실동작에는 영향이 없다 — systemd 유닛(`user-data.sh.tftpl:136,169`)과 워크플로
(`deploy-develop.yml:101,112,117`) 모두 `-ec2.yml` 만 참조한다. 다만 누군가 EC2 에 접속해
`docker compose -f docker-compose-prod.yml ...` 을 치면 저장소에 없는 낡은 정의로 컨테이너가 뜬다.

"참조 0 건"은 저장소 안에서만 검증된 사실이고 호스트 상태는 포함하지 않는다.
정리는 이번 범위 밖으로 두되, EC2 접속 시 `/opt/pickple` 의 잔존 파일을 확인한다.

**4. Apple 검증이 2 차 실패 지점**
`.env:39` 에 `OAUTH_APPLE_ENABLED=true` 가 있고(`.env.example` 권장값은 `false`),
`AppleProperties` 가 enabled=true 일 때 6 개 변수를 강제한다. 현재 `.env` 에는 6 개가 모두
채워져 있어 통과하지만, **팀원의 `.env` 에 Apple 값이 없으면 JWT 를 고친 직후 여기서 막힌다.**
`.env.example` 과 README 에 "Apple 을 안 쓰면 `OAUTH_APPLE_ENABLED=false`" 를 명시해 완화한다.

## 열린 질문

- `AuthProperties` 의 에러 메시지를 null 과 길이 부족으로 분리할 것인가. 이번 오진의 직접 원인이지만
  범위 밖으로 뺐다. 별도 이슈로 다룬다.
- EC2 아닌 환경 배포가 필요해지면 일반형 compose 를 어떻게 되살릴 것인가.
  `-ec2.yml` 에서 caddy·EIP 의존을 걷어내는 방식을 ADR-0024 에 적어 두었다.
