# PRD-012 — 투표 참여 API

**이슈**: #21 · **ADR**: 해당 없음 · **작성**: 2026-09-03

## 무엇을 왜

투표는 도메인·저장소·서비스가 모두 있는데 **HTTP 표면이 없다.** 앱이 투표를 보낼 곳이 없어
기능명세 §2.2(카드에서 즉시 투표 → 게이지 전환)와 §6.3 이 통째로 막혀 있다.

표면을 얹으려고 기존 코드를 읽는 과정에서, **표면만으로는 이슈의 완료 판정을 만족할 수 없다**는
것이 드러났다. 증상이 아니라 원인 두 가지다.

| # | 측정 결과 | 원인 |
|---|---|---|
| 1 | `grep -rn "vote_count" src/main/java` → `post_option.vote_count` 를 **쓰는 코드 0건** | 지금까지 투표를 부르는 곳이 테스트뿐이라 **득표율을 읽을 소비자가 없었다.** 이 API 가 첫 소비자다 |
| 2 | 16명 동시 투표에서 **14건이 `CannotAcquireLockException` 으로 500** | `castFirst` 가 `vote` INSERT → `UPDATE post` 순서다. INSERT 가 FK 검사로 `post` 행에 공유 락(S)을 잡은 뒤 배타 락(X)을 요구하는 **락 승격**이라, 동시 요청 둘이 각각 S 를 쥔 채 서로의 X 를 기다린다 |

(1) 은 `post_option.vote_count` 컬럼이 V3 부터 `'투표율 표시용'` 주석과 함께 존재하는데도
행을 만들 때 0 으로 넣고 **아무도 증감시키지 않는** 상태다. 이슈가 요구하는
"재투표 시 이전 선택지 −1 / 새 선택지 +1" 은 이 경로 없이는 성립할 수 없다.

(2) 는 이 PR 이 만든 문제가 아니라 **`develop` 에 이미 있던 것**이다
(`git show HEAD:...VoteService.java` 로 순서 확인). 부르는 곳이 없어 드러나지 않았을 뿐이고,
이슈의 완료 판정 "동시 투표 요청에서 카운터 합 = 인원 수" 가 이것을 정면으로 겨눈다.

## 범위

**포함**
- `app.pickple.vote.controller.VoteController` 신규 — `POST /api/posts/{postId}/votes`,
  요청/응답 DTO 를 같은 패키지 중첩 record 로 (`CommentController` 선례)
- `PostCounters` 에 `increaseOptionVoteCount`·`decreaseOptionVoteCount` 포트 추가와
  `JpaPostCounters`·`PostCounterRepository` 원자 UPDATE 구현
- `PostOptionEntity.vote_count` 를 읽기 전용(`insertable=false, updatable=false`)으로 전환
- `VoteService` 최소 변경 — R-10 선검증, 선택지 카운터 이동, 집계 반환,
  **교착을 없애는 락 획득 순서 고정**
- `VoteControllerIT` — 이슈 완료 판정 5항 + 게스트 거부 + 득표율
- `docs/SPEC.md` §3.5 투표 계약과 변경 이력 1행

**제외**
- **투표 결과 단독 조회 API** — 투표 응답이 곧 게이지 데이터라 지금은 불필요하다.
  이미 투표한 사용자가 진입 시점부터 게이지를 보는 화면(§2.2 후반)은 게시글 상세(#24)가 담당한다
- **`users.vote_count`(누적 투표 횟수) 증가** — 포인트·등급 기능의 일부다.
  이 PR 은 재투표가 그 값을 **늘리지 않음**만 고정한다(R-22)
- **카운터 드리프트 감지·보정 배치** — 아래 열린 질문 1
- **기존 투표 데이터의 `post_option.vote_count` 백필** — 개발 환경 테스트 데이터뿐이라
  하지 않았다. 운영 데이터가 있었다면 필요하다(SPEC 마이그레이션 절 참조)
- **선택지 변경 이력** — 누가 언제 마음을 바꿨는지는 요구되지 않았다. `vote` 는 현재 선택만 든다
- **`ActivePostGuard` 의 확인–행동 경합 창 제거** — 기존 한계이며 이 PR 이 넓히지 않았다
- ADR — 되돌리기 비싼 **신규** 결정이 없다. 락 순서와 읽기 전용 카운터는 둘 다
  `PostEntity`·`PostCounterRepository` 에 이미 선 예가 있는 기존 결정을 따른 것이다

## 완료 판정

측정 가능한 것만 적는다. **테스트 통과·빌드 green 은 대리지표라 판정으로 쓰지 않는다.**
아래는 모두 **DB 에서 직접 읽은 값**이거나 **HTTP 응답 상태·본문**이며,
테스트는 그 값을 만들어 읽는 계측 도구다.

| # | 판정 | 검증 방법 | 결과 |
|---|---|---|---|
| 1 | 같은 사용자가 양쪽 선택지에 각각 투표해도 투표 인원이 1 (R-09) | 두 번 투표 후 `SELECT COUNT(DISTINCT user_id) FROM vote`, `post.vote_count`, `COUNT(*) FROM vote` 세 값을 직접 조회 | ✅ 1 / 1 / 1 — 행도 하나뿐이다 |
| 2 | 다른 게시글의 선택지로 투표 시 거부 (R-10) | 다른 글의 선택지 id 로 요청 → 상태코드와 `code` 확인, 양쪽 게시글의 투표 인원 조회 | ✅ `400 INVALID_REQUEST`, 양쪽 0명. **500 이 아니다** — FK 까지 가면 500 이 된다 |
| 3 | 재투표 시 이전 선택지 −1 / 새 선택지 +1 / 인원 불변 (R-22) | 재투표 전후 `post_option.vote_count` 두 값과 `post.vote_count` 를 DB 에서 비교 | ✅ (1,0) → (0,1), `post.vote_count` 1 로 불변 |
| 4 | 재투표가 누적 투표 횟수를 늘리지 않음 (R-22) | 재투표 전후 `SELECT vote_count FROM users WHERE id=?` 비교 | ✅ 불변 |
| 5 | 동시 투표에서 선택지 카운터 합 = 인원 수 | 16 스레드를 `CountDownLatch` 로 동시 출발(절반씩 다른 선택지) → 전원 응답 상태 확인 후 `post_option` 두 카운터의 합·`COUNT(DISTINCT user_id)`·`post.vote_count` 비교 | ✅ 16 = 16 = 16, 전원 200 |
| 6 | **반증 — 락 순서가 실제로 그 결과를 만든다** | `castFirst` 의 문장 순서를 되돌려 재실행 | ✅ **판정 5 만 실패**(14/16 이 500). 순서를 복원하면 다시 통과 — 통과가 우연이 아님을 확인 |
| 7 | 게스트는 투표할 수 없다 (R-11) | 토큰 없이 요청 → 상태코드 확인, 이후 `vote` 행 수 조회 | ✅ `401 UNAUTHORIZED`, 표 0건 |
| 8 | 투표 직후 응답에 선택지별 표수와 득표율이 담긴다 (§2.2) | 1명 투표 후 응답 본문, 2명이 갈라 투표 후 응답 본문 | ✅ 100/0, 50/50 — 별도 조회 없이 게이지 전환 가능 |
| 9 | 투표 없는 유형(GENERAL)에 투표 시 거부 | 일반 게시글에 요청 | ✅ `400 INVALID_REQUEST` |
| 10 | 기존 동작 무회귀 | 판정 1~9 를 만든 변경 후 저장소 전체 테스트 재실행 | ✅ 363건 실패 0 — 이건 **대리지표라 판정이 아니라 회귀 부재 근거**로만 쓴다 |

> **측정 환경 함정(실측)**: Testcontainers 재사용(`withReuse(true)`) 때문에 **판정을 오염된
> 컨테이너에서 내리면 안 된다.** 뒷정리를 붙이기 전 실행이 남긴 `vote_count=16` 게시글이
> 다음 실행의 `PostControllerIT` 인기순 검증을 깨뜨렸다(필터 없이 첫 항목을 단언하는 자리를
> 그 글이 차지). 컨테이너를 내리고 새로 띄워 판정했고, 같은 컨테이너에서 **연속 2회** 통과하는
> 것까지 확인해 뒷정리가 실제로 동작함을 근거로 삼았다.

## 열린 질문

1. **집계 카운터를 두 번째 진실 원천으로 두는 것이 맞나.** `COUNT(*) GROUP BY` 로 매번 세면
   드리프트가 원천 차단된다. 스키마가 `post_option.vote_count` 를 "투표율 표시용"으로 이미
   두었고 이슈도 "선택지 카운터만 이동한다"고 명시해 설계 의도를 따랐지만,
   **드리프트를 감지·보정할 장치는 지금 없다.** 표가 많아지기 전에 정할 문제다.
2. **재투표 횟수 제한.** 무제한으로 선택을 바꿀 수 있다. 정책이 정해지지 않았고
   현재 스키마(`vote` 행 하나를 UPDATE)로는 변경 횟수를 셀 수 없다.
   제한이 필요해지면 이력 테이블이나 카운터 컬럼이 필요하다.
3. **투표 마감.** 마감 시각·마감 후 투표 거부가 명세에 없다. `post` 에 관련 컬럼도 없다.
   생기면 `ActivePostGuard` 옆에 같은 모양의 관문이 붙을 자리다.
4. **이미 투표한 사용자의 진입 시 게이지 표시.** §2.2 후반이 요구하지만 이 API 범위가 아니다.
   게시글 상세(#24)가 "내가 어디에 투표했는가"를 함께 내려야 하며, 그 계약은 #24 에서 정한다.
