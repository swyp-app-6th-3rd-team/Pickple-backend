# PRD-018 — 뱃지 도메인과 획득 판정

**이슈**: #27 · **ADR**: [0031](../adr/0031-badge-daily-activity-aggregate.md) · **작성**: 2026-09-04

## 무엇을 왜

뱃지 8종(정책 요약표 §3)의 도메인과 획득 판정을 신설한다. **도메인도 테이블도 없다** —
규칙만 문서에 있다. [ERD 초안](../erd/ERD-초안.md) §5.3 이 설계해 두고
[ERD 2차](../erd/ERD-2차.md) §1.2 가 "코어 흐름 밖" 이라며 유예한 항목이다.

**표면 요구는 "뱃지 8종 판정" 이지만 중심축은 R-19 다.** 조건 유형이 셋인데(R-18)
일일·연속 둘을 `vote` 에서 직접 구하면 회원의 투표 이력 전체를 날짜로 묶어야 한다.
`DATE(created_at)` 이 `idx_vote_user_created` 를 무력화하고, 연속 판정은 `DISTINCT DATE(...)`
때문에 그 회원의 투표를 **전부** 훑는다 — 1,000회 투표한 사람의 "7일 연속" 에 1,000행이다.
그리고 이 판정은 **투표할 때마다** 일어난다(명세 §2.3 "투표 시 미션 2의 상태바가 즉시 변경됨").
쓰기 핫패스에 선형 증가 비용이 붙는 구조라, 날짜별 집계 테이블이 사실상 요구사항이다.

**설계 도중 드러난 전제 결손** — `users.vote_count` 는 V3 에 있지만 **애플리케이션 어디도
이 컬럼에 쓰지 않는다**(`UserEntity` 가 매핑조차 하지 않는다). 투표 경로는 `post`·`post_option`
카운터만 올린다. 곧 오늘 모든 회원의 값이 0 이다. ADR-0028 이 `users.point` 에서 발견하고
"영원히 동작하지 않는 코드" 라 부른 것과 같은 상황이라, 누적 투표 횟수의 정본부터 정해야 했다.

## 범위

**포함**

- [ADR-0031](../adr/0031-badge-daily-activity-aggregate.md) — 판정 위치와 뱃지 정의의 소재
- `V9__badge.sql` — `badge`·`user_badge`·`user_daily_activity` 3테이블 + 뱃지 8행 시드
  + **기존 `vote` 백필**
- 도메인 — `Badge`(임계값 판정) · `BadgeConditionType` · `VoteActivity` · `BadgeProgress`
  + 3개 Store 인터페이스
- 인프라 — `JpaBadgeStore` · `JpaUserBadgeStore` · `JpaDailyActivityStore`(연속 계산)
  + 엔티티·리포지토리
- 서비스 — `BadgeService`(판정·현황·미션) · `BadgeVoteActivityRecorder`
- 투표 연결 — `vote` 에 포트 `VoteActivityRecorder` 선언, `VoteService.castFirst` 에서 호출
- API — `GET /api/users/me/badges` · `GET /api/users/me/badges/missions`
- 테스트 — `BadgeTest`(15) · `JpaDailyActivityStoreIT`(9) · `BadgeControllerIT`(11)
  · `BadgeJudgementQueryIT`(4)
- 문서 — SPEC §3.7·§4, 도메인 모델 R-17~R-19 코드 연결, 용어사전

**제외**

- **뱃지 일러스트** — §12.2 가 요구하지만 자산이 아직 없다. `badge` 행에 URL 컬럼을 더하면
  되도록 이름을 데이터로 둔 구조가 그대로 받아준다(ADR-0031 열린 질문 3).
- **획득 모달 API**(§12.3) — "새로 얻은 뱃지" 를 가리려면 조회 시각이나 확인 플래그가 필요한데,
  그 상태를 어디에 둘지는 화면 흐름이 확정돼야 정할 수 있다. `acquired_at` 은 남겨 두었다.
- **연속 뱃지의 미션 슬롯** — 명세 §2.3 이 슬롯을 둘(누적·일일)로 못박았고 `<조회 데이터>` 에도
  연속 항목이 없다. 세 번째 슬롯을 지어내면 화면이 그릴 수 없는 데이터를 내려주는 셈이다.
- **집계·`vote` 정합성 점검 배치** — 유도 값이라 어긋날 수 있지만 알아챌 장치가 지금은 없다.
  어긋남이 실제로 관측될 때 만든다(ADR-0031 열린 질문 1).
- **`users.vote_count` 채우기** — 등급(#25)이 같은 값을 쓰므로 건드리지 않는다.
  뱃지는 자기 애그리거트 안에서 완결한다.
- **등급(`Grade`)** — 별도 도메인이고 이 사이클 밖이다(#25).

## 한계와 남은 위험

- **백필을 빈 DB 에서만 확인했다.** 통합 테스트는 매번 새 스키마에 마이그레이션을 적용하므로
  `vote` 가 비어 있고, 백필 SQL 이 행을 옮기는 것은 문법 수준에서만 검증됐다.
  실제 데이터가 있는 develop 에 적용될 때가 첫 실행이다.
- **집계가 `vote` 와 어긋나도 알아챌 장치가 없다.** 유도 값이라 재계산은 가능하다.
- **투표 트랜잭션이 길어진다.** UPSERT 하나 + 뱃지 8행 조회. 부하 측정은 하지 않았다 —
  현재 규모에서 문제가 관측되지 않았고, 측정 없이 최적화하지 않는다.
- **연속 일수를 31 에서 자른다.** 최대 임계값 30 이라 판정에는 영향이 없다.

## 열린 질문

1. 집계·`vote` 정합성 점검을 배치로 둘 것인가, 어긋남이 관측될 때 만들 것인가.
2. 연속 뱃지를 미션 슬롯에 넣을 것인가(기획 확인 필요).
3. 획득 모달(§12.3)의 "새 뱃지" 판정 상태를 어디에 둘 것인가.
