# PRD-023 탈퇴 시 개인정보를 즉시 파기한다

**이슈**: [#111](https://github.com/swyp-app-6th-3rd-team/Pickple-backend/issues/111)
**근거 ADR**: [ADR-0040](../adr/0040-withdrawal-erases-personal-data.md)
**확장하는 결정**: [ADR-0037](../adr/0037-apple-withdrawal-detaches-provider-identity.md)
**도메인 규칙**: R-27(즉시 파기) · R-28(소셜 신원은 활성 회원만) — [도메인 모델](../domain/도메인%20모델.md)

## 무엇을 왜

개인정보처리방침 제3조는 **"회원 탈퇴 시 지체 없이 파기"** 를 약속하고 부칙이 시행일을
**2026-09-20** 으로 못박았다. 그 시점에 서비스는 자사 방침을 위반하는 상태가 된다.

`DELETE /auth/me` 는 `state` 를 `INACTIVE` 로 바꾸고 Apple 사용자의 `provider_id` 만 놓는다.
제1조가 수집 항목으로 명시한 나머지는 **무기한 보존**된다.

| 컬럼 | 제1조 수집 항목 | 탈퇴 후 현재 |
|---|---|---|
| `email` | 이메일 주소 | **잔존** |
| `name` | 소셜 제공 이름 | **잔존** |
| `nickname` | 닉네임 | **잔존** |
| `profile_image_url` | 프로필 이미지 | **잔존** |
| `provider_id` (KAKAO) | 소셜 로그인 식별값 | **잔존** |
| `provider_id` (APPLE) | 소셜 로그인 식별값 | 해제됨 (ADR-0037) |

제9조가 "암호화하여 저장·관리" 대상으로 선언한 소셜 로그인 식별값이 카카오 회원에게는
**평문으로 남는다.** 제3조가 게시물·댓글을 보존 예외로 두면서 붙인 조건
"작성자 정보는 **비식별 처리**" 도 지켜지지 않는다.

**원인은 버그가 아니라 도메인 모델 결손이다.** 규칙 표에는 R-20("탈퇴해도 데이터를 지우지
않고 비활성으로 표시한다")만 있었다. 코드가 파기를 빠뜨린 것이 아니라, 코드가 표현할
파기 규칙 자체가 존재하지 않았다.

## 범위

### 포함

- `User.withdraw()` 가 `email`·`name`·`nickname`·`profileImageUrl`·`providerId` 를 파기(NULL)
- `User` private 생성자 불변식을 `APPLE && INACTIVE` → `INACTIVE`(provider 무관)로 확대
- 기존 탈퇴 회원의 소급 파기 마이그레이션(**V14**)과 `provider_id` 컬럼 COMMENT 정정
- 카카오·애플 양쪽의 파기·재로그인·연속 탈퇴 검증
- 탈퇴 회원 작성 게시글·댓글의 작성자 비식별 표기 **검증**(구현 아님 — 아래 참조)

### 제외

- **작성자 비식별 표기의 신규 구현.** `PostListRepository`·`CommentRepository`·
  `RankingListRepository` 가 이미 `COALESCE(NULLIF(u.nickname,''), NULLIF(u.name,''), '알 수 없음')`
  이라, `nickname`·`name` 을 비우면 **코드 변경 없이** 비식별 표기가 나온다. 검증만 한다.
- **#45 축 4 재가입 제한.** 식별자를 지우므로 자동으로 "제한 없음" 이 된다. 제3조
  `탈퇴 후 [ ]개월` 공란이 채워지면 재검토하되 **이 이슈 이후 탈퇴자에게 소급 불가**하다.
- **#45 축 5 토큰 폐기.** #106 이 `ActiveAccountAuthorizationManager` 로 해소했다(ADR-0035).
- **게시물 본문의 개인정보.** 제1조 3항이 "회사가 별도로 수집·요구하는 개인정보가 아니다"
  로 선을 그었다.
- **탈퇴 시각 감사값(`deleted_at`).** SPEC 이 예고한 항목이나 이번 범위가 아니다.

## 작업 단위 분해

의존 순서가 있어 **직렬**이다. 병렬 워크트리로 쪼개지 않는다.

| # | 단위 | 산출물 | 의존 |
|---|---|---|---|
| 1 | 도메인 불변식 확대 + 파기 구현 | `User.java` | — |
| 2 | 기존 테스트 정정 | `UserTest`·`AppleWithdrawalReloginIT`·`AccountWithdrawalPersistenceServiceTest` | 1 |
| 3 | 파기 검증 통합테스트 신설 | `WithdrawalPiiErasureIT`(신규) | 1 |
| 4 | 소급 파기 마이그레이션 | `V14__erase_withdrawn_user_personal_data.sql` | 1 |
| 5 | 문서 갱신 | `SPEC.md` | 1·4 |

**1 이 2·3 보다 먼저여야 하는 이유**: 불변식을 넓히기 전에 파기를 넣으면 마스킹한 카카오
행을 읽는 순간 `User.restore()` 가 생성자 예외로 터진다. 두 변경은 **원자적**이라 한 커밋이다.

## 완료 판정 (= GOAL 명세)

이슈 "완료 조건" 을 측정 가능한 형태로 옮긴 것이다. **빌드 green·테스트 통과는 근거가 아니다.**

| # | 판정 | 검증 방법 |
|---|---|---|
| C-1 | 카카오 탈퇴 후 `users` 행의 다섯 컬럼이 전부 `NULL` | 탈퇴 실행 후 `JdbcTemplate` 으로 **행을 직접 조회** — `email`·`name`·`nickname`·`profile_image_url`·`provider_id` 비-NULL **0건**. 인메모리 게터가 아니라 DB 값으로 판정 |
| C-2 | 애플 탈퇴에서도 같다 | C-1 과 동일 절차를 `APPLE` 로 반복. 기존 `provider_id` 분리 동작이 유지되는지 함께 확인 |
| C-3 | 마스킹 후 재조회가 터지지 않는다 | `userStore.findById(탈퇴자)` 가 예외 없이 반환. **회귀 위험 1순위** — 불변식을 안 넓히면 여기서 `IllegalArgumentException` |
| C-4 | 활성 회원의 `providerId` 누락은 여전히 거부된다 | `User.restore(..., state=ACTIVE, providerId=null)` → `IllegalArgumentException`. provider 4종 전부. **거부되지 않으면 실패** |
| C-5 | 비활성이면 provider 무관하게 허용된다 | `User.restore(..., state=INACTIVE, providerId=null)` 이 `KAKAO`·`GOOGLE`·`NAVER`·`APPLE` 전부에서 성공 |
| C-6 | 두 명 이상 연속 탈퇴에 유니크 위반이 없다 | 같은 provider 회원 2명을 연속 탈퇴 → `uk_users_provider` 위반 **0건**, 두 행 모두 `provider_id IS NULL` |
| C-7 | 카카오 탈퇴 후 동일 계정 재로그인이 **신규 가입**이다 | 탈퇴 후 같은 `sub` 로 `loginOrRegister` → 새 `userId` 발급, `state=ACTIVE`, `hasProfile()=false`. 과거 행은 그대로 남아 있음 |
| C-8 | 탈퇴 회원의 게시글이 목록에 남고 작성자만 비식별 표기 | 탈퇴자 작성 게시글 조회 → **게시글 자체는 결과에 존재**하고 `author_nickname = '알 수 없음'`. 사라지면 실패(INNER JOIN 회귀) |
| C-9 | 탈퇴 회원의 댓글도 같다 | `GET /posts/{id}/comments` → 댓글 존재 + `nickname = '알 수 없음'` |
| C-10 | 카카오 unlink 가 값 있는 `providerId` 로 호출된다 | `InOrder` 로 `unlink(실제값)` → `complete()` 순서 고정. `unlink(null)` 이면 실패 |
| C-11 | 소급 파기 후 기존 탈퇴 행에 잔존 개인정보 0건 | V14 적용 후 `SELECT COUNT(*) FROM users WHERE state='INACTIVE' AND (email IS NOT NULL OR name IS NOT NULL OR nickname IS NOT NULL OR profile_image_url IS NOT NULL OR provider_id IS NOT NULL)` → **0** |
| C-12 | 소급 파기가 활성 회원을 건드리지 않는다 | V14 적용 전후 `state='ACTIVE'` 행의 다섯 컬럼 값이 **동일**. 활성 회원 수 변화 0 |
| C-13 | 기존 탈퇴 테스트가 깨지지 않는다 | `AppleWithdrawalReloginIT`·`WithdrawnUserAuthorizationIT` 통과. 단 **보존을 단언하던 항목은 파기 단언으로 정정**하고 정정 사실을 PR 에 명시 |

### C-13 이 별도 항목인 이유

기존 테스트 3건이 **파기의 반대를 단언**하고 있다. 이들은 "깨진" 것이 아니라 **계약이 바뀐** 것이다.

| 테스트 | 현재 단언 | 정정 후 |
|---|---|---|
| `UserTest.nonAppleWithdrawalKeepsProviderId` | 비 Apple 은 `providerId` 유지 | provider 무관 파기 |
| `UserTest.withdrawKeepsNicknameValue` | 탈퇴해도 닉네임 값 보존 | 닉네임도 파기 |
| `AppleWithdrawalReloginIT` | 탈퇴 후 `nickname`·`profileImageUrl` 보존 | 둘 다 파기 |

`withdrawKeepsNicknameValue` 의 주석은 보존을 **적극적으로 정당화**한다 —
"도메인이 값을 지우면 누가 쓰던 닉네임인지를 잃는다." 처리방침이 이 근거를 뒤집었다는 사실을
테스트 이름과 주석에 남긴다. 조용히 지우면 다음 사람이 왜 뒤집혔는지 알 수 없다.

## 마이그레이션 판단

**V14 를 만든다.** 근거는 다음과 같다.

제3조의 파기 의무는 **"탈퇴한 회원"** 에게 걸리지 탈퇴 시점으로 나뉘지 않는다. 코드만 고치면
신규 탈퇴자만 파기되고 **기존 탈퇴자는 2026-09-20 에 위반 상태로 남는다.**

V12 가 Apple `provider_id` 에 대해 이미 같은 판단을 했다 — "이 변경 이전에 이미 탈퇴한
Apple 사용자도 재가입할 수 있게 소급 적용한다." 이번은 그 범위를 다섯 컬럼·전 provider 로
넓히는 같은 종류의 작업이다.

- **적용 순서**: 컬럼 값 UPDATE → `provider_id` COMMENT 정정. 스키마 구조 변경은 없다.
- **롤백**: **불가능하다.** 파기한 값은 DB 만으로 복구할 수 없다. ADR-0037 이 V12 에서
  같은 비가역성을 이미 수용했고, ADR-0040 이 이를 명시적으로 다시 수용한다.
- **기존 데이터 영향**: `state='INACTIVE'` 행만 대상이다. 활성 회원은 `WHERE` 절이 제외한다(C-12).

**스키마 구조 변경은 필요 없다.** V12 가 `provider_id` 를 `NULL DEFAULT NULL` 로 완화하고
`ck_users_active_provider_id CHECK (state <> 'ACTIVE' OR provider_id IS NOT NULL)` 를 걸어
두었는데, 이 CHECK 는 **provider 를 보지 않고 state 만 본다.** `email`·`name`·
`profile_image_url` 은 원래 `DEFAULT NULL` 이다. 막던 것은 Java 도메인 불변식뿐이었다.

## 열린 질문

- 방침의 `부정이용 관련 기록 | 탈퇴 후 [ ]개월` **공란**을 누가 언제 채우는가. 채워지면 R-27 에
  예외가 생기고 목적을 명시한 별도 보유 테이블 설계가 필요하다. 채워지기 전까지는 보유 근거가
  없으므로 파기가 유일한 준수 방법이다.
- 탈퇴 시각 감사값이 필요해지는 시점. 지금은 `updated_at` 근사뿐이고 파기 후에는 그것이
  탈퇴 시각과 같아진다.
