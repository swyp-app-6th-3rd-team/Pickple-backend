# PRD-021 탈퇴 회원 차단을 인가 계층 한 곳으로 모은다

**이슈**: [#106](https://github.com/swyp-app-6th-3rd-team/Pickple-backend/issues/106)
**근거 ADR**: [ADR-0035](../adr/0035-withdrawn-user-central-authorization.md)
**근거 검증**: [2026-09-04 인증 수명주기 E2E 검증](../verification/2026-09-04-auth-lifecycle-e2e.md) §D-1

## 무엇을 왜

탈퇴한 회원이 **탈퇴 전 발급받은 액세스 토큰**(TTL 30분)으로 댓글·투표·원픽을 계속 만들 수 있다.
실서버에서 서버 재기동을 사이에 두고 두 번 재현됐다.

| 요청 | 게스트 | 탈퇴 회원 |
|---|---|---|
| `POST /posts/{id}/comments` | 401 | **201 CREATED** |
| `POST /posts/{id}/votes` | 401 | **200 OK** |
| `POST /comments/{id}/pick` | 401 | **201 CREATED** |

**탈퇴 회원이 게스트보다 권한이 많다.** 피해는 조회에 그치지 않는다 — 원픽은 포인트를 지급하므로
탈퇴 계정에 `PICKING +5`, 상대에게 `PICKED +10` 이 적립된다. 포인트는 TOP 피커 랭킹의 입력이고
`users.point` 집계는 배치가 나중에 채우므로(ADR-0028) **다음 재계산 때 오염이 표면화된다.**

원인은 세 곳의 누락이 아니라 **하나의 부재**다. `.anyRequest().authenticated()` 는
"토큰이 유효한가" 만 묻고 "이 신원이 아직 살아 있는가" 를 묻지 않는다. 탈퇴 판정은 각 서비스의
`isActive()` 호출에 맡겨져 있는데 `vote`·`comment`·`point` 패키지에는 한 줄도 없다.
막힌 두 엔드포인트는 우연히 그 확인을 하는 서비스를 지났을 뿐이다.

## 범위

## 열린 질문과 그 답 (ADR-0035 "착수 전 결정해야 할 것")

### 1. 비활성 계정은 401 인가 403 인가 → **401 UNAUTHORIZED**

저장소에 두 선례가 공존한다. `AuthService.getById()`(= `GET /auth/me`)는 탈퇴자에게 **401**,
`AuthService.refresh()` 는 **403** 이다. 실측된 관측 동작(`GET /auth/me` → 401)과 맞추고,
클라이언트가 재로그인을 유도하도록 **401** 로 통일한다.
탈퇴자에게 "계정은 있으나 권한이 없다" 는 정보를 주지 않는 이점도 있다.

`AuthService.refresh()` 의 403 은 **그대로 둔다** — 아래 3번의 이유로 중앙 관문 밖이고,
그 경로는 액세스 토큰이 아니라 리프레시 쿠키를 다루므로 의미가 다르다. 의도된 불일치로 기록한다.

### 2. 선택적 인증 공개 경로의 정책 → **익명으로 강등**

실측: `GET /posts/{id}/comments` 에서 게스트는 `mine=false`, **탈퇴자 토큰은 `mine=true`** 다.
`permitAll` 은 필터를 우회하지 **않으므로** 탈퇴자 신원이 그대로 반영된다.

거부가 아니라 **강등**을 택한다. 거부하면 토큰을 지우지 않은 탈퇴자가 공개 목록조차 못 보게 되어
R-20(탈퇴자의 글은 계속 보인다)의 취지와 어긋난다. R-20 은 **글의 가시성**을 말하는 것이지
탈퇴자가 개인화된 신원을 유지해도 된다는 뜻이 아니다 — 강등이 정확히 그 구분을 만든다.

| `GET /posts/{id}/comments` | 결과 |
|---|---|
| 게스트(토큰 없음) | 200, `mine=false` |
| **탈퇴자 토큰** | **200, `mine=false`** (강등) |
| ACTIVE 토큰 | 200, `mine=true` |

**구현상의 제약**: `AuthorizationManager` 는 `permitAll` 경로에서 호출되지 않는다.
따라서 강등은 관문과 같은 지점에서 처리할 수 없고 별도 처리가 필요하다.

### 3. `/auth/refresh` 는 예외 → **자체 `isActive()` 확인 유지**

`permitAll` 이고 액세스 토큰 없이도 호출되므로 중앙 관문이 대신할 수 없다.
`AuthService` 의 확인을 **유지**한다. 중앙 관문이 생겼다고 서비스별 확인을 일괄 제거하지 않는다 —
관문은 이 시큐리티 체인을 지나는 HTTP 요청만 보호하고 배치·내부 호출·테스트는 못 막는다.

### 4. `/auth/logout` 은 그대로 → **익명·탈퇴자도 호출 가능**

자격증명을 버리는 데 ACTIVE 를 요구할 이유가 없다. `permitAll` 유지.

## 잃는 것 / 감수하는 것

### 신원이 붙은 요청당 조회 1회가 는다
좁은 존재 확인 쿼리(`type=const`, `key=PRIMARY`, 실측 0.03ms warm)지만 **매 요청 도는 0.1ms 는
건당은 싸도 총 DB 용량을 지배할 수 있다.** 운영 규모 총량 영향은 C-12 로 측정하되,
localhost·빈 테이블 한계는 그대로 남는다.

**범위를 정확히 적는다.** 조회가 도는 것은 **`Authorization` 헤더가 붙은 요청**이다.
토큰 없는 게스트와 그 트래픽이 부르는 정적 경로는 0회다. 그러나 **토큰을 붙인 채 정적·문서
경로**(`/swagger-ui/**`, `/scalar/**`, `/docs/**`, `/llms.txt`)를 부르면 그 경로에서도 조회가 돈다 —
강등 필터에 `shouldNotFilter` 를 두지 않았기 때문이다.

경로 목록으로 거르지 않은 이유는 **그 목록이 낡기 때문**이다. "지금 정적 경로는 이것뿐" 은
새 경로가 생기면 즉시 틀리고, 그 실패 모드가 정확히 이 결함을 만든 것("확인 지점이 4곳뿐")이다.
정적 경로에 토큰을 붙이는 트래픽은 드물어 지금은 비용을 감수한다. 문제가 되면
`shouldNotFilter` 로 좁히되, 그때는 목록이 `SecurityConfig` 의 `permitAll` 과 어긋나지 않게
한 곳에서 관리해야 한다.

### `DELETE /auth/me` 재호출이 200 → 401 로 바뀐다
현재는 멱등하게 200 이다(E2E §D-5). 중앙 차단이 들어가면 두 번째 호출이 관문에서 401 로 막힌다.
**외부에 보이는 계약 변경을 의식적으로 수용한다** — 이미 탈퇴한 계정이 탈퇴 API 를 다시 부르는 것은
정상 흐름이 아니고, 관문에 예외를 뚫는 비용이 멱등성의 가치보다 크다.
이 계약 변경은 **#108 에 코멘트로 알린다**(#108 자체는 이 PR 범위 밖).

### TOCTOU 경합은 남는다
`open-in-view: false` 이므로 인가 시점 조회는 서비스 트랜잭션 **밖**에서 끝난다.

```
1. 요청 A 의 인가 조회: ACTIVE
2. 요청 B 가 탈퇴를 커밋: INACTIVE
3. 요청 A 가 서비스에 진입해 그 사용자로 쓰기를 커밋
```

"조회 시점엔 ACTIVE" 는 보장해도 "커밋 시점에도 ACTIVE" 는 보장하지 못한다.
**중앙 관문은 진입 장벽이지 트랜잭션 불변식이 아니다.** 이 저장소는 같은 한계를 이미
`ActivePostGuard` 주석에 적어 두었다. "절대 안 된다" 가 요구사항이면 포인트 원장 같은 치명적
쓰기에는 조건부 쓰기·잠금 등 트랜잭션 수준 방어가 **따로** 필요하다 — 이 PRD 범위 밖이다.

### 관문이 못 막는 것
이 시큐리티 체인을 지나는 HTTP 요청만 보호한다. 배치·내부 호출·테스트·향후 두 번째 필터체인은
못 막는다. 그래서 **기존 서비스별 확인을 일괄 제거하지 않는다.**

## 리뷰에서 고친 것

구현 후 `reviewer` 에이전트 리뷰에서 나온 지적과 처리:

| 지적 | 처리 |
|---|---|
| 두 커스텀 필터를 같은 기준점(`AuthorizationFilter`) 앞에 걸어 **상대 순서가 프레임워크 계약이 아니다.** 뒤집히면 강등 필터의 `DataAccessException` 이 503 필터 밖으로 새어 C-9 가 조용히 무너진다 | 순서를 서로에게 직접 명시(`addFilterAfter(강등, 503필터)`)하고, **실제 체인의 필터 인덱스를 단언하는 테스트**를 추가했다. 주석이 아니라 실행으로 고정한다 |
| C-8 테스트가 이름이 주장하는 것보다 약하다 — 없는 토큰으로 `is4xxClientError()` 만 봐서 탈퇴자 분기에 닿지 않았다 | **탈퇴 전에 발급해 저장까지 된** 리프레시 토큰으로 바꾸고 401 `INVALID_TOKEN` 까지 단언한다. 그 과정에서 거부 사유가 "비활성 계정" 이 아니라 **탈퇴가 토큰 행을 함께 지우기 때문**임이 드러나, 실서버 E2E 의 401 관측과 이유까지 일치하게 됐다 |
| 정적·문서 경로에 토큰이 붙으면 조회가 돈다 — PRD 의 "게스트·정적 경로는 0회" 가 과한 주장 | 위 "잃는 것" 에 범위를 정확히 다시 적고, 경로 목록으로 거르지 않은 이유를 남겼다. 테스트로 "정적 경로가 막히지 않는다" 는 것도 고정했다 |
