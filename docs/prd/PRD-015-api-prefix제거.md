# PRD-015 — API 경로 `/api` prefix 제거

**이슈**: #75 · **ADR**: [0029](../adr/0029-drop-api-path-prefix.md) · **작성**: 2026-09-03

## 무엇을 왜

배포 도메인이 `dev-api.pickple.app` 로 이미 `api.` 서브도메인을 쓰는데 경로에 다시 `/api` 를
붙여 `dev-api.pickple.app/api/posts` 가 된다. 같은 말을 두 번 한다.

**증상은 "경로가 길다" 지만 원인은 그게 아니다.** prefix 가 **어디서 오는지**를 먼저 측정했다.

| # | 위치 | 측정 결과 |
|---|---|---|
| 1 | `server.servlet.context-path` | **미설정** — `src/main/resources`·`docker/` 전수 grep 0건 |
| 2 | `docker/Caddyfile` | **`/api` 를 라우팅 키로 안 씀** — `handle { reverse_proxy app:8080 }` 전량 전달 |
| 3 | 컨트롤러 애노테이션 | 클래스 레벨 `@RequestMapping` 4개 + 메서드 직접 1개 (`ImageUploadController`) |
| 4 | `SecurityConfig` | `/api/**` 매처 **7개** (permitAll 3 + POST 4) |
| 5 | `application.yml:165` | ⚠️ `springdoc.paths-to-match: /api/**` — **이슈 범위 조사에 없던 항목** |

**원인은 "설정이 아니라 컨트롤러에 손으로 반복해 적은 문자열"이다.** 그래서 제거 자체는 싸다.
비싼 것은 제거가 아니라 **파급**이다 — 이건 API 계약 변경이라 프론트가 `/api/...` 를
하드코딩하고 있으면 서버만 바꾸는 순간 전부 404 다. 백엔드 단독으로 밀 수 없다.

**5번은 조용한 실패다.** `paths-to-match` 가 `/api/**` 인 채로 prefix 를 걷어내면 필터에
아무것도 안 걸려 Swagger·`/v3/api-docs`·`/llms.txt`(ADR-0011 이 같은 스펙을 런타임 렌더)가
**전부 빈 문서**가 된다. 에러도 실패 테스트도 없이 문서만 비므로 배포 후에야 발견된다.

그래서 이 사이클은 **결정과 안전망을 먼저 놓고, 계약 변경은 합의 뒤로 미룬다.**

## 범위

**포함**

  상태는 `Proposed` (프론트 합의 전이므로 `Accepted` 아님)
- `ArchitectureTest` 새 `@Nested` 그룹 `ControllerMapping` 규칙 2개
  - 핸들러 매핑 경로 비어있음 금지 — **활성**
  - `@RestController` 의 클래스 레벨 `@RequestMapping` 금지 — 코드만 넣고 `@Disabled`
- `PostController.findAll` 의 bare `@GetMapping` → `@GetMapping("/api/posts")` (**URL 불변**)
- `docs/SPEC.md` — 계획된 경로 변경과 변경 이력 한 줄
- 이 PRD

**제외** (제외가 범위를 정의한다)
- **컨트롤러 5개의 `/api` 실제 제거 + `SecurityConfig` 매처 7개 동기화** — 프론트 합의 전이라
  착수할 수 없다(ADR-0029 "열린 질문"). 진행 중인 #21·#24·#76 과도 정면 충돌한다

  지금 바꾸면 오히려 현재 문서가 빈다
- **통합 테스트 경로 갱신** — 바꿀 경로가 아직 안 바뀌었다
- **기존 ADR·PRD 본문의 `/api/` 표기 수정** — ADR 은 불변이고, PRD 의 `/api/` 는 대부분
  **실측 완료 판정 기록**(`POST /api/images` 201 등)이다. 그 시점에 실제로 측정한 값이므로
  고치면 기록이 거짓이 된다. 경로가 바뀐 사실은 새 ADR 이 갖는다
- 경로 네이밍 정리(`/users/me` 와 `/auth/me` 공존 등) — 별개 결정

> 이 PRD 의 완료는 **"prefix 가 제거된 상태"가 아니다.** 그건 프론트 합의 뒤의 후속 PR 이 한다.

### 반증 결과 (규칙이 무언가를 실제로 막는가)

두 규칙을 **각각** 확인했다. 통과는 증거가 아니므로 위반을 주입해 실패를 확인했다.

| 규칙 | 주입한 위반 | 결과 |
|---|---|---|
| 핸들러 경로 비어있음 금지 | `PostController.findAll` 을 bare `@GetMapping` 으로 되돌림 | ✅ **이 규칙만** FAILED, 나머지 19개 PASSED. 메시지가 위반 메서드를 정확히 지목 |
| 클래스 레벨 매핑 금지 | `@Disabled` 를 뗌 (현재 코드가 이미 위반 상태) | ✅ **이 규칙만** FAILED. 작성 시점엔 3개였으나 **#21 머지 후 재측정에서 `VoteController` 가 합류해 4개**를 정확히 지목한다(ADR-0029 §위반 대상은 고정된 목록이 아니다) |

확인 후 둘 다 되돌렸다. 부수 확인 하나 — `ImageUploadController` 는 **위반으로 잡히지 않았다.**
`@PostMapping(path = "/api/images")` 로 `path` 속성을 쓰는데, ArchUnit 은 바이트코드를 읽어
Spring 의 `@AliasFor`(`value` ↔ `path`) 해석을 하지 않는다. `value` 만 검사했다면
멀쩡한 코드가 오검출됐을 것이다. 규칙이 `value` → `path` 순으로 본다.

## 열린 질문

1. **프론트가 `/api/...` 를 하드코딩하는가, base URL 로 주입하는가.** 후자면 브릿지 없이도
   전환이 싸고, ADR-0029 의 "대안 3 브릿지" 절반이 불필요해진다. **사람 간 합의라 이 사이클에서
   닫을 수 없다.**
2. **iOS 클라이언트 배포 주기.** 앱은 강제 업데이트 전까지 구 버전이 남으므로 브릿지 기간이
   앱 릴리스 주기만큼 길어진다. 그러면 "한시적" 전제 자체를 재검토해야 한다.
3. **브릿지 제거 기한.** 2번이 정해져야 정할 수 있다. ADR 이 `Accepted` 로 갈 때 명시한다.
4. **머지 순서 의존.** 이 PR 은 #21·#24·#76 이 **모두 머지된 뒤 마지막에** 머지해야 한다.
   먼저 머지되면 나중에 들어온 bare 매핑을 규칙이 보지 못한다(ADR-0029 "머지 순서" 참조).
5. **`springdoc.paths-to-match` 의 장기 의도** — PRD-006 이 이미 남긴 질문이다.
   prefix 를 걷으면 `/api/**` 는 무의미해지므로 그때 함께 결론 내야 한다.
