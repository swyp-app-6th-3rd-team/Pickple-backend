# PRD-024 — 조회 계층 타입 안전화

**이슈**: [#130](https://github.com/swyp-app-6th-3rd-team/Pickple-backend/issues/130)

## 무엇을 왜 만드는가

조회 저장소가 **네이티브 SQL 문자열 + `List<Object[]>` + 컬럼 인덱스 상수**로 짜여 있다.
이 조합의 대가는 셋이다.

1. **런타임에만 깨진다.** SELECT 절에 컬럼을 끼워 넣으면 뒤 인덱스가 전부 밀리는데 컴파일은 통과한다.
2. **문자열 SQL 조립.** 컬럼명·정렬 방향을 `.append()`·`.formatted()` 로 잇는다. 지금은 enum 필터가
   막지만 방어가 **호출자 규약에 의존**한다.
3. **선례 복제로 번진다.** 인덱스 상수 클래스가 파일마다 반복된다.

`Object[]` 는 증상이고 원인은 **조회 계층 표준의 부재**다. `QuerydslConfig` 에 `JPAQueryFactory` 빈이
있고 Q클래스 16개가 생성되는데 사용처가 0건이었다 — 배선만 해두고 아무도 쓰지 않았다.

| 대상 | 제외 사유 |

| 원자적 카운터 6개 (`PostCounterRepository`) | `GREATEST(CAST(…))` 템플릿이 필요해 이득 대비 위험이 크다 |

`CommentRepository` 를 제외한 것이 이 PRD 의 판단이다. "네이티브 쿼리" 를 기준으로 잡았다면
멀쩡한 코드를 건드렸을 것이다 — **판별 기준은 네이티브 여부가 아니라 `Object[]` 사용 여부**다.

## 측정 기록

### 1. `RankingListRepository` → QueryDSL

**실행계획 (전환 후)**

```
-> Limit: 21 row(s)  (cost=0.71 rows=1)
   -> Index range scan on u using idx_users_ranking_order over (10 < ranking)
      index condition: ((u.ranking not null) and (u.ranking > 10))
```

`idx_users_ranking_order` **range scan** 유지. filesort·풀스캔 0건.
V10 마이그레이션이 기록한 기준(200k 회원에서 33ms → 0.060ms)의 인덱스를 그대로 탄다.

**회귀 방지**: 일회성 확인으로 끝내지 않고 `RankingControllerIT.sliceUsesRankingIndex` 로 남겼다.
정렬 키를 `u.point` 로 바꿔 **위반을 주입했을 때 실제로 실패**하는 것을 확인했다 —
통과만으로는 보호의 증거가 되지 않는다.

**제거된 것**: `Object[]` 6곳 · `Column` 상수 6개 · `toLong`/`toRanking` 방어 함수 2개 · 149줄 저장소

### 2. `JpaGradeStore` 프로젝션 교체 (#132)

**QueryDSL 로 옮기지 않았다.** `READ_INPUTS` 는 FROM 절 없는 스칼라 서브쿼리 SELECT 라 JPQL 문법에
없다. SQL 은 그대로 두고 **반환 타입만** 바꿨다 — 파일럿의 `Projections.constructor` 규약은 JPQL 전제라
여기 적용되지 않는다.

**매핑 방식: Spring Data 인터페이스 프로젝션** (`CommentRepository.CommentListRow` 선례).
record 매핑을 기각한 이유는 드라이버 타입이다 — `SUM()` 이 `BigDecimal` 로 오는데 Hibernate 의
네이티브 record 매핑은 생성자 인자 타입과 드라이버 타입이 맞아야 한다. 맞추려면 SQL 에 `CAST` 를
넣거나 record 가 `BigDecimal` 을 들어야 해서, 어느 쪽이든 `toLong` 이 막던 문제가 계약으로 새어 나온다.
인터페이스 프로젝션은 접근자 반환 타입에 맞춰 `ConversionService` 가 변환한다
(`spring-data-commons 4.1.0` `ProjectingMethodInterceptor.potentiallyConvertResult` 소스 확인).
`highest_grade`(TINYINT) 스칼라는 `JpaQueryMethod.potentiallyUnwrapReturnTypeFor` 가 `Optional<Integer>` 를
`Integer` 로 벗긴 뒤 `JpaQueryExecution.execute` 가 같은 `ConversionService` 로 변환한다(이종 리뷰가 바로잡음 —
초안은 `QueryExecutionResultHandler` 로 적었다). 오버플로는 이전 `BigDecimal.longValue()` 가 조용히 wrap 하던 것과
달리 `ConversionFailedException` 으로 드러난다 — 비트 단위 동일이 아니라 더 안전한 쪽으로의 차이다.

**ADR 을 쓰지 않았다.** 두 파일·한 패키지에 갇힌 결정이고 스키마·API 계약이 바뀌지 않으며, 방식을
바꾸더라도 리포지토리 인터페이스 하나만 고치면 된다. 근거는 `GradeRepository` javadoc 에 있다.

**실행계획 (교체 후 — SQL 이 같으므로 교체 전과 동일)**

```
-> Rows fetched before execution  (cost=0..0 rows=1)
-> Select #2 (subquery in projection; run only once)
    -> Aggregate: sum(ph.amount)  (cost=0.45 rows=1)
        -> Index lookup on ph using idx_point_user_created (user_id=1)  (cost=0.35 rows=1)
-> Select #3 (subquery in projection; run only once)
    -> Aggregate: count(0)  (cost=0.45 rows=1)
        -> Covering index lookup on v using idx_vote_user_created (user_id=1)  (cost=0.35 rows=1)
```

두 서브쿼리 모두 `user_id` 선행 인덱스 lookup, 테이블 스캔 0건. 투표 횟수는 커버링 조회다.

**회귀 방지**: `JpaGradeStoreIT.readInputsUsesUserIndexes` 가 `GradeRepository.READ_INPUTS` 상수를
**그대로** EXPLAIN 한다(SQL 을 베끼지 않아 문장이 바뀌면 함께 검사된다). 위반 주입 결과:

| 주입 | 결과 |
|---|---|
| `WHERE ph.user_id + 0 = :userId` (인덱스 무력화) | 9개 중 **1개 실패** — EXPLAIN 단언만 |
| `AS point` → `AS points` (별칭 드리프트) | 9개 중 **8개 실패** — 접근자가 null 을 돌려줘 첫 호출에서 NPE |

두 번째 행이 인터페이스 프로젝션의 트레이드오프다 — 이름으로 묶이므로 컴파일은 통과하지만,
`readInputs` 를 부르는 테스트 전부가 첫 호출에서 깨진다.

**동작 보존**: 사용자가 없을 때 이전 구현은 `NoResultException` 을 그대로 흘려 500 이었다. Spring Data 는
빈 값을 돌려주므로 `JpaGradeStore` 가 `GradePersistenceException` 을 던진다 — 각 기능 `infra` 의
`*PersistenceException` 규약(ADR-0039)을 따르며 응답은 같은 500 이다. 리뷰(동종)가 지적해 raw JPA 예외
재던지기에서 바꿨다. `JpaGradeStoreIT` 10건 · `GradeServiceIT` 7건 통과.

**제거된 것**: `Object[]` 1곳 · 인덱스 리터럴 `row[0]`·`row[1]` · `toLong` · `EntityManager` 직접 사용

## 열린 질문

- **2쿼리 분할의 성능 영향** (#3·#4·#5) — `FROM (SELECT…LIMIT)` 파생 테이블을 QueryDSL-JPA 가
  지원하지 않아 ① id 목록 → ② `WHERE id IN (…)` 로 나눈다. 쿼리가 1→2회로 늘지만 인덱스 이득은
  유지될 것으로 본다. **PR 3 에서 실측으로 판정한다.** 회귀가 나오면 해당 파일만 네이티브 유지 +
  프로젝션만 교체로 후퇴한다.
- `popularity_score` 매핑은 실측했으나(ADR-0041), `active_nickname` 은 아직 매핑하지 않았다.
  필요해지는 시점(#3)에 같은 방식으로 검증한다.
